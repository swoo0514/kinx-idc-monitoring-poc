# 알림 게이트웨이 기술 명세서 (데모 B·C 공용)

## 1. 시스템 개요 및 위치

본 모듈은 사내 및 MSP Zabbix, Wazuh 관측 시스템의 알림 데이터를 단일 접점에서 수집하여 **통합 심각도 정규화(SEV) ➔ 멱등성 검증 ➔ 태그 기반 라우팅**을 전담하는 공용 알림 게이트웨이(Egress Gateway)입니다. AI 기반 초동 분석(데모 C) 및 승인 기반 자가 치유 파이프라인(데모 B)의 공통 백엔드로 동작합니다.

```text
Zabbix Webhook Media Type ─┐
                           ├─▶ [통합 게이트웨이] 토큰 검증 ➔ 멱등성 검사 ➔ SEV 정규화 ➔ 태그 라우팅
Wazuh Integrator ──────────┘                                            │
                                 ┌──────────────────────────────────────┴──────────────────────────────────────┐
                                 ▼                                      ▼                                      ▼
                      triage (데모 C 트리아지)               remediate (데모 B 자가 치유)                digest / dashboard_only
```

## 2. 파일 구조 및 구성 모듈

| 파일 경로 | 주요 역할 및 담당 기능 |
|---|---|
| `gateway/app.py` | FastAPI 웹 애플리케이션 — REST 엔드포인트 제공, 토큰 검증, 멱등성 처리, 비동기 디스패치 |
| `gateway/severity.py` | 통합 심각도 정규화 상수 정의 — [`severity-normalization.md`](../docs/02-design/severity-normalization.md)의 코드 구현체 |
| `gateway/router.py` | 태그 기반 라우팅 로직 — `automate`, `scope` 태그 조합을 통한 처리 경로 분기 |
| `gateway/selftest.py` | 파이프라인 순수 제어 로직 독립 검증 모듈 (FastAPI 의존성 없이 실행) |
| `gateway/collector.py` | Zabbix, Loki, Wazuh 텔레메트리 데이터 비동기 교차 수집기 |
| `gateway/prejudge.py` | 과거 90일 발생 이력 기반 결정론적 만성/신규 장애 선판정 모듈 |
| `gateway/incident.py` | (감시 영역, 호스트, 알림 유형) 기반 디바운스 창 제어 및 알림 병합(Incident Merging) 모듈 |
| `gateway/llm.py` | Claude/Ollama LLM 어댑터 및 양방향 가명화(Masking) 파이프라인 |
| `gateway/slack.py` | Slack Block Kit 기반 알림 카드 및 트리아지 결과 회신 모듈 |
| `gateway/triage.py` | 수집 ➔ 가명화 ➔ LLM 연산 ➔ Slack 회신 전체 파이프라인 오케스트레이터 |
| `gateway/masking.py` | 호스트명·IP·그룹명 양방향 가명화 및 전송 항목 화이트리스트 |
| `gateway/keep.py` | 관제 도구(Keep) 알림 등록 — 조치 후보·생략 사건·분석 결과 |
| `gateway/pending.py` | 디바운스 대기 알림 영속화 및 재기동 시 재투입 (§8-4) |
| `gateway/heartbeat.py` | 생존 신호 전송 및 처리량 집계 (§20) |
| `gateway/holmes.py` | HolmesGPT 심층 조사 연동 (§10) |

**Zabbix 서버 측 스크립트는 본 패키지에 두지 않습니다.** 웹훅 미디어 타입 스크립트(`ansible/files/zabbix_media_webhook.js`·`zabbix_media_selfwatch.js`)는 Zabbix 서버 내장 엔진에서 실행되며 게이트웨이 프로세스가 읽거나 실행하지 않습니다. Ansible 이 `lookup('file')` 로 본문을 읽어 API 로 등록하고, 이후에는 Zabbix 서버 DB 에 저장된 사본이 동작합니다. 파이썬 패키지 내에 배치할 경우 게이트웨이 구성 요소로 오인됩니다.

## 3. 실행 및 검증 방법

```bash
# bot/ 디렉토리 이동 및 가상환경 설정
cd bot
source ~/bot-venv/bin/activate
pip install -r requirements.txt

# 게이트웨이 인증 토큰 설정 (코드 내 하드코딩 금지)

# 게이트웨이 데몬 기동 (단일 Worker 프로세스로 실행)
```

## 4. REST API 엔드포인트 명세

### 4-1. POST `/webhook/zabbix`

Zabbix 웹훅 액션으로부터 알림 데이터를 수신합니다 (헤더 `X-Gateway-Token` 인증 필수).

**요청 페이로드 예시:**
```json
{
  "source": "zabbix-internal",
  "event_id": "12345",
  "event_value": 1,
  "event_name": "Filesystem /data usage is high on lab-web01",
  "nseverity": 4,
  "host": "lab-web01.novalocal",
  "tags": [
    {"tag": "automate", "value": "service_restart"},
    {"tag": "scope", "value": "full"}
  ]
}
```

**응답 페이로드 예시 (신규 수신):**
```json
{
  "status": "accepted",
  "sev": "SEV2",
  "route": "remediate",
  "playbook": "service_restart"
}
```

**응답 페이로드 예시 (중복 수신):**
```json
{
  "status": "duplicate"
}
```
*(동일 `(source, event_id, event_value)` 조합 수신 시 HTTP 200 `duplicate`를 반환하여 Zabbix의 불필요한 재전송을 즉시 중단시킵니다.)*

### 4-2. POST `/webhook/wazuh`

Wazuh Manager 커스텀 연동 스크립트로부터 경보 데이터를 수신합니다. (`alert_id`, `rule_id`, `rule_level`, `agent_name` 전달)

## 5. Zabbix 미디어 타입 배선 명세

Zabbix Administration ➔ Media types ➔ Create Media Type: Type = **Webhook**, Script = `ansible/files/zabbix_media_webhook.js`

스크립트 본문은 Ansible 이 `lookup('file')` 로 읽어 API 로 등록하며, 이후 Zabbix 서버 DB(`media_type.script`)에 저장되어 **Zabbix 서버 내장 엔진에서 실행**됩니다. 게이트웨이 프로세스는 본 스크립트를 읽거나 실행하지 않습니다.

### 설정 파라미터 매핑표

| 파라미터 명칭 | 설정값 (Zabbix 매크로) | 검증 상태 및 비고 |
|---|---|---|
| `gateway_url` | `http://<게이트웨이_IP>:8800` | 환경별 IP 지정 |
| `token` | `{$GATEWAY_TOKEN}` | DB 저장 파라미터 |
| `source` | `zabbix-internal` 또는 `zabbix-msp` | 소스 구별 매크로 |
| `event_id` | `{EVENT.ID}` | 공식 매크로 검증 완료 |
| `nseverity` | `{EVENT.NSEVERITY}` | Numeric event severity 매크로 검증 완료 |
| `event_name` | `{EVENT.NAME}` | 공식 매크로 검증 완료 |
| `tags_json` | `{EVENT.TAGSJSON}` | JSON Array event tags 매크로 검증 완료 |
| `host` | `{HOST.HOST}` | FQDN 호스트명 매크로 검증 완료 |
| `event_value` | `{EVENT.VALUE}` | 장애(1)/해소(0) 구분 매크로 |

## 6. 핵심 아키텍처 의사결정 및 기술적 근거

1. **`severity.py` 단일 구현체 적용 (Single Source of Truth):**  
   사내 Zabbix Warning ➔ `SEV4` (노이즈 강등), MSP Warning ➔ `SEV3` (고객 통보 신호 유지), Wazuh 레벨 10+ ➔ `SEV2` 정규화 규칙을 코드 수준에서 엄격히 보장합니다.
2. **미지 소스 및 예외 상태의 페일세이프(Fail-safe) 정규화:**  
   미정의 소스 또는 스펙 범위를 벗어난 데이터 수신 시 과소평가로 인한 장애 누락을 방지하고자 `SEV2`로 상향 정규화합니다.
3. **상수 시간 비교를 통한 타이밍 공격 차단 (`hmac.compare_digest`):**  
   인증 토큰 비교 시 단순 `==` 연산자 대신 `hmac.compare_digest`를 적용하여 타이밍 부채널(Timing Side-channel) 공격 위험을 차단합니다.
4. **인메모리 1시간 TTL 멱등성 버퍼 연산:**  
   동일 알림 재전송 시 중복 LLM API 호출 및 중복 Slack 카드 발송을 차단합니다. (프로덕션 환경 적용 시 Redis/DB 지속화 스토리지로 마이그레이션 추진)
5. **계약 조건의 코드화 (`scope` 우선순위 제어):**  
   트리거에 `automate` 태그가 존재하더라도 위탁 계약 속성이 `scope=notify_only`일 경우, `router` 단에서 자동 조치 경로 진입을 차단하고 `triage` 경로로 강제 라우팅합니다.

## 7. 컨텍스트 수집기 및 선판정 로직 (`collector.py` / `prejudge.py`)

트리아지 경로 진입 시 LLM 연산에 필요한 재료 데이터를 3개 소스로부터 비동기 교차 수집하고 결정적 선판정을 수행합니다.

### 7-1. 교차 소스 텔레메트리 수집 (Multi-source Context Collection)

- **Loki (로그 축):** `/loki/api/v1/query_range` 엔드포인트를 통해 `{<라벨>="<host>"}` **정확 일치** 조건으로 최근 15분간의 로그 최대 40줄(라인당 300자 제한)을 수집합니다. 라벨명은 `LOKI_HOST_LABEL`(기본 `host`)로 지정하며, 호스트명 해석 규칙과 0건 응답의 판정은 §12 를 따릅니다.
- **Wazuh (보안 축):** OpenSearch `wazuh-alerts-*/_search` 엔드포인트를 통해 `agent.name` 조건으로 최근 15분간 발생한 보안 경보 최대 20건을 수집합니다.
- **조회 실패 및 미배선 처리:** API 호출 실패 시 예외를 삼키지 않고 `sources` 메타데이터에 `unavailable` 상태를 기록하여, 거짓 안심(False Confidence) 기반 분석을 차단합니다.

### 7-2. Zabbix API 읽기 전용 5종 병렬 조회

1. `event.get`: 현재 이벤트 상세 및 태그 수집
2. `trigger.get`: 트리거 조건식 및 메트릭 역참조 정보 수집
3. `item.get` ➔ `history.get`: 관련 메트릭 최근 1시간 수치 추이(20개 데이터 포인트) 수집
4. `event.get` (90일 창): 동일 트리거의 과거 누적 발생 이력 조회 (선판정 연산 입력값)
5. `host.get`: 호스트 메타데이터 및 그룹 정보 수집

*①~④ 항목은 `asyncio.gather`를 통해 병렬 호출되며, 개별 콜 타임아웃을 5초로 제한하여 30초 처리 예산 내 구동을 보장합니다.*

### 7-3. 결정적 만성/신규 선판정 규칙 (`prejudge.py`)

과거 90일간 동일 트리거의 누적 발생 횟수를 바탕으로 결정론적 판정을 내리며, LLM이 이를 재판정하거나 변경할 수 없습니다.

| 최근 90일 발생 횟수 | 최종 판정 | LLM 회신 톤 및 출력 메시지 |
|---|---|---|
| 0회 | **신규 (New)** | *"처음 관측된 미지 장애 — 즉시 원인 확인 권장"* |
| 1~2회 | **재발 (Recurrent)** | *"최근 90일 내 N회 재발된 장애 — 이전 발생 건과의 공통점 점검"* |
| 3회 이상 | **만성 (Chronic)** | *"알려진 만성 반복 장애 (90일간 N회 발생) — 정비 대상 항목"* |

#### 만성 기준의 산정 근거

**본 임계값은 횟수가 아니라 재발 간격으로 정의합니다.** 횟수로 고정할 경우 두 가지 문제가 발생합니다. 첫째, 특정 수치를 선택한 근거를 제시할 수 없습니다. 둘째, 관측 창을 90일에서 180일로 변경하면 동일 횟수의 의미가 2배로 완화되나 설정상 변화가 드러나지 않습니다.

| 설정 항목 | 기본값 | 산출 |
|---|---|---|
| `PREJUDGE_WINDOW_DAYS` | 90 | 관측 창 |
| `PREJUDGE_CHRONIC_INTERVAL_DAYS` | 30 | 만성으로 판정할 재발 간격 |
| 만성 하한(산출값) | 3 | `ceil(창 ÷ 간격)`, 최솟값 2 |
| `PREJUDGE_CHRONIC_MIN` | (미설정) | 지정 시 산출값 대신 해당 값을 사용 |

**30일 선정 근거:** MSP 월간 리포트 발행 주기와 일치시킵니다. 월 1회 이상 재발하는 항목은 리포트 발행 시마다 포함되며, 매 리포트에 반복 등장함에도 해소되지 않은 항목이 정비 대상에 해당합니다. 즉 **"월간 리포트에 매회 등장하는 항목"**을 만성으로 정의합니다. 리포트 주기 변경 시 본 값도 함께 조정합니다.

**외부 기준 부재:** SRE 문헌에서 반복 알림의 만성 판정 횟수를 규정한 자료는 확인되지 않았습니다. ITIL 문헌에는 "동일 증상 30일 내 3건 이상 시 별도 관리 대상 등록"이 통상적 관행으로 언급되나, 동일 자료에서 표준이 아닌 조직별 조정값임을 명시하고 있습니다(간격 환산 시 본 기준과 동일한 30일).

**실측 분포 (사내 Zabbix 90일):** 트리거 계열의 71.7%가 관측 기간 중 1회만 발생하며, 상위 2.0%(200회 이상)가 전체 이벤트의 95.0%를 차지합니다. 이러한 분포에서는 임계값을 2회로 낮추거나 50회로 상향하여도 **이벤트 기준 만성 비중은 97~99% 구간에서 변동하지 않습니다.** 임계값 변경이 실질적으로 영향을 미치는 대상은 정비 후보 목록의 범위(계열 기준 10.5% → 18.8%)입니다.

## 8. 알림 병합 메커니즘 (`incident.py`)

### 8-1. 알림 병합 및 브리지 규칙 (Incident Merging & Bridge Rules)

단일 알림 단위 트리아지의 한계를 극복하기 위해 동일 호스트 및 연관 유형의 알림들을 디바운스 창(Debounce Window) 동안 수집하여 **단일 인시던트로 병합 처리**합니다.

- **기본 병합 키:** `incident_key(host, class) = (host, bridge_id(class))`
- **연관 브리지 규칙 (`BRIDGE_GROUPS`):**
  - `{replication, cpu_io_pressure}`: DB 복제 지연 알림과 CPU/IO 자원 경합 알림을 단일 사건으로 병합
  - `{disk_space, service_down}`: 디스크 용량 초과 알림과 서비스 중단 알림을 단일 사건으로 병합
  - `auth_security` (보안 경보) 항목은 브리지 그룹에 포함하지 않고 항상 독립 사건으로 격리 처리합니다.

### 8-1-1. 감시 영역 구분 (Monitoring Realm)

**호스트명은 개별 감시 서버 내에서만 고유합니다.** 사내 Zabbix 와 MSP Zabbix 를 동시에 수용하는 구성에서는 서로 다른 물리 장비가 동일한 호스트명을 가질 수 있으며, 호스트명만으로 병합할 경우 **서로 다른 고객사의 알림이 단일 인시던트로 병합**됩니다. 이 경우 단일 Slack 카드·단일 LLM 호출·단일 리포트 항목에 복수 고객사의 데이터가 포함됩니다.

이에 병합 키를 `(감시 영역, 호스트, 브리지 ID)` 로 구성합니다.

| 환경 변수 | 형식 | 기본값 |
|---|---|---|
| `INCIDENT_REALM_MAP` | `소스=영역,소스=영역` | (미설정 — 전 소스 단일 영역) |

**소스가 아닌 영역 단위로 구분하는 이유:** 동일 장비를 Zabbix 와 Wazuh 가 각각 보고하므로, 소스를 그대로 키에 포함하면 두 관측 소스가 분리되어 교차 소스 병합이 성립하지 않습니다. 영역은 소스의 상위 개념으로, 사내 Zabbix 와 사내 Wazuh 는 동일 영역, MSP Zabbix 는 별도 영역으로 분류합니다.

```bash
INCIDENT_REALM_MAP=zabbix-internal=internal,zabbix-msp=msp,wazuh=internal
```

**미설정 시 동작:** 전 소스를 단일 영역으로 처리하며, 이는 감시 서버가 1대인 환경의 기존 동작과 동일합니다. 기동 시 미설정 상태를 로그로 표시합니다.

**인시던트 지문에도 영역이 포함됩니다.** 미포함 시 관제 도구(Keep)에서 서로 다른 고객사의 동일 유형 사건이 단일 레코드로 중복 제거되며, 심층 조사 결과가 타 고객사 레코드에 병합될 수 있습니다.

**적용 범위 한계:** 본 항목은 병합·지문 단계의 구분입니다. 컨텍스트 수집 시 조회 대상 Zabbix 서버를 영역에 따라 선택하는 기능은 미구현 상태로, 현재는 `ZABBIX_URL` 단일 인스턴스만 조회합니다(§7-2). 복수 감시 서버 환경에서는 후속 반영이 필요합니다.

### 8-2. 디바운스 창 제어 (Debounce Window Control)

- **일반 디바운스 대기:** 마지막 알림 수신 후 `INCIDENT_DEBOUNCE_S`(기본 90초) 동안 추가 알림이 없을 경우 인시던트 마감
- **최대 창 허용 시간:** 알림이 지속 수신되더라도 `INCIDENT_MAX_WINDOW_S`(기본 300초) 도달 시 강제 마감 및 트리아지 실행
- **우선순위 단축 대기:** `SEV1` 알림 포함 시 `INCIDENT_PRIORITY_DEBOUNCE_S`(기본 15초)로 대기 시간 단축

### 8-3. 분석 발동 조건 (`should_triage`)

인시던트 마감 후 LLM 분석을 실제로 수행할지 판정합니다. 아래 순서로 평가하며 먼저 성립하는 조건에서 판정을 확정합니다.

| 순서 | 조건 | 판정 | 근거 |
|---|---|---|---|
| 1 | `SEV1` 포함 | 발동 | 위중 사건은 조건 없이 분석 |
| 2 | 복수 알림 병합 | 발동 | 교차 축이 이미 존재 |
| 3 | 교차 소스 조회 실패(`unavailable`) 또는 이름 불일치(`unmatched`) | 발동 | 신호 부재가 아니라 미상이므로 보수적 판단 (§12) |
| 4 | 교차 신호 `INCIDENT_GATE_MIN_CROSS` 건 이상 | 발동 | 단일 알림에 로그·보안 신호가 동반 |
| 5 | 선판정 결과가 **신규** | 발동 | 아래 단일 소스 환경 항목 참조 |
| 6 | 그 외 | 스킵 | 정상 조회 상태에서 교차 신호가 없는 만성·재발 알림 |

조건 3 과 5 에는 각각 독립적인 시간당 상한을 적용합니다(아래 폭주 방지 항목).

**단일 관측 소스 환경 대응:** 로그·보안 축이 미배선된 환경에서는 위 조건 중 3·4 가 성립하지 않습니다. 미배선(`disabled`)은 조회 실패로 계상되지 않고, 교차 신호는 항상 0 으로 산출되며, 90일 상관 분석에서 유효한 교차 유형 조합이 확인되지 않아 병합 조건도 발생하지 않습니다. 잔여 조건인 `SEV1` 은 사내 심각도 분포상 극소수에 해당하므로(Warning 등급 99.5%), 조건 5 가 없으면 분석 구동 빈도가 사실상 0 에 수렴합니다.

이에 따라 **선판정 결과가 신규(최근 90일 내 동일 트리거 이력 없음)인 사건**을 독립 발동 사유로 추가하였습니다. 처음 관측되는 문제는 대응 이력이 존재하지 않으므로 분석의 정보 이득이 가장 큰 구간입니다.

**폭주 방지 상한:** 조건 3 과 5 는 관측 환경의 상태 변화만으로 다수 호스트에서 동시에 성립할 수 있으므로 각각 최근 1시간 이동 창 기준의 상한을 적용합니다. 두 예산은 분리되어 있으며, 한쪽이 소진되어도 다른 쪽 발동에는 영향을 주지 않습니다.

| 사유 | 폭주 발생 조건 | 설정 항목 | 기본값 |
|---|---|---|---|
| 조회 실패 · 이름 불일치 (조건 3) | 관측 소스 1종의 장기 중단 또는 명명 규칙 불일치가 전체 호스트에 적용된 상태 | `INCIDENT_GATE_DEGRADED_MAX_PER_HOUR` | 30건 |
| 신규 판정 (조건 5) | 신규 트리거를 템플릿 단위로 다수 호스트에 일괄 적용 | `INCIDENT_GATE_NEW_MAX_PER_HOUR` | 20건 |

상한 도달 시 스킵 사유에 도달 사실을 기록합니다. 조건 3 의 상한 도달은 관측 소스 자체의 지속적인 이상을 의미하므로, 상한값 조정이 아니라 해당 소스의 복구를 우선 조치 대상으로 삼습니다. 조건 5 전체를 해제하려면 `INCIDENT_GATE_FIRE_ON_NEW=0` 을 설정합니다.

### 8-4. 대기 알림 영속화 (Pending Alert Persistence)

디바운스 창 대기 중 프로세스가 종료될 경우 해당 인시던트가 소실되며, 발송 측은 이미 성공 응답(200)을 수신하였으므로 재전송을 수행하지 않습니다. 이를 방지하기 위해 대기 상태 알림을 파일에 선기록한 후 응답합니다.

| 항목 | 내용 |
|---|---|
| 기록 대상 | `triage` 경로 알림 (디바운스 대기가 발생하는 유일한 경로) |
| 기록 위치 | `GATEWAY_PENDING_FILE` (기본 `~/.kinx-gateway/pending.jsonl`) |
| 기록 방식 | JSON Lines 추가 기록 후 `fsync` 완료 시점에 200 반환 |
| 기록 실패 시 | HTTP 503 반환 → Zabbix 미디어 타입 `Attempts`(기본 3회) 재시도로 위임 |
| 제거 시점 | 인시던트 분석 완료 후 |
| 재기동 처리 | 잔여 항목 자동 재투입, 시도 한도 `GATEWAY_PENDING_MAX_REPLAY`(기본 3회) 초과 시 폐기 및 오류 로그 기록 |

**제거 시점 선정 근거:** 분석 수행 전 제거 시 분석 구간 장애에서 알림이 소실되며, 분석 완료 후 제거 시 동일 상황에서 재기동 후 카드가 1회 중복 게시됩니다. 중복 게시는 육안 식별이 가능하나 소실은 식별이 불가능하므로 후자를 채택하였습니다.

**적용 범위 한계:** `digest`·`dashboard_only`·`remediate` 경로는 대기 없이 즉시 처리되므로 기록 대상에서 제외하였습니다. 해당 경로에서도 처리 직전 프로세스 종료 시 소실이 발생할 수 있으나, 대기 구간(90~300초) 대비 노출 시간이 현저히 짧습니다.

### 8-5. 수동 분석 요청 (Manual Analysis Request)

발동 조건(§8-3)에 의해 분석이 생략된 사건에 대해, 관제 담당자가 임의 시점에 분석을 직접 요청할 수 있는 경로를 제공합니다. 관측 소스 미배선 환경에서는 생략 비율이 높으므로, 해당 경로가 없을 경우 봇의 판정이 최종 결정으로 확정되며 사람이 이를 번복할 수단이 존재하지 않습니다.

| 항목 | 내용 |
|---|---|
| 진입점 | Keep 알림 카드의 Run Workflow (`keep/workflows/analyze_now.yml`) |
| 안전 게이트 | `alert.playbook == 'analyze'` — 해당 속성이 없는 카드에서는 미동작 |
| 대상 카드 | 발동 조건 미충족으로 생략된 사건, `digest`·`dashboard_only` 경로 알림 |
| 실행 모듈 | `bot/analyze_now.py` (SSH 경유 실행) |
| 발동 조건 | `run_incident(force=True)` — 조건 재평가를 수행하지 않음 |
| 결과 출력 | 기존 트리아지와 동일한 Slack 카드 |

**사건 복원 방식:** 생략 시점의 컨텍스트를 저장하지 않고, 알림 식별자 문자열(`analyze_ref`)만 카드에 실어 요청 시점에 Zabbix 를 재조회합니다. 이는 생략 이후 경과 시간 동안 변화한 상태를 분석에 반영하기 위함입니다. 형식은 `소스,이벤트ID,트리거ID,유형` 이며 복수 알림은 `|` 로 연결합니다.

**발동 조건 미적용 근거:** 본 경로는 봇의 판정을 사람이 번복하는 절차이므로, 조건을 재평가할 경우 요청 자체가 무시됩니다.

**랩 검증 (2026-08-10):** 발동 조건에 의해 생략된 사건을 대상으로 실행하여 수집·분석·Slack 게시 전 구간 정상 동작을 확인함(총 20.8초, Claude 정상 경로).

### 8-6. 정상 종료 시 대기 사건 마감 (Graceful Flush)

프로세스 종료 시그널 수신 시 디바운스 대기 중인 사건을 즉시 마감하고 처리합니다. §8-4 의 대기 알림 영속화가 강제 종료를 대상으로 한다면, 본 항목은 정상 종료 경로에 해당합니다.

**미적용 시 영향:** 데이터는 대기 파일이 보존하므로 소실되지 않으나, 두 가지 손실이 발생합니다.

| 항목 | 내용 |
|---|---|
| 대기 시간 재계산 | 재기동 후 디바운스 창을 처음부터 다시 계산함. 기존 대기분이 무효화됨 |
| 재투입 횟수 소모 | 재기동 1회당 재투입 시도 횟수가 1 증가함. 배포 등으로 반복 재기동 시 미처리 알림이 상한(`GATEWAY_PENDING_MAX_REPLAY`, 기본 3회)에 도달하여 폐기됨 |

**제한 시간:** `INCIDENT_FLUSH_TIMEOUT_S`(기본 25초). 초과분은 대기 파일에 잔존하여 재기동 후 처리됩니다. 종료가 무한정 지연되면 관리자가 강제 종료하게 되며, 그 경우 정상 종료 경로 자체가 성립하지 않습니다.

**대기 목록 제거 시점:** 처리 완료 이후로 한정합니다. `finally` 절에 배치할 경우 마감 제한 시간 초과에 따른 취소 시에도 제거가 실행되어, 처리하지 않은 알림이 소실됩니다.

## 9. 실시간 원시 알림 표출 (Fast-Path Pipeline)

디바운스 창 마감 대기 시간으로 인한 초동 통보 지연을 방지하기 위해 **원시 알림 Fast-Path 파이프라인**을 제공합니다.

```text
알림 수신 ──▶ [0초] 원시 알림 카드 즉시 게시 (Slack 최상위 메시지)
   │
   ├─▶ 후속 알림 수신 ──▶ 동일 Slack 스레드 답글로 추가 표출
   │
   └─▶ 디바운스 창 마감 ──▶ LLM 초동 분석 결과를 동일 스레드 답글로 최종 회신
```

인시던트 버퍼 생성 시 최상위 Slack 메시지를 즉시 생성하고, 이후 수집되는 알림 및 최종 LLM 분석 결과를 해당 메시지의 스레드(Thread) 답글로 병합하여 메시지 파편화를 방지합니다.

## 10. HolmesGPT 심층 조사 연동 (`holmes.py`)

선판정 결과를 활용하여 분석 가치가 높은 미지 장애 및 긴급 장애에 심층 조사 리소스를 효율적으로 배분합니다.

### 심층 조사 발동 순서 및 조건

1. `scope=notify_only` 및 마스킹 미배치 조건 ➔ **발동 차단** (보안 유출 방지)
2. `SEV1` 긴급 장애 ➔ **무조건 발동**
3. 게이트웨이 1차 분석 열화(`degraded`) 상태 ➔ **무조건 발동** (분석 품질 보완)
4. 선판정 결과 **만성 (Chronic)** 장애 ➔ **억제** (기지 장애에 대한 리소스 남용 방지)
5. 선판정 결과 **신규 (New)** 장애 ➔ **우선 발동** (정보 이득 극대화)
6. 복수 알림 병합 사건 ➔ **발동**

심층 조사 결과는 신규 알림 카드를 생성하지 않고, 1차 분석 결과가 게시된 **Slack 스레드의 답글 및 Keep 인시던트 Note 항목**에 비동기(`asyncio.create_task`)로 첨부됩니다.

## 11. 자가 치유 조치 후보 경로 연동 (`router.py` / `keep.py`)

트리거 내 `automate` 태그가 정의되고 계약 제약이 없는 경우, 게이트웨이는 알림을 `remediate` 경로로 라우팅하고 Keep 승인 큐에 등록합니다.

```text
Zabbix 트리거 (automate=service_restart)
  │
  ▼
게이트웨이 라우팅 (route=remediate) ──▶ Keep 승인 큐 등록 (상태: 승인 대기)
                                               │
                                      [관제 담당자 승인 클릭]
                                               │
                                               ▼
                                   Keep 워크플로 실행 ➔ Ansible 플레이북 실행 ➔ 상태 재검증
```

### Keep 워크플로 동적 매크로 연동

Ansible 실행 파라미터 하드코딩을 제거하고, Keep 알림 객체의 동적 필드를 매핑하여 플레이북을 호출합니다:
- `target_host`: `{{ alert.host }}`
- `service_name`: `{{ alert.service }}`
- `playbook_name`: `{{ alert.playbook }}`

워크플로 시작부에 `if: "'{{ alert.playbook }}' == 'service_restart'"` 안전 게이트를 배치하여, 지정된 플레이북 외의 무단 실행을 차단합니다.

## 12. 교차 소스 조회 상태 계약 (Source Status Contract)

수집기(`collector.py`)의 외부 API 조회 연산 결과를 4가지 명시적 상태로 구분하여 데이터 부재에 따른 오판을 차단합니다.

| 수집 상태 (`sources`) | 정의 및 상태 의미 | LLM 분석 및 프롬프트 해석 지침 |
|---|---|---|
| `ok` | API 정상 조회 완료 | 데이터 부재 시 **"이상/침해 흔적 없음"**으로 판정 가능 |
| `unavailable` | API 연동 실패 | 데이터 부재 시 **"조회 실패에 따른 미상 상태"**로 명시 (안심 단정 금지) |
| `unmatched` | 조회는 성공하였으나 해당 소스가 이 호스트 이름을 보유하지 않음 | 데이터 부재 시 **"호스트 이름 불일치로 조회되지 않음"**으로 명시하고, 확인 명령에 이름 대조 항목을 포함 |
| `disabled` | 미연동 설정 상태 | 해당 관측 축 분석 대상에서 제외 |

**`unmatched` 판정 절차:** 조회 결과가 0건인 경우에 한하여 추가 확인을 수행합니다. Loki 는 라벨 값 목록 API(`/loki/api/v1/label/<label>/values`)로, Wazuh 는 동일 조건의 건수 전용 질의(`size: 0`)로 최근 7일 범위를 조회하여 해당 호스트 이름의 등록 여부를 확인합니다. 확인 질의 자체가 실패한 경우에는 판정이 불가하므로 `unavailable` 로 처리합니다. 결과가 존재하는 정상 경로에서는 추가 질의가 발생하지 않습니다.

**도입 배경:** 관측 소스 3종(Zabbix·Loki·Wazuh)이 동일 호스트를 각기 다른 이름으로 식별하는 문제가 랩 환경에서 실측되었습니다(Zabbix `node1` / Loki `vm-target-001.novalocal` / Wazuh FQDN). 이름이 일치하지 않으면 API 는 정상 응답과 함께 빈 결과를 반환하므로, 기존 로직은 이를 조회 성공으로 처리하여 분석 봇이 "로그에 기록 없음"을 사실로 단정하는 결함이 존재하였습니다.

**관측 축 면제 대상:** 해당 관측 축의 데이터가 원천적으로 발생하지 않는 호스트가 존재합니다. 이러한 호스트를 이름 불일치로 판정하면 알림 발생 시마다 분석이 구동되며, 실제 불일치 대응에 사용할 시간당 상한(§8-3)을 선점하게 됩니다. Zabbix 호스트명 패턴을 등록하면 해당 축의 조회를 수행하지 않고 `disabled` 로 기록합니다. 와일드카드는 `*` 를 사용합니다.

| 환경 변수 | 적용 축 | 등록 대상 |
|---|---|---|
| `LOGS_EXEMPT_HOSTS` | Loki | OS 가 존재하지 않는 가상 호스트(인증서 만료 감시 대상, 리포트 값 저장용) |
| `SECURITY_EXEMPT_HOSTS` | Wazuh | 위 가상 호스트 + Wazuh 에이전트 미배포 호스트 |
| `LOG_AXIS_EXEMPT_HOSTS` | 양쪽 | 축별 변수 미지정 시 적용되는 기본값 |

```bash
LOGS_EXEMPT_HOSTS=cert-*,report-*
SECURITY_EXEMPT_HOSTS=cert-*,report-*,customer-*,lab-*,Zabbix server
```

**두 축의 커버리지가 다른 이유:** 로그 축은 Alloy 의 라벨 변환을 통해 복수 컨테이너를 단일 논리 호스트로 귀속시킬 수 있습니다. 반면 Wazuh 는 에이전트가 OS 인스턴스 단위로 배포되므로, 컨테이너를 특정 논리 호스트의 에이전트로 귀속시킬 수단이 없습니다(컨테이너 내부 에이전트 설치는 권장 방식이 아님). 실환경 역시 Wazuh 도입 진행 단계로 에이전트가 일부 서버에만 배포된 상태이므로, 축별 개별 선언이 필요합니다.

**관련 설정:** 라벨 이름이 `host` 가 아닌 환경을 위해 `LOKI_HOST_LABEL` 환경 변수를 제공합니다. 조회 질의와 확인 질의가 동일한 값을 사용합니다.

**호스트 이름 해석 규칙 (`_resolve_label`):** `HOST_LABEL_MAP` 의 명시적 매핑을 최우선으로 적용하고, 미지정 시 인터페이스 `dns` 필드를 사용하되 **FQDN 형태(점 포함)인 경우로 한정**합니다. 조건 미충족 시 Zabbix 호스트명을 사용합니다. 랩 실측 결과 `dns` 필드에 컨테이너 이름(`zabbix-agent2`, `snmpsim`)이 입력된 사례가 확인되었으며, 해당 값은 복수 호스트가 공유할 수 있어 타 호스트의 로그를 조회 대상 호스트의 데이터로 오인할 위험이 존재합니다.

**사전 점검 명령:** 위 판정은 사건 발생 시 해당 호스트 1대에 대해서만 수행됩니다. 에이전트 배포 직후 또는 명명 규칙 변경 후에는 전수 대조가 필요하므로 진단 명령을 제공합니다. 수집기와 동일한 이름 해석 규칙(`HOST_LABEL_MAP` ➔ 인터페이스 `dns` ➔ Zabbix 호스트명)을 사용합니다.

```bash
python3 probe.py names
```

수집 상태 정보는 마스킹 파이프라인을 거쳐 LLM 프롬프트 및 Slack 알림 카드 배지(⚠️ 조회 실패 · ⚠️ 이름 불일치)로 전파되어, 시스템 장애 상황에서의 거짓 안심(False Confidence) 발생을 차단합니다.

## 20. 게이트웨이 생존 감시 (Heartbeat)

이상 신호의 발생이 아니라 **정상 신호의 부재**로 게이트웨이 중단을 감지합니다. 게이트웨이가 중단되면 알림은 계속 수신되나 분석이 수행되지 않으며, 이 상태는 어떠한 알림도 발생시키지 않습니다. 실환경에서 알림 채널 1종이 30일간 9,198건을 연속 실패했음에도 인지되지 않은 사례와 동일한 구조입니다.

### 20-1. 전송 방식

`gateway/heartbeat.py` 가 Zabbix sender 프로토콜을 표준 라이브러리로 직접 구현합니다(공식 문서 기준 — 헤더 `ZBXD` + 플래그 1바이트 + 데이터 길이 4바이트 리틀엔디언 + 예약 4바이트, 본문 `{"request": "sender data", "data": [...]}`). `zabbix_sender` 실행 파일에 의존하지 않으므로 설치 환경 제약이 없습니다.

| 환경 변수 | 기본값 | 설명 |
|---|---|---|
| `HEARTBEAT_ZABBIX_SERVER` | (없음) | 수신 Zabbix 서버 주소. 미설정 시 기능 전체 비활성 |
| `HEARTBEAT_ZABBIX_PORT` | `10051` | 트래퍼 수신 포트 |
| `HEARTBEAT_HOST` | (없음) | Zabbix 상의 수신 호스트명. 미설정 시 기능 전체 비활성 |
| `HEARTBEAT_INTERVAL_S` | `60` | 전송 주기 |

### 20-2. 전송 항목

생존 여부만으로는 **게이트웨이는 정상이나 알림이 유입되지 않는 상태**(발행 측 액션·미디어 장애)를 구분할 수 없으므로, 마지막 알림 수신 이후 경과 시간과 처리량을 함께 전송합니다.

| 아이템 키 | 내용 |
|---|---|
| `gateway.alive` | 생존 신호(항상 1) |
| `gateway.uptime` | 프로세스 구동 시간(초) |
| `gateway.since_last_alert` | 마지막 알림 수신 이후 경과(초). 수신 이력이 없으면 기동 시점 기준 |
| `gateway.alerts` / `gateway.incidents` | 수신 알림 수 / 병합된 사건 수(누적) |
| `gateway.analyzed` / `gateway.skipped` | 분석 수행 / 조건 미충족 생략(누적) |

### 20-3. Zabbix 측 구성

수신 항목과 트리거는 `ansible/gateway_heartbeat.yml` 로 배포합니다. 트리거는 두 가지 상태를 분리하여 판정합니다.

| 트리거 | 조건 | 심각도 | 의미 |
|---|---|---|---|
| 게이트웨이 신호 끊김 | `nodata(gateway.alive, 3m)=1` | High | 프로세스 중단 또는 전송 경로 장애 |
| 알림 수신 경로 끊김 | `alive=1` 이고 `zbx_events > 3` 이고 `recent_alerts = 0` | Average | 발행 측은 이벤트를 생성했으나 수신 0건 |

`nodata` 창은 전송 주기의 3배로 설정합니다. 1회 누락 시 발화하도록 구성하면 재기동 시마다 알림이 발생합니다.

**"수신 없음"을 무알림 지속 시간으로 판정하지 않는 이유:** 최초 구성 시 `since_last_alert > 30분` 조건을 적용하였으나, 알림이 발생하지 않는 시간대가 정상인 환경에서는 오탐이 발생합니다(랩 환경에서 실제 발화 확인). 본 프로젝트가 해소 대상으로 삼은 알림 노이즈를 새로 생성하는 구성에 해당합니다.

대신 **발행 측 생성량과 수신량을 비교**합니다. 게이트웨이가 동일 창에 대해 Zabbix 가 생성한 문제 이벤트 수를 읽기 전용으로 조회하여(`countOutput`) 자체 수신 건수와 함께 전송하며, 트리거는 두 값을 비교합니다.

| 상태 | 발행 측 | 수신 | 판정 |
|---|---|---|---|
| 정상(무알림 구간) | 0 | 0 | 미발화 |
| 정상(알림 처리 중) | N | N 근사 | 미발화 |
| 경로 장애 | N > 3 | 0 | **발화** |

조회 실패 시 해당 항목을 전송하지 않습니다. 0 을 전송할 경우 "발행 측도 무알림"으로 해석되어 경로 장애가 정상으로 판정됩니다. 임계값 3 은 액션 조건에 의해 일부 이벤트가 대상에서 제외될 수 있는 점을 고려한 여유값입니다.

**⚠ 알림 경로 주의:** 본 호스트의 알림을 게이트웨이 경유로 발송하도록 구성하면, 게이트웨이 중단 시 해당 알림도 함께 소실됩니다. 감시 주체는 감시 대상 외부에 위치해야 합니다.

**⚠ 실환경 적용:** 본 플레이북은 아이템과 트리거를 **생성**하므로 실환경 읽기 전용 접근 원칙에 위배됩니다. 실환경은 동일한 정의를 담당자가 반영합니다.

### 20-5. 알림 경로 분리 (Independent Notification Path)

**본 트리거의 알림을 게이트웨이 경유로 발송하면 게이트웨이 중단 시 알림도 함께 소실됩니다.** 랩 환경 점검 결과 활성 트리거 액션이 게이트웨이 웹훅 1종뿐이었으며, 해당 상태에서는 게이트웨이 중단 사실이 어디에도 통보되지 않습니다.

이에 Zabbix 서버가 Slack 으로 직접 발송하는 독립 경로를 구성합니다. 웹훅 스크립트는 Zabbix 서버 내부에서 실행되므로 게이트웨이 동작 여부와 무관합니다.

| 구성 요소 | 내용 |
|---|---|
| 미디어 타입 | `Selfwatch Slack` (webhook) — `ansible/files/zabbix_media_selfwatch.js` |
| 액션 조건 | 호스트 = `kinx-gateway` 단일 조건. 미지정 시 전체 알림이 본 경로로 유입되어 채널이 무의미해짐 |
| 발송 채널 | **봇 사용 채널과 분리.** 게이트웨이 중단 시 봇 채널은 무음 상태가 되며, 그 무음 자체가 증상이므로 동일 채널에 경고를 배치하면 두 상태가 혼재함 |
| 크리덴셜 | 실행 시 환경 변수로 주입(`SELFWATCH_SLACK_BOT_TOKEN`·`SELFWATCH_SLACK_CHANNEL`). 미설정 시 플레이북 중단 |

**Slack 응답 검증:** Slack API 는 처리 실패 시에도 HTTP 200 을 반환하므로, 스크립트에서 응답 본문의 `ok` 필드를 확인하고 거짓일 경우 예외를 발생시킵니다. 미검증 시 발송 실패가 성공으로 기록됩니다.

### 20-6. 구성 시 확인된 무음 실패 사례 (2026-08-11)

본 구성 과정에서 **API 응답과 화면 설정은 정상이나 알림이 발송되지 않는** 상태가 3회 발생하였습니다. 관측 파이프라인 점검 시 참고 사항으로 기록합니다.

| 현상 | 원인 | 확인 방법 |
|---|---|---|
| 모듈이 `changed` 를 반환했으나 액션 미생성 | 호스트 조건의 `value` 는 호스트명이 아닌 **hostid** 를 요구함 | 생성 후 재조회 검증 단계 추가 |
| `action.get` 조회 시 액션 미표시 | **읽기 전용 토큰 권한 제약** — 액션이 참조하는 사용자에 대한 권한 부재 시 목록에서 제외됨. 실제로는 정상 생성됨 | DB 직접 조회(`actions` 테이블) |
| 액션·조건·사용자 미디어 정상이나 발송 미생성 | 미디어 타입에 **메시지 템플릿 부재**. `default_msg` 사용 시 알림 자체가 생성되지 않음 | `alerts` 테이블 오류 컬럼 — `No message defined for media type.` |

세 건 모두 오류 로그가 발생하지 않았으며, `alerts` 테이블 직접 조회로 확인되었습니다.

### 20-4. 랩 검증 결과 (2026-08-11)

1. 프로토콜 전송 확인 — 서버 응답 `processed: 7; failed: 0`
2. 게이트웨이 중단 후 3분 경과 시점에 `게이트웨이 신호 끊김` 트리거 발화 확인(High)
3. 게이트웨이 재기동 후 해당 문제 자동 해소 확인
4. **독립 경로 Slack 발송 확인** — 발생·해소 각각에 대해 `alerts` 테이블 상태 1(성공) 기록. 스크립트가 Slack 응답의 `ok` 를 검증하므로 성공 상태는 Slack 수신 완료를 의미함

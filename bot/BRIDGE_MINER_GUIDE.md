# 브리지 후보 마이닝 — 사용법과 해석

`bot/bridge_miner.py`. 이력에서 **같이 나타나는 축 쌍**을 찾아 추천한다. 읽기 전용이다.

## 왜 만들었나

게이트웨이의 인시던트 병합은 `(host, class)` 로 알림을 묶고, 서로 다른 class 라도 인과
후보면 `BRIDGE_GROUPS` 로 한 사건으로 본다. 그런데 그 초기값이 이렇다.

```python
frozenset({"replication", "cpu_io_pressure"})   # 데모 C 시나리오
frozenset({"disk_space", "service_down"})       # 데모 B 시나리오
```

**우리 데모 두 개가 그대로 코드에 박혀 있다.** 사람이 지정한 쌍이고, 근거가 "우리가 그
시나리오를 만들었기 때문"이다. 확장 설계가 아니다.

이 도구는 그 의존을 **데이터로 검증하고 확장**한다.

- 우리가 고른 쌍이 **실제 이력에서도 지지되는가**
- 우리가 **몰랐던 쌍**이 있는가

**자동 적용하지 않는다.** 출력은 "검토하라"는 목록이다. `판정은 코드, 설명은 LLM` 원칙의
확장 — **그룹 정의는 사람, 후보 발굴은 데이터**다. 상관은 인과가 아니므로 사람이 확정한다.

## 실행

```bash
cd ~/kinx-idc-monitoring-poc/bot
source .env                     # ZABBIX_URL·ZABBIX_TOKEN·WAZUH_INDEXER_* 필요
python bridge_miner.py --days 90
```

| 옵션 | 기본 | 뜻 |
|---|---|---|
| `--days` | 90 | 조회 기간 |
| `--window` | 600 | 같은 사건으로 볼 시간창(초). 게이트웨이 디바운스보다 넉넉하게 |
| `--min-pairs` | 5 | 이 미만 동시 발생은 우연으로 본다 |
| `--min-lift` | 2.0 | 독립 가정 대비 몇 배로 함께 나오는가 |
| `--source` | all | `zabbix` / `wazuh` 로 한쪽만 |
| `--json` | | 원시 결과 |

**실환경에도 그대로 돌릴 수 있다.** Zabbix 는 `ZabbixClient.call` 을 쓰는데 그 함수가
`.get` 이외의 메서드를 코드로 거부한다. Wazuh 는 인덱서 `_search` 뿐이다.

## 무엇을 계산하나

호스트별로 시간창을 겹치지 않게 자르고, 각 창에 어떤 class 가 등장했는지 본다.

```
lift = P(A와 B가 같은 창에) / (P(A) x P(B))
```

독립이면 1이다. 1보다 크면 우연보다 자주 함께 나온다.

조건부 확률도 함께 낸다 — **`P(B|A)` = A가 났을 때 B도 날 확률**.

## 해석 — lift만 보면 틀린다

합성 데이터로 검증한 결과가 그 이유를 보여준다.

```
cpu_io_pressure + replication   together=40   lift=6.90   P(B|A)=1.000   hosts=1
disk_space + service_down       together=6    lift=7.67   P(B|A)=0.167   hosts=1
```

**두 번째가 lift 는 더 높은데 실제로는 약하다.** `service_down` 이 희귀해서 분모가 작아
lift 가 부풀려졌다. `P(B|A)=0.167` 이 그걸 드러낸다 — 디스크가 차도 6번 중 1번만 서비스가
멈췄다는 뜻이다.

그래서 세 지표를 함께 본다.

| 지표 | 무엇을 말하나 | 주의 |
|---|---|---|
| `together` | 절대 동시 발생 횟수 | 작으면 우연 |
| `lift` | 우연 대비 배수 | 희귀 쌍에서 부풀려진다 |
| `P(B|A)` | A 뒤에 B가 올 확률 | **인과 강도에 가장 가깝다** |
| `hosts` | 몇 개 호스트에서 보였나 | 1이면 그 호스트 사정일 수 있다 |

**판정 기준(권고)**

- `together >= 5` **그리고** `lift >= 2` — 기본 필터
- `P(B|A) >= 0.5` — 브리지로 확정할 만한 강도
- `hosts >= 2` — 특정 호스트 사정이 아니라는 근거

기본 필터만 통과한 쌍은 "관찰됨"이고, 뒤 둘까지 통과하면 "브리지 후보"다.

## 출력 읽기

**축별 등장 창 수** — 어느 축이 이력을 지배하는지. 사내 Zabbix 라면 `network` 가 압도할
것으로 예상된다(진단상 이벤트의 78.6%가 인터페이스 에러). 그게 확인되면 진단과 정합한다.

**현행 BRIDGE_GROUPS 가 데이터에서 지지되는가** — 우리가 고른 두 쌍의 실측 수치.
`데이터에 함께 나온 적 없음` 이 나오면 **그 브리지는 근거가 없다**는 뜻이고, 그건 솔직하게
기록할 값이 있다(랩에서 우리가 만든 시나리오라 이력이 얇을 수 있다).

**추천 후보** — `신규` 표시가 붙은 쌍이 검토 대상이다.

## `other` 비중이 크면 분류기를 먼저 고친다

`other` 는 분류 실패 묶음이라 추천에서 제외한다. 그런데 **축별 등장에서 `other` 가 크면
그건 브리지 문제가 아니라 분류기 문제다.**

분류는 선언 우선이다 — Zabbix 트리거 태그 `class=<축>`, Wazuh `rule.groups`. 둘이 없을 때만
알림명 키워드로 떨어진다. `other` 가 크다는 것은 **선언이 없고 키워드도 안 맞는 알림이 많다**는
뜻이므로, 답은 키워드를 늘리는 것이 아니라 **소스에 태그를 붙이는 것**이다.

이게 확장 경로다. 팀이 트리거에 태그를 붙이면 게이트웨이 코드를 고치지 않아도 분류가
정확해지고, 그러면 이 도구의 출력도 정확해진다.

## 한계 — 정직하게

**상관은 인과가 아니다.** 함께 나는 것이 원인과 결과라는 보장이 없다. 제3의 원인이 둘을
동시에 일으킬 수 있다(예: 호스트 재부팅이 복제 지연과 서비스 중단을 함께 만든다).

**시간 순서를 쓰지 않는다.** 창 안의 등장만 세고 A→B 순서를 구분하지 않는다. 순서를 넣으면
방향성 있는 인과 후보가 되지만, 알림 발화 시각은 실제 원인 발생 시각과 지연이 있어(트리거의
지속 조건 등) 순서가 뒤집힐 수 있다. **지금은 넣지 않는 것이 정직하다.**

**창 경계 효과가 있다.** 겹치지 않는 창으로 자르므로, 경계에 걸친 쌍은 다른 창으로 나뉜다.
`--window` 를 늘려 민감도를 확인한다. 값이 크게 흔들리면 그 쌍은 약하다.

**분류 품질에 종속된다.** 위의 `other` 항목과 같다.

## 이 도구가 답하지 못하는 것

"어떤 알림이 어떤 조치로 이어지는가"는 알 수 없다. 그건 **조치 이력**이 있어야 하고, 우리는
아직 그걸 축적하지 않는다. Keep 에 조치 후보와 승인 결과가 쌓이면 그때 가능해진다 —
**후속 로드맵 항목**이다.

Holmes 조사 결과에서 인과를 추출하는 방식도 검토했으나 채택하지 않았다. LLM 자유 텍스트
파싱이라 신뢰도가 낮고 재현되지 않는다. 공동 발생은 산수라서 검증되고 재현된다. 값이 큰
쪽은 "사람이 확인한 인과를 라벨로 축적"인데 그건 PoC 범위 밖이다.

# 브리지 후보 마이닝 가이드 — 연관 알림 클래스 분석 및 수집 모듈 명세

본 문서는 `bot/bridge_miner.py` 유틸리티의 동작 원리, 실행 방법 및 이력 데이터 기반의 **연관 알림 브리지 후보(BRIDGE_GROUPS) 추출 및 해석 절차**를 명시한 가이드입니다. (본 모듈은 읽기 전용으로 동작합니다.)

---

## 1. 개발 배경 및 목적

게이트웨이 파이프라인의 알림 병합 로직은 `(호스트명, 알림 유형)` 단위로 1차 그룹화를 수행하며, 서로 다른 유형이라도 사전 정의된 `BRIDGE_GROUPS` 연관 규약에 부합할 경우 단일 인시던트로 병합합니다.

기존 코드는 시나리오 시뮬레이션을 위한 인과 쌍이 정적으로 하드코딩되어 있었습니다:

```python
frozenset({"replication", "cpu_io_pressure"})   # DB 복제 지연 및 자원 경합 시나리오
frozenset({"disk_space", "service_down"})       # 디스크 용량 초과 및 서비스 중단 시나리오
```

본 마이닝 유틸리티는 이러한 정적 정의 방식에서 벗어나 **실제 수집 이력 데이터 기반으로 연관 알림 후보를 검증하고 확장**하기 위해 구현되었습니다:

- 기존 지정된 브리지 쌍이 실제 발생 이력 데이터에서도 타당하게 지지되는지 검증
- 수동 관측으로 식별하지 못한 미지의 연관 알림 클래스 쌍 추출

> **[운영 원칙]**  
> 모듈 추출 결과는 자동 적용되지 않으며 관제 담당자의 검토 항목으로 제공됩니다. 이는 **"판단은 코드, 설명은 LLM"** 원칙의 연장선으로, 연관 후보 발굴은 데이터 연산으로 자동화하되 최종 브리지 규칙 확정은 사람이 담당합니다 (상관관계가 항상 인과관계를 의미하지는 않기 때문입니다).

## 2. 실행 방법 및 CLI 옵션

```bash
cd ~/kinx-idc-monitoring-poc/bot
source .env                     # ZABBIX_URL·ZABBIX_TOKEN·WAZUH_INDEXER_* 환경변수 필요
python bridge_miner.py --days 90
```

### 주요 CLI 옵션 명세

| 옵션 파라미터 | 기본값 | 설정 의미 및 목적 |
|---|---|---|
| `--days` | `90` | 분석 대상 과거 데이터 조회 기간 (일) |
| `--window` | `600` | 동일 인시던트로 간주할 시간 창 (초 단위 / 디바운스 창보다 넓게 설정) |
| `--min-pairs` | `5` | 동시 발생 임계치 (해당 횟수 미만은 우연한 수집으로 간주하여 제외) |
| `--min-lift` | `2.0` | 독립 가상 대비 동시 발생 비율 (Lift) 하한 임계치 |
| `--source` | `all` | 수집 대상 지정 (`all` / `zabbix` / `wazuh`) |
| `--json` | - | 분석 결과를 원시 JSON 형식으로 출력 |

**실운영 환경 안전성 (Read-only Guard):**  
Zabbix API 연동 시 `.get` 메서드 외의 수정/삭제 호출을 소스 코드 수준에서 거부하며, Wazuh 연동 또한 Indexer `_search` 전용 조회만 수행하므로 운영 환경에 영향을 주지 않고 실행할 수 있습니다.

## 3. 연산 수식 및 지표 정의

동일 호스트를 대상으로 겹치지 않는 시간 창(Time Window)을 생성한 후, 각 시간 창 내에 동시 수집된 알림 클래스($A, B$)의 확률을 계산합니다.

$$\text{Lift} = \frac{P(A \cap B)}{P(A) \times P(B)}$$

- **$\text{Lift} = 1$:** 두 알림 클래스의 발생이 완전히 독립적임
- **$\text{Lift} > 1$:** 우연한 발생 빈도보다 두 알림이 동시 수집될 확률이 높음

또한 $A$ 알림 발생 시 $B$ 알림이 연쇄 발생할 조건부 확률 $P(B|A)$를 함께 산출합니다:

$$P(B|A) = \frac{P(A \cap B)}{P(A)}$$

## 4. 데이터 해석 지침 — Lift 지표의 한계 및 종합 평가

합성 시뮬레이션 데이터 분석 결과, Lift 지표 단독 참조 시 희귀 알림 발생에 따른 착시 현상이 나타날 수 있습니다:

```text
cpu_io_pressure + replication   together=40   lift=6.90   P(B|A)=1.000   hosts=1
disk_space + service_down       together=6    lift=7.67   P(B|A)=0.167   hosts=1
```

두 번째 케이스(`disk_space + service_down`)의 Lift 수치가 더 높게 산출되나, 이는 `service_down` 발생 빈도가 매우 낮아 분모 $P(B)$가 작아짐에 따라 Lift 값이 부풀려진 결과입니다. 실제로 조건부 확률 $P(B|A) = 0.167$을 확인하면 디스크 포화 시 서비스가 중단된 비율은 16.7%에 불과하여 연관 강도가 약함을 알 수 있습니다.

따라서 아래 4가지 지표를 종합적으로 평가하여 브리지 후보를 확정합니다.

| 산출 지표 | 평가 의미 및 해석 지침 | 유의 사항 |
|---|---|---|
| `together` | 시간 창 내 절대 동시 발생 횟수 | 표본 수가 적을 경우 우연에 의한 왜곡 발생 가능 |
| `lift` | 독립 가상 대비 동시 발생 배수 | 희귀 발생 알림의 경우 수치가 상향 과대평가됨 |
| `P(B|A)` | $A$ 발생 후 $B$가 연달아 수집될 조건부 확률 | **실질적인 인과 연관 강도에 가장 부합하는 지표** |
| `hosts` | 해당 동시 발생이 관측된 독립 호스트 수 | 1개 호스트 국한 시 특정 노드 특이 현상일 수 있음 |

### 브리지 규칙 확정 권고 기준

1. `together >= 5` **AND** `lift >= 2.0` (기본 동시 발생 필터)
2. `P(B|A) >= 0.5` (연관 인과 강도 충족)
3. `hosts >= 2` (특정 호스트 편중 현상 배제)

*1번 조건만 만족하는 조합은 "단순 관측 쌍"으로 분류하며, 2·3번 조건까지 동시 충족하는 항목을 최종 "브리지 후보"로 결정합니다.*

## 5. 출력 결과 분석 및 분류기(Classify) 고도화 연계

- **축별 등장 빈도:** 이력 데이터 내 상위 점유 알림 유형을 식별합니다. (예: 사내 인프라의 경우 네트워크 인터페이스 에러 알림이 78.6%를 점유하여 `network` 축이 상위 집계됨)
- **기존 `BRIDGE_GROUPS` 검증:** 현재 설정된 브리지 규칙이 실제 이력 데이터에서 지지되는지 평가합니다. (`데이터 수집 이력 없음` 출력 시 해당 브리지 규칙은 데이터 기반 근거가 미비한 것으로 간주함)

### `other` 미분류 비중 증가 시 조치 사항

분석 결과에서 `other` 범주의 비중이 높게 나타날 경우, 이는 브리지 규칙의 문제가 아닌 **알림 분류기(`classify`)의 매칭 미비 현상**에 해당합니다.

알림 분류 우선순위는 Zabbix 트리거 태그 `class=<축>` 또는 Wazuh `rule.groups` 설정이 최우선 적용되며, 미설정 시 알림명 키워드 기반 폴백 추정이 동작합니다. 따라서 소스 관측 시스템(Zabbix/Wazuh) 상에서 트리거 태그를 명시적으로 부여하면 게이트웨이 코드를 수정하지 않고도 분류 정밀도를 지속 향상시킬 수 있습니다.

## 6. 기술적 한계 및 제약 사항 (Limitations)

- **상관관계와 인과관계의 구별:** 두 알림이 동일 시간 창 내 발생했더라도 공통 제3의 원인(예: 호스트 재부팅에 따른 복제 지연 및 서비스 중단 동시 발생)에 의한 결과일 수 있으며, 직접적 인과관계를 단정할 수 없습니다.
- **시간 순서(Sequencing) 미반영:** 시간 창 내 발생 유무만 집계하며 $A \to B$ 발생 순서 구별을 적용하지 않습니다. (트리거 발화 지연 및 지속 조건 설정에 의해 수신 시각 역전 현상이 발생할 수 있어 순서 제어를 배제함)
- **시간 창 경계 효과 (Window Boundary Effect):** 고정 시간 창 분할 방식 특성상 경계 지점에 걸쳐 수신된 알림 쌍이 분리될 수 있습니다. (필요시 `--window` 파라미터를 상향 조정한 후 지표 변동성을 재검증함)
- **분류기 정확도 종속성:** 입력 알림의 분류 결과 정밀도에 직접적인 영향을 받습니다.

## 7. 추후 고도화 및 미반영 영역

본 유틸리티는 알림 간 동시 발생 패턴만을 추적하므로, "특정 알림이 어떤 자동 조치 행위(Remediation)로 이어지는가"에 대한 조치 이력 연계 분석은 수행하지 않습니다.

해당 기능은 Keep 승인 UI를 통해 실제 자동 조치 실행 이력이 유의미한 모수로 축적된 이후 추가 고도화 과제로 추진합니다. (자율 언어 모델에 의한 자유 텍스트 인과 추론 방식은 재현성 및 결과 신뢰도가 낮아 적용 대상에서 제외하고, 데이터 기반 연산 방식을 유지합니다.)

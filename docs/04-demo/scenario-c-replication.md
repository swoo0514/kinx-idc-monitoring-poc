# 데모 C 시나리오 — DB 복제 지연 원인 분석 ("DB 장애 vs 자원 경합")

본 문서는 데모 C(AI 기반 초동 분석) 시나리오의 기술적 설계 배경, 사건 구성, 기존 관제 방식과의 차별성 및 예상 질의에 대한 답변 대책을 정립한 명세서입니다.

*상세 실행 명령 및 절차:* [`runbook.md`](runbook.md) §2 참조  
*(문서 내 명시된 호스트 및 서비스 명칭은 실험 인프라 환경의 가상 식별자입니다.)*

---

## 0. 도입 정당성 (Core Justification)

> **[기술적 차별성]**  
> Wazuh 룰 엔진은 자사 수집 데이터 범위 내에서만 상관 분석을 수행하므로 Zabbix 메트릭 및 Loki 로그 지표를 분석 대상에 포함할 수 없습니다. 그러나 실제 인프라 장애는 복수의 관측 시스템에 파편화되어 수집됩니다. 본 게이트웨이 봇 파이프라인은 파편화된 원시 신호를 단일 인시던트로 병합하고, 단일 관측 도구로는 도출이 불가능한 **인과관계 추론, 근본 원인 재프레이밍(Reframing) 및 검증 명령 세트**를 제공합니다. 이는 단일 룰 엔진 구성으로는 달성할 수 없는 구조적 우위 요소입니다.

---

## 1. 장애 사건 정의 (Incident Definition)

* **인프라 전제 조건:** MariaDB Master-Slave 복제 토폴로지가 상시 가동 중인 환경입니다. (기존 관제 진단 결과, 서비스 DB 복제를 1/0 Status 플래그로만 관측하고 지연 시간(Lag Seconds)을 미감시하는 사각지대가 식별되어 본 시나리오의 당위성이 확보되었습니다.)
* **장애 시나리오:** Slave 노드에서 대용량 데이터 백업(또는 대량 쿼리 연산)이 기동되면서 디스크 I/O 자원을 점유하고, 이로 인해 Slave가 Master의 변경 이력을 적시에 추적하지 못해 복제 지연(Replication Lag)이 누적되는 현상입니다. 겉으로는 "DB 복제 엔진 장애"로 보이나, 실제 근본 원인은 **동일 서버 내 자원 경합(Resource Contention)**에 해당합니다.

---

## 2. 모니터링 성숙도 4계층 체계 및 인시던트 병합

| 성숙도 계층 | 수행 역할 및 분석 범위 | 담당 시스템 |
|---|---|---|
| **1계층 (단일 알림)** | 단일 메트릭 지표의 임계치 초과 탐지 | Zabbix (현행) |
| **2계층 (시스템 내 상관)** | 단일 관측 시스템 내부 룰 기반 패턴 결합 | Wazuh 룰 엔진 (현행) |
| **3계층 (시스템 간 상관 = 인시던트 병합)** | **복수 시스템에 파편화된 알림을 단일 사건으로 병합 + 인과관계 추론 및 재프레이밍** | **통합 분석 봇 (데모 C 핵심)** |
| **4계층 (관측 영역 확장)** | 미관측 영역에 대한 신규 텔레메트리 계측 | Loki (앱 로그) / Suricata (네트워크 패킷) |

*핵심 구현 전략:* 2계층(Wazuh 룰)의 역할을 존중하면서 그 상위 계층으로 3계층 통합 레이어를 탑재합니다. Wazuh는 보안 축 내부 룰 결합에 유효하나, 수집 데이터 범위를 벗어난 Zabbix 복제 지연 및 Loki 백업 로그와의 연관 관계는 구조적으로 파악할 수 없습니다.

## 3. 장애 발생 타임라인 (Timeline)

```text
T+0:00  Slave 노드에서 대용량 백업 / 쿼리 작업 기동
        └ Loki (Alloy): 백업 프로세스 실행 로그 (tar / mysqldump / rsync) 기록 시작
T+0:02  디스크 I/O 포화 상태 도달
        └ Zabbix (Agent2): iowait · Disk Latency · Load Average 상승 ➔ 알림 ① 발화
T+0:03  Slave 복제 처리 속도 지연 발생
        └ Zabbix: replication lag (seconds_behind_master) 급증 ➔ 알림 ② 발화
T+0:05  애플리케이션 데이터 동기화 지연 발생 (DB 응답 지연 현상으로 오인)
T+0:06  Wazuh (Wazuh Agent): 동일 시점 보안 침해 및 비인가 설정 변경 이벤트 없음 ➔ 배제 신호 수집
T+0:07  Zabbix High CPU 알림 추가 발생 ➔ 알림 ③ 발화
```

*관제 현황:* 관제 담당자에게는 3개 관측 화면에 파편화된 2~3개의 독립 알림(복제 지연, iowait, High CPU)으로 수집되며, 기존 시스템은 단일 사건으로 통합해 제공하지 못합니다.

## 4. 관측 도구별 분석 한계 및 단일 소스 분석의 제약

- **Zabbix 단독 관측의 한계:** "복제 지연" 및 "High iowait" 알림이 별개로 수집되며, 복제 모듈 자체의 장애인지 자원 경합 때문인지 메트릭 지표만으로 구별할 수 없습니다.
- **Wazuh 단독 관측의 한계:** 해당 인시던트 내 보안 침해 이벤트가 존재하지 않으므로 단독 관측이 불가합니다. (단, "보안 침해 및 설정 변경 없음" 상태를 **명시적으로 배제하는 정황 근거**를 제공합니다.)
- **Loki 단독 관측의 한계:** 백업 로그가 수집되나, 단독 로그 데이터만으로는 현재 발생한 복제 지연과의 직접적인 인과관계를 입증할 수 없습니다.

➔ **복제 지연(Zabbix) + iowait 동시 상승(Zabbix) + 동일 시점 백업 로그(Loki) + 보안 침해 부재(Wazuh)** 지표가 타임라인 상에서 통합 시각화될 때 비로소 "복제 엔진 장애가 아닌 디스크 I/O 자원 경합"이라는 정밀 분석이 완성됩니다.

---

## 5. 기존 관제 프로세스의 문제점 (Before)

단일 관측 화면 내 단순 판단 구조는 잘못된 장애 조치를 유발합니다:

1. **장애 오인:** 관제 담당자가 `Replication Lag` 알림을 확인하고 기존 경험에 기반하여 "DB 복제 엔진 결함"으로 단정합니다.
2. **오조치 실행:** 복제 스레드 리셋(`STOP SLAVE; START SLAVE;`) 또는 Slave 재동기화 작업을 실행합니다. ➔ 복제 모듈은 정상 상태이므로 재동기화 작업은 추가 I/O 부하를 유발하여 시스템 상태를 악화시키며, 근본 원인(백업 프로세스)이 제거되지 않아 장애가 재발합니다.
3. **수동 연관 분석 공수 소요:** 숙련된 관제 담당자라 하더라도 Zabbix 메트릭 확인, Loki 로그 검색, Wazuh 보안 대조 등 3개 대시보드를 수동 교차 검증하는 데 수 분~수십 분의 소요 시간이 발생합니다.

## 6. AI 초동 분석 및 인시던트 병합 프로세스 (After)

1. **인시던트 디바운스 병합:** 수신된 알림은 게이트웨이 버퍼에 수집되며, 브리지 룰(`replication + cpu_io_pressure`)에 의해 단일 사건으로 병합됩니다. 디바운스 창(기본 90초) 마감 시점에 교차 텔레메트리 데이터를 통합 수집합니다:
    - **Zabbix API:** 복제 지연 추이, iowait/Load 지표, 트리거 조건식
    - **Loki API:** 해당 호스트의 최근 백업/대량 쿼리 로그
    - **Wazuh Indexer:** 해당 에이전트의 보안 경보 수집 (보안 침해 여부 배제)
    - **코드 선판정:** 최근 90일간 해당 트리거 발생 이력 조회 (신규/만성 구분)
   > *판단은 코드 로직이 결정하고, LLM은 인과관계 설명 생성을 전담합니다.*
2. **Slack 분석 카드 실시간 회신 (사건 확정 후 30초 이내):**

   > 🟠 **[SEV2] `<호스트명>` DB 복제 지연 — 복제 엔진 장애 아님 (자원 경합)**  
   > 수신된 3건의 알림(복제 지연·iowait 상승·High CPU)은 단일 자원 경합 사건입니다.  
   > **추정 인과:** 동일 서버 내 백업/대량 쿼리 작업(Loki 로그 확인)에 따른 디스크 I/O 포화 ➔ Slave 복제 동기화 지연 발생 (복제 기능 자체는 정상 상태임). 보안 침해 흔적 없음(Wazuh).  
   > **선판정:** 신규 (최근 90일 이력 0회).  
   > ⚠️ **주의 및 권고:** **Slave 재동기화 및 복제 스레드 리셋 금지** (장애 악화 위험). 백업 스케줄/우선순위 조정 또는 I/O 스로틀링 적용 필요.  
   > **검증 명령어:** `iostat -x 1`, `SHOW PROCESSLIST`, `SHOW SLAVE STATUS\G`

## 8. 관측 계층의 한계 및 확장 방향

본 시나리오는 운영 자원 경합 이슈로 네트워크 계층 트래픽이 수반되지 않습니다. 그러나 침투 후 아웃바운드 C2 통신 또는 내부 스캔 작업과 같은 보안 인시던트는 호스트 로그에 기록되지 않아 3개 관측 축만으로는 탐지가 불가능합니다. 이러한 사각지대를 보완하기 위해 네트워크 패킷 레벨을 계측하는 **Suricata(4계층 관측 확장)** 파이프라인을 별도 트랙으로 구성합니다.

---

## 9. 분석 타당성 및 실측 근거

- **Wazuh 독립 분석의 한계:** Wazuh 아키텍처상 Zabbix/Loki 텔레메트리가 룰 엔진에 수집되지 않음을 확인했습니다.
- **감시 깊이 정합성:** 실환경 진단 결과 서비스 DB 복제를 1/0 Status 플래그로만 감시하던 기존 방식의 한계를 보완했습니다.
- **처리 지연 시간 예산 충족:** 파이프라인 End-to-End 실측 결과 총 **15.77초** 소요를 확인했습니다 (수집 0.16초 + LLM 15.03초 + Slack 전송 0.58초).

## 10. 예상 질의 및 대응 논리 (Q&A)

- **Q1. Wazuh 룰을 확장하여 처리할 수 없는가?**  
  ➔ Wazuh 룰 엔진은 자사 수집 데이터만 참조하므로, Zabbix 메트릭 및 Loki 로그와의 교차 분석을 위해서는 상위 통합 게이트웨이 레이어가 필수적입니다.
- **Q2. LLM의 분석 결과에 오류가 발생하는 경우는 어떻게 대응하는가?**  
  ➔ 본 시스템은 자율 제어가 아닌 관제 담당자의 판단을 보조하는 HITL(Human-in-the-Loop) 구조입니다. 추천 검증 명령어를 함께 제공하여 30초 이내에 수동 검증이 가능하도록 지원하며, 만성/신규 선판정 결과는 코드 기반으로 산출되어 환각이 발생하지 않습니다.
- **Q3. 보안 및 데이터 반출 정책 제약은 어떻게 처리하는가?**  
  ➔ 데이터 마스킹 후 전송 계약 준수, API 학습 제외(No-training) 조항을 확인하였으며, 필요 시 온프레미스 Ollama 폴백 경로로 즉시 전환할 수 있습니다.

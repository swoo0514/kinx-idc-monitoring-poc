# 데모 C 시나리오 — "복제 지연: DB가 고장인가, 자원 경합인가"

데모 C(AI 초동 분석)의 설계 문서입니다. 무엇을 왜 이 사건으로 골랐는지, 어떤 반문이 들어올 수
있는지를 적었습니다. **실행 명령은 [`runbook.md`](runbook.md) §2.**

등장하는 호스트·서비스 이름은 전부 **랩 가상명**입니다.

---

## 0. 한 줄 정당화 — 왜 이 봇이 필요한가

> **Wazuh는 자기가 수집한 데이터 안에서만 상관한다. Zabbix 메트릭과 Loki 로그는 Wazuh 룰
> 엔진에 애초에 들어가지 않는다. 그런데 진짜 사건은 세 도구에 조각으로 흩어져 온다. 봇은 그
> 조각들을 하나의 인시던트로 병합하고, 개별 알림이라면 못 냈을 인과·재프레이밍·확인명령을
> 제시한다. 이것은 어떤 단일 도구도 구조적으로 못 하는 일이다 — 룰을 아무리 잘 짜도.**

---

## 1. 확정 사건

랩 자산: MariaDB master-slave 복제가 이미 가동 중. 진단 정합: 실측에 "서비스 DB 복제를 1/0
플래그로만 감시하고 지연 초는 미감시"가 있어 "왜 이 감시·이 봇이 필요한가"가 자명합니다.

**사건**: slave 서버에서 야간 백업(또는 대량 쿼리)이 시작되면서 디스크 I/O를 잠식하고, 그
결과 복제가 master를 못 따라가 지연이 쌓입니다. 겉보기엔 "복제 고장"이지만 실제 원인은 같은
서버의 자원 경합입니다.

## 2. 지적 척추 — 모니터링 성숙도 4계층 + 인시던트 병합

| 계층 | 하는 일 | 담당 |
|---|---|---|
| 1. 알림 | 단일 지표 임계 초과 | Zabbix (현행) |
| 2. 시스템 내 상관 | 한 시스템 안에서 룰로 패턴 결합 | Wazuh 룰 (현행) |
| **3. 시스템 간 상관 = 인시던트 병합** | 여러 시스템의 흩어진 알림을 1개 사건으로 병합 + 인과·재프레이밍 | **봇 (데모 C)** ← 도약 |
| 4. 관측 확장 | 없던 계층을 새로 계측 | Loki(앱로그), Suricata(네트워크, 별도 트랙) |

핵심: 2계층(Wazuh 룰)을 부정하지 않고 **그 위에** 3계층을 얹습니다. Wazuh는 보안 축 안의 룰
결합엔 강하지만, 그 신호가 Zabbix 복제 지연·Loki 백업 로그와 한 사건인지는 **구조적으로**
모릅니다 — 그 데이터가 Wazuh 룰 엔진 밖이기 때문입니다.

## 3. 정밀 타임라인

```
T+0:00  slave에서 야간 백업/대량 쿼리 시작
        └ Loki(Alloy): 백업 프로세스 로그(tar/mysqldump/rsync 계열) 기록 시작
T+0:02  디스크 I/O 잠식
        └ Zabbix(agent2): iowait·disk latency·load average 상승 → 알림 ①
T+0:03  복제가 master를 못 따라감
        └ Zabbix: replication lag(seconds_behind_master) 증가 → 알림 ②
T+0:05  애플리케이션이 최신 데이터를 늦게 봄 = "DB 죽은 것처럼" 보임
T+0:06  Wazuh(wazuh-agent): 이 시간창 침해·비인가 변경 이벤트 없음 (= 배제 신호)
T+0:07  Zabbix "High CPU"까지 겹치면 알림 ③
```

주목: 운영자에게는 **서로 다른 알림 2~3개**가 세 화면에 흩어져 뜹니다(복제 지연, iowait, CPU).
셋이 한 사건임을 아무도 말해주지 않습니다.

## 4. 각 도구의 최선과 한계 — 왜 각각으론 못 닫는가

- **Zabbix만**: "복제 지연"과 "iowait 높음"이 **따로** 뜹니다. 둘이 같은 원인인지, 복제 기능
  자체 문제인지 메트릭만으론 모릅니다.
- **Wazuh만**: 이 사건엔 보안 이벤트가 없습니다 → 단독으론 아무 말도 못 합니다(정상). 단
  "침해·설정 변경 아님"을 **배제**해주는 조연 가치는 있습니다(보안팀 소집 여부 판단).
- **Loki만**: 백업 로그가 있습니다. 그러나 그것이 지금 복제 지연의 원인인지, 무관한 정기
  작업인지 로그 단독으론 인과를 못 맺습니다. 게다가 실환경에서는 **로그 감시 아이템을 가진
  호스트 비율이 사실상 0**이라 이 축 자체가 안 보였습니다.

→ **복제 지연(Zabbix) + iowait 동반 상승(Zabbix) + 같은 시각 백업 로그(Loki) + 침해 없음
(Wazuh)** 이 시간축에서 겹칠 때만 "복제 고장이 아니라 자원 경합"이 닫힙니다. 이 병합이 3계층.

## 5. Before — 기존 프로세스가 어디서 왜 어긋나는가

정확한 Before는 **"각 시스템이 자기 조각은 보여주지만, 병합은 사람이 세 창을 오가며 하고,
가장 자연스러운 단일 창 해석('복제가 깨졌다')이 오진으로 이끈다"** 입니다.
"모니터링이 안 보인다"는 사실이 아닙니다.

1. DBA/운영자가 "replication lag" 알림을 봅니다.
2. 패턴 매칭: "복제가 깨졌다 → slave 재동기화 / 복제 스레드 리셋." 가장 흔한 1차 대응입니다.
   → **복제 기능은 멀쩡한데 엉뚱한 데 손댑니다.** 재동기화는 오히려 I/O를 더 유발해 악화될 수
   있고, 진짜 원인(백업)은 그대로라 곧 재발합니다.
3. 성실한 운영자라면 Zabbix에서 iowait를 확인하고, Grafana/Loki를 열어 그 시각 로그를 뒤지고,
   Wazuh로 침해 여부까지 대조합니다 = "장애 시 서버에 접속해 로그 확인"의 3창 버전. 수 분~
   수십 분이 걸립니다. 그리고 Warning이 이벤트의 대부분을 차지하는 노이즈 속이라 알림 자체가
   묻히기도 합니다.

이중 비용: (가) 시간(3창 수동 병합) + (나) 오진(복제 리셋이라는 틀린 조치). **(나)가 더
치명적입니다.**

## 6. After — 인시던트 병합

1. 알림들이 게이트웨이로 도착 → 봇이 `(host, incident_class)` 버퍼에 모읍니다. 복제 지연·
   iowait·CPU는 브리지룰(`replication + cpu_io_pressure`)로 **1개 인시던트**로 묶입니다. 짧은
   관측창(디바운스, 기본 90초·마지막 알림 후 무알림이면 마감)으로 흩어져 도착하는 알림을
   기다렸다가 **창이 닫히면 통합 트리아지 1회**. 이때 네 축을 자동 수집합니다.
   - Zabbix API: replication lag 추이 + iowait/load 추이 + 트리거 조건식
   - Loki: `{host="<호스트>"}` 최근 로그(백업/대량 쿼리 흔적)
   - Wazuh Indexer: `agent.name=<호스트>` 최근 경보(→ 침해 없음 확인)
   - 코드 선판정: 이 트리거 90일 이력 → 신규/만성

   > **병합은 코드가 결정, LLM은 설명만.** 어느 알림이 한 사건인지는 `(host, class)`+브리지룰
   > 로 코드가 판정합니다(환각 불가). LLM은 이미 묶인 사건에 인과만 붙입니다.

2. **인시던트 확정(창 마감) 후 30초 내** Slack 회신(요지):

   > 🟠 [SEV2] `<호스트>` 복제 지연 — **복제 고장 아님, 자원 경합**
   > 이 시간창의 알림 3건(복제 지연·iowait 상승·CPU)은 **개별 장애가 아니라 하나의 사건**.
   > 추정 인과: 같은 서버의 백업/대량 쿼리(Loki 로그 확인)가 디스크 I/O를 잠식 → 복제가
   > master를 못 따라감. **복제 기능 자체는 정상.** 침해 흔적 없음(Wazuh).
   > 판정: 신규(90일 0회).
   > ⚠️ 권장: **slave 재동기화·복제 리셋 금지**(원인 아님, 악화 위험). 백업 스케줄/우선순위
   > 조정 또는 I/O 스로틀. 확인: `iostat -x 1`, `SHOW PROCESSLIST`, `SHOW SLAVE STATUS`,
   > 백업 잡 시각 대조.

3. 핵심 개선: 봇이 **흩어진 3건을 1개 인시던트로 병합**하고, "복제 고장" 가설을 강등·"자원
   경합" 가설을 승격합니다. 자율 조치가 아니라 **1차 판단 + 안전 권고**이며, 실제 조치는
   사람 승인(데모 B)을 거칩니다.

## 7. Before/After 비교

| 차원 | Before (현행) | After (AI 트리아지) |
|---|---|---|
| 알림 형태 | 세 화면에 2~3건 흩어짐 | 1개 인시던트 카드로 병합 |
| 병합 주체 | 사람 (세 창 수동 대조) | 봇 (네 소스 자동) |
| 1차 가설 | "복제 고장" (오진) | "자원 경합" (병합의 결론) |
| 오조치 위험 | 높음 (복제 리셋 → 악화·재발) | 낮음 ("리셋 금지" 선권고) |
| 초동 소요 | 수 분~수십 분 / 또는 즉시 오조치 | 인시던트 확정 후 ~30초 (랩 트리아지 실측 15.77초 기반) |
| KPI 기준점 | (없음) | 알림이 아니라 **사건** — "인시던트 확정(창 마감) 후 30초" |
| 만성/신규 | 사람 기억 | 코드 선판정 (환각 불가) |
| 침해 여부 | 별도 확인 필요 | 자동 배제 (Wazuh 조회 포함) |

## 8. 이 3축으로도 안 보이는 것

이 사건은 순수 운영 문제라 네트워크 계층이 안 엮입니다. 그러나 다른 사건(침입 후 아웃바운드
C2·내부 스캔)은 **어느 호스트 로그에도 안 남아** 3축으로 못 잡습니다. 그 계층을 새로 계측하는
것이 Suricata(4계층 관측 확장)이며, "AI가 병합한다"(3계층)와 성격이 다릅니다. 별도 트랙으로
분리했고 판정 근거는 `docs/02-design/`에 있습니다.

## 9. 근거

| 요소 | 근거 |
|---|---|
| Wazuh는 자기 데이터 안에서만 상관 | Wazuh 아키텍처(룰 엔진에 Zabbix/Loki 미포함) |
| 복제를 1/0 플래그로만 감시(지연 미감시) | 실환경 진단 — 서비스 DB 복제 감시 깊이 |
| 3시스템 병합을 사람이 손으로 | 실환경 진단 — 관측 사일로 |
| 알림이 노이즈에 묻힘 | 실환경 진단 — Warning이 이벤트의 대부분 |
| 로그 축이 안 보임 → Loki 명분 | 실환경 진단 — 로그 감시 아이템 보유 호스트 비율 사실상 0 |
| 30초 예산·수집 오버헤드 미미 | 랩 실측 15.77초 (수집 0.16 + LLM 15.03 + Slack 0.58) |

## 10. 반문 대비

- **"Wazuh 룰로 되지 않나?"** → Wazuh는 자기 데이터 안에서만 상관합니다. Zabbix 메트릭·Loki
  로그는 Wazuh 룰 엔진에 안 들어갑니다. 교차 상관은 구조적으로 상위 레이어가 필요합니다.
- **"AI가 틀리면?"** → 판단 대체가 아니라 초동 분석 가속입니다(HITL). 확인 명령을 함께 줘
  운영자가 30초 내 검증할 수 있고, Wazuh/Zabbix 원본 알림은 그대로 남습니다. 만성/신규는
  코드 판정이라 환각이 불가능합니다.
- **"비용·보안은?"** → 로그 마스킹 후 전송(전송 데이터 명세표), no-training 계약 확인,
  Ollama 온프렘 옵션이 로드맵에 있습니다. 관제망 egress 가부는 미확인 항목이며 어댑터가
  흡수합니다.

## 11. 축 채택·기각

- **축 1 (교차 상관 = 인시던트 병합)**: 메인 채택.
- **축 2 (자연어 트리아지 = 룰번호 해석·확인명령)**: 서브 채택 — 봇 회신에 이미 포함.
- **축 3 (룰 없는 이상 탐지)**: **기각** → 로드맵 언급만. AI 환각 위험이 "코드 선판정"
  원칙과 충돌하므로 데모에 넣지 않았습니다.

## 12. 시연 컷 순서

```
[Before ~40초] "복제 지연" 알림 → DBA "복제 깨졌다 → 재동기화" 가정 → (오진 지점 짚기) →
               성실 버전은 Zabbix iowait·Loki 백업로그·Wazuh를 세 창 수동 대조. 흩어진 3개 알림.
[After]        동일 발화 → 짧은 관측창에서 3개 알림이 1개 인시던트로 병합(창 마감) →
               그 시점부터 스톱워치 → 30초 뒤 Slack에 "3건은 1개 사건·복제 고장 아님·자원
               경합·리셋 금지" 인시던트 카드 + 확인 명령. 같은 사건, 두 번.
               (디바운스를 짧게 설정해 대기 체감 최소화 — 기준점은 '사건 확정 후 30초')
[여운]         "이 3축에도 안 잡히는 것(네트워크 계층)" → 별도 트랙 예고.
```

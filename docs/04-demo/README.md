# 데모 시나리오 가이드 — 시나리오별 검증 목적 및 연계 구조

전체 시연은 **"통합 가시성 확보(통합 관제) ➔ AI 기반 통합 인시던트 분석(초동 분석) ➔ 승인 기반 자가 치유(HITL)"**의 단계적 흐름으로 구성됩니다.

상세 실행 명령어 및 절차는 [`runbook.md`](runbook.md) 가이드를 참조하며, 본 문서는 시연 시나리오별 검증 목적 및 기술적 가치를 명시합니다.

---

## 1. 데모 A — 통합 관제 (Integrated Observability)

**검증 목적:**  
단일 장애 주입 시 **메트릭·로그·보안 3개 관측 축의 데이터가 동일 타임라인 및 동일 호스트 조건으로 통합 시각화**되는 과정을 검증합니다. 또한 보안 이벤트 클릭 시 해당 호스트의 관련 로그로 즉시 이동하는 대시보드 드릴다운(Drill-down) 기능을 시연합니다.

- **장애 주입 스크립트:** `chaos/ssh_bruteforce.sh` (Wazuh 레벨 10 경보 생성)
- **확인 화면:** Grafana `kinx-overview` 통합 관제 대시보드
- **기술적 의의:** 개별 운영되던 관측 시스템을 단일 뷰로 통합하여 탭 이동 및 수동 연관 분석 공수를 제거합니다. 본 드릴다운이 정상 동작하기 위해서는 3개 시스템 간 호스트 식별자를 일치시키는 **FQDN 정규화**가 선행되어야 합니다.

---

## 2. 데모 B — 자가 치유 (HITL 승인 기반 자동 조치)

**검증 목적:**  
서비스 중단 발생 시 봇이 해당 알림을 자동 조치 후보로 분류하여 승인 큐에 등록하고, **관제 담당자의 단일 승인(Run 버튼 클릭)을 통해 Ansible 기반의 자동 조치 및 조치 후 재검증**까지 실행되는 전체 제어 흐름을 검증합니다.

- **장애 주입 스크립트:** `chaos/service_down.sh`
- **확인 화면:** Keep 승인 관리 UI ➔ 워크플로 실행 결과 확인 (`before: inactive -> after: active`)
- **승인 제어(HITL) 도입 이유 및 안전 메커니즘:**  
  MSP 위탁 계약 조건상 임의 자동 조치가 불가능한 자산이 존재하므로 명시적 승인 계층이 요구됩니다. `scope=notify_only` 태그 적용 시 조치 라우팅 경로가 차단되며, 워크플로 시작부에서 `playbook` 매칭 조건을 검증하는 안전 게이트가 동작합니다. 실질적인 안전장치는 **가역성·멱등성이 보장된 플레이북 실행 및 조치 후 자동 재검증** 로직입니다.

---

## 3. 데모 C — AI 초동 분석 (AI-assisted Triage & Incident Merging)

**검증 목적:**  
상이한 트리거로 분산 수신된 복수의 알림(N건)을 단일 인시던트로 **자동 병합**하고, "단순 DB 복제 장애가 아닌 백업 작업 부하에 의한 I/O 경합"으로 근본 원인을 **재프레이밍(Reframing) 및 분석**하는 과정을 검증합니다.

- **장애 주입 스크립트:** `chaos/repl_lag_contention.sh` (소요 시간: 약 7분)
- **확인 화면:** Slack 채널 내 병합 알림 카드 및 LLM 인과관계 분석 스레드
- *상세 검증 가이드:* [`scenario-c-replication.md`](scenario-c-replication.md) 참조
- **단일 도구 분석과의 차별성:**  
  Wazuh 룰 엔진은 자사 수집 데이터 범위 내에서만 상관 분석을 수행하므로 Zabbix 메트릭 및 Loki 로그와의 연관 관계를 분석할 수 없습니다. 3개 시스템으로 분산된 지표를 단일 사건으로 묶어 분석하는 파이프라인은 본 통합 게이트웨이를 통해 달성됩니다.

### 변형 시나리오 — 보안 축 중심 연관 분석

단순 Brute-force 공격 알림은 다량 발생하는 노이즈 성격이 강하나, '로그인 성공' 및 '`/etc/ssh/sshd_config` 파일 변조' 이벤트가 연쇄 발생할 경우 위험도가 급증합니다. 분석 봇은 3가지 이벤트를 단일 인시던트로 병합하고 심층 조사를 통해 2단계 복합 공격임을 명확히 규명합니다. (다중 관측 축 중첩 시 유의미한 사건으로 승격되는 아키텍처적 특성 검증 — [`runbook.md`](runbook.md) §5 시나리오 D 참조)

## 4. 장애 주입 스크립트 ↔ 데모 시나리오 매핑

| 장애 주입 스크립트 | 주입 대상 및 발생 이벤트 | 관련 데모 시나리오 |
|---|---|---|
| `ssh_bruteforce.sh` | Wazuh 레벨 10 보안 경보 생성 | 데모 A (보안 축), 데모 C 변형 |
| `service_down.sh` | 서비스 중단 ➔ 자동 조치 후보 라우팅 | **데모 B (자가 치유)** |
| `repl_lag_contention.sh` | DB 복제 지연 + CPU/IO 부하 (자원 경합) | **데모 C (AI 초동 분석 핵심)** |
| `repl_lag.sh` | DB 복제 지연 (Master 대량 Write 발생) | 메트릭 시각화 깊이 검증 (지연 시간 수치 추이) |
| `error_burst.sh` | 애플리케이션 로그 에러율 급증 | 메트릭 시각화 깊이 검증 (로그의 지표화) |
| `snmp_iface_error.sh` | 네트워크 인터페이스 에러 카운터 누적 | 알림 노이즈 절감 시연 (Before) |
| `seed_security.sh` | 보안 데이터 시드 생성 | 리포트 및 대시보드 표출용 데이터 생성 |

*스크립트별 실행 위치 및 동작 원리는 [`chaos/README.md`](../../chaos/README.md) 가이드를 참조합니다.*

## 5. 시연 범위의 기술적 한계 및 경계 (Limits)

본 데모 시나리오에서 식별되는 기술적 한계 사항은 [`../03-pitfalls/limits.md`](../03-pitfalls/limits.md) 문서에 명시되어 있습니다.

요약하자면 본 시스템은 **"핵심 판단 및 선판정은 코드 기반 규칙으로 수행하고, LLM은 분석 결과의 인과 설명 생성만을 전담"**하는 구조를 취하고 있습니다. 알림 병합 규칙 및 만성/신규 장애 선판정은 사전 정의된 로직에 의해 구동되며 LLM이 자율 추론한 결과가 아닙니다. 이는 LLM의 환각(Hallucination)을 통제하기 위한 의도적인 아키텍처 설계 판단에 해당합니다.

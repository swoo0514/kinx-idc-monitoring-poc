## A. 값싸고 효과가 확실한 것

### A-1. 종료 시 열린 인시던트 마감(flush) `[제안]`

재기동하면 창이 열려 있던 사건의 분석이 **영영 나가지 않습니다**(G8). 지속화는 검증된 타이밍
로직을 건드릴 위험이 있어 미뤘지만, **종료 시그널에서 열린 인시던트를 즉시 마감하는 것은
값쌉니다.** 자동 재기동을 켜기 전에 이것부터 합니다 — 안 그러면 자동 재기동이 유실을
조용하게 만듭니다.

### A-2. LLM 호출 동시성 상한 `[제안]`

전역 세마포어(N=2~3)로 LLM 구간만 감쌉니다(G7). **랩에서는 절대 재현되지 않고 감시 호스트가
많은 환경에서만 터지는 종류**라, 실환경에 올리기 전에 넣어야 합니다.

### A-3. 게이트웨이 입구에서 호스트명 정규화 `[제안]`

병합 키·Keep fingerprint·수집을 **한꺼번에** 정합시킵니다(G4). 지금은 수집 단계에만 정규화가
걸려 있어, 이름이 다른 호스트는 같은 물리 서버여도 영원히 별개 사건입니다.

### A-4. 만성 판정 개수 정확도 `[제안]`

`countOutput`으로 개수만 별도로 정확히 세거나 limit을 올립니다(G3).
**먼저 `countOutput` 동작을 공식 문서로 확인해야 합니다(미확인).**
이것이 안 되면 "반복 최다 유형 랭킹 → 자동화 후보" 구상이 **조용히 무의미해집니다.**

## B. 랩이 있어야 하는 것

### B-1. 인증서 만료 감시 랩 검증

코드는 있고 실행은 안 했습니다. 표준 템플릿(`Website certificate by Zabbix agent 2`) +
목록 기반 자동화 + Grafana 재고 패널. 절차는
[`ansible/DEPLOY_GUIDE.md`](../../ansible/DEPLOY_GUIDE.md).

**주의**: 7.0 템플릿에는 LLD가 없어 공식 절차가 "도메인마다 호스트 복제"입니다. 목록 기반
자동화가 곧 그 부채를 피하는 방법이고, **상위 버전에는 LLD가 추가**되므로 업그레이드 편익으로
기록해 둡니다.

### B-2. Wazuh 매니저 측 룰 적용 (사용자 실행분)

모듈은 이미 켜져 있고 수집도 되고 있습니다. 남은 것은 **무엇을 컷라인 위로 올릴지**입니다.

- 인덱서 커넥터 + keystore + 방화벽
- 매니저 전역 FIM 무시 규칙 — **에이전트 태그는 파서가 안 읽습니다**(소스 확인). 매니저에 넣습니다
- 로컬 룰 3건 — 패키지 매니저 강등 / 인증 파일 변경 승격 / 통과→실패 회귀 승격
  (**이미 다수 실패 상태인 개별 검사 룰은 승격 금지** — 그대로 폭탄이 됩니다)
- **레플리카 0 → 1** — 현재 설정으로는 인덱서 1대 다운 시 yellow가 아니라 **red**입니다.
  "1대 다운 → green 유지" 검증이 지금 설정으론 성립하지 않습니다

### B-3. 데모 A 드릴다운 강화

로그를 보내는 호스트가 1대뿐이면 "All"과 "그 호스트"의 결과가 같아 **시각적 변화가
없습니다.** 두 번째 호스트에 로그·보안 에이전트를 붙이면 이벤트 행마다 로그가 갈립니다.

### B-4. Ollama 폴백 실측

`--provider ollama`로 같은 벤치를 돌립니다. 콜드/웜을 구분하고, **예산을 초과하면
"온프렘은 사양 상향이 필요하다"를 로드맵에 정직하게 적습니다.** 온프렘이 하드 요건이므로
이 숫자가 도입 판단을 가릅니다.

### B-5. LLM 모델 선정

opus vs sonnet의 지연·비용·품질. `--claude-model` / `LLM_CLAUDE_MODEL`로 스왑 가능합니다.
현재 **미확정**입니다.

## C. 구조를 바꾸는 것

### C-1. 룰의 출처를 사람에서 데이터로 (co-occurrence) `[제안]`

**이것이 이 PoC가 남긴 가장 큰 숙제입니다.**

지금은 사람이 우연히 알아챈 조합만 브리지 룰이 되고, 룰이 된 조합에서만 병합이 일어나며,
병합에서만 심층조사가 도는 **순환**이 있습니다. 발동 기준 반전으로 배분은 고쳤지만
순환 자체는 남아 있습니다.

같은 호스트에서 두 유형이 반복해 함께 뜨면 **시스템이 브리지 후보로 제안하고 사람이
확정**합니다. 그러면 "사람이 알아챈 것만 룰이 된다"가 **"데이터가 제안하고 사람이 승인한다"**
로 바뀝니다. 후보 식별은 코드가, 확정은 사람이 — 만성 판정·병합과 같은 원칙의 반복입니다.

기초 도구는 이미 있습니다 — [`bot/BRIDGE_MINER_GUIDE.md`](../../bot/BRIDGE_MINER_GUIDE.md).

### C-2. 관련 로그만 선별해 주입 `[제안]`

여러 알림이 한 번에 들어올 때 최근 N줄을 통째로 넣는 대신, **사건 유형·키워드에 관련 있는
로그만** 골라 넣습니다. 컨텍스트 상한(한계 #1)을 정면으로 개선하는 방향입니다.

### C-3. 로그를 판정 주체로 올릴 것인가

현재 Loki는 **사건을 만들지 못합니다.** 로그는 발화하지 않기 때문이고, 이건 결함이 아니라
구조입니다. 올리려면 Loki Ruler / Grafana Alerting이 필요하고, **그때는 심각도 매핑표에
Loki 행을 먼저 만들어야 합니다.**

## D. 실환경 로드맵 (랩 밖)

- **dnsdist 네이티브 관측 활성화** — Suricata보다 먼저입니다. 더 싸고 더 빠릅니다
  ([ADR-004](../02-design/decisions/adr-004-suricata-defer.md))
- **프록시 구간 보호** — 인터넷 구간을 지나는 수집 경로에 TLS/PSK가 없습니다. 적용 권고 +
  프록시 고유 지표 감시 확인 + SPOF 리스크 문서화
- **표준 템플릿 활용** — 자작 아이템으로 하던 것을 표준 템플릿이 이미 공짜로 주는 경우가
  있습니다(복제 지연이 그 예). **자작보다 표준을 먼저 봅니다**
- **알림 임계·의존성 정비** — 노이즈의 구조적 원인. 소비 측 보정(심각도 정규화)은 어댑터이고
  근본 해결은 발행 측입니다

## 손대지 않기로 한 것

**안 하기로 한 것도 결정입니다.** 다시 논의하려면 근거를 먼저 반박해야 합니다.

| 항목 | 왜 안 하나 |
|---|---|
| 룰 없는 이상 탐지 | 환각 위험이 "코드 선판정" 원칙과 충돌 |
| 별도 GUI 워크플로 엔진 추가 | Keep의 승인 계층을 두 번 재사용해 이미 충족 |
| Suricata 랩 구축 | 정당성이 좁혀졌고 더 싼 선택지가 먼저 |
| Active Response · 외부 해시 전송 | 계약 제약 · 반출 원칙 |
| 컨테이너·클라우드 커넥터 | 대상 부재 |
| 인시던트 SQLite 지속화 | 검증된 타이밍 로직을 건드릴 위험. A-1로 대신함 |

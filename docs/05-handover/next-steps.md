# 1. 개선 과제 (Correction / Fix) — 현행 결함 및 오류 수정

## 1-1. 게이트웨이 파이프라인 (Bot Engine)

### ~~1-1-1. 웹훅 수신 응답(HTTP 200) 처리 시점 재조정 ★ `[코드]` `[문서]`~~ — **반영 완료 (2026-08-10)**
- **현상 및 문제점:** 게이트웨이가 알림 수신 직후(처리 완료 전) 즉시 HTTP 200 OK를 반환함. 디바운스 대기 중 프로세스가 재기동될 경우 해당 인시던트 데이터가 소실되나, Zabbix는 이미 성공 응답을 수신했으므로 재전송을 수행하지 않음.
- **개선 방안:** Zabbix 미디어 타입의 기본 재시도 메커니즘(기본 3회, 최대 100회 수신 재시도 스펙)을 활용하도록 파이프라인을 수정함. 수신 알림의 파일 인메모리 기록 성공 시점에 200 OK를 반환하고, 실패 시 에러 응답을 반환하여 Zabbix의 자동 재시도 파이프라인을 유도함. *(소요 공수: 0.5일)*
- **공식 근거:** 미디어 타입 공통 파라미터 `Attempts` 기본값 3회(최대 100), `Attempt interval` 0~3600초로 전송 실패 시 자동 재시도를 수행함 — [Zabbix 미디어 타입](https://www.zabbix.com/documentation/7.0/en/manual/config/notifications/media). 현행 구조는 조기 응답으로 인해 해당 기능이 동작할 여지가 없음.
- **반영 내용:** 대기 상태 알림을 파일에 선기록한 후 200 을 반환하도록 변경함(`bot/gateway/pending.py`). 기록 대상은 디바운스 대기가 발생하는 `triage` 경로에 한정하며, `fsync` 완료 후 응답함. 기록 실패 시 503 을 반환하여 Zabbix 재시도 파이프라인으로 처리를 위임함. 프로세스 재기동 시 잔여 항목을 자동 재투입함.
- **설계 판단:** 목록 제거 시점을 분석 완료 후로 지정함. 분석 전 제거 시 분석 구간 장애에서 알림이 소실되며, 분석 후 제거 시 동일 상황에서 카드가 1회 중복 게시됨. 중복은 육안 식별이 가능하고 소실은 불가하므로 후자를 채택함. 재투입 반복을 방지하기 위해 시도 한도(기본 3회)를 적용하되, 폐기 시 반드시 오류 로그를 기록함.
- **랩 검증 (2026-08-10):** 알림 수신 후 디바운스 창 종료 전 `kill -9` 로 프로세스를 강제 종료함. 재기동 후 잔여 항목 1건이 자동 재투입되어 정상 처리되었으며, 처리 완료 후 목록에서 제거됨을 확인함.

### ~~1-1-2. Loki 조회 결과 0건 상태 분류 세분화 ★ `[코드]`~~ — **반영 완료 (2026-08-10)**
- **현상 및 문제점:** 호스트명과 Loki 라벨 불일치 발생 시 API가 HTTP 200 OK + 빈 리스트(`[]`)를 반환함. 수집기는 이를 정상 조회(`ok`)로 간주하여 LLM에 "로그 상 기록 없음"으로 왜곡 전달함.
- **개선 방안:** 수집 계약 메타데이터(`sources`)에 기존 3종(`ok` / `unavailable` / `disabled`) 외에 **"조회 성공 및 대상 식별 실패 (`unmatched_label` / `not_found`)"** 상태 구분을 추가함. 라벨 불일치 시 봇이 판단을 보류하고 보수적 라우팅을 타도록 게이트 제어를 보완함. *(소요 공수: 0.5일)*
- **실측 근거:** 랩 검증 시 `HOST_LABEL_MAP` 미설정 상태에서 로그 수집 0건, 매핑 적용 후 6건으로 확인됨. 당시 매핑 추가로 현상만 우회했고 상태 계약 자체는 보완되지 않음. 실환경은 MaC 배포를 거치지 않은 호스트가 다수이므로 명칭 불일치가 재발할 조건이 갖춰져 있음.
- **반영 내용:** 상태값 `unmatched` 를 추가하고 Loki·Wazuh 양쪽에 동일하게 적용함. 조회 결과가 0건인 경우에 한하여 최근 7일 범위로 호스트 이름 등록 여부를 확인하며(Loki 는 라벨 값 목록 API, Wazuh 는 건수 전용 질의), 확인 질의가 실패하면 판정 불가로 보아 `unavailable` 로 처리함. 새 상태는 마스킹 화이트리스트·LLM 프롬프트·Slack 카드 배지·발동 조건에 모두 전파함. 라벨 이름이 `host` 가 아닌 환경을 위해 `LOKI_HOST_LABEL` 을 분리함. 명세는 `bot/GATEWAY_GUIDE.md` §12.

### ~~1-1-4. 단일 관측 소스 환경 내 발동 조건 확장 ★ `[코드]`~~ — **반영 완료 (2026-08-10)**
- **현상 및 문제점:** 현행 트리아지 발동 조건(`should_triage`)이 교차 상관 분석(다중 소스)을 전제로 설계되어 있어, 단일 Zabbix 알림만 존재하는 인프라 환경에서는 대부분의 알림이 스킵됨.
- **개선 방안:** 단일 소스 환경 수용을 위해 **지식 공백(신규 장애 선판정)** 축을 발동 사유에 추가하여, 처음 발생하는 단일 장애에 대해서도 분석 파이프라인이 구동되도록 제어 로직을 확장함. *(소요 공수: 0.5일)*
- **실측 근거:** 로그·보안 축이 미배선인 상태에서는 발동 조건 4종 중 3종이 성립하지 않음 — 미배선은 조회 실패로 계상되지 않고, 교차 신호는 0으로 산출되며, 90일 상관 분석 결과 유효 조합이 0건이라 병합 조건도 미발생함. 잔여 조건인 SEV1 은 사내 심각도 분포상 극소수에 해당(Warning 등급이 99.5%)하므로, 현행 로직을 실환경에 그대로 적용하면 분석 구동 빈도가 사실상 0에 수렴함.
- **반영 내용:** 선판정 결과가 **신규**(최근 90일 내 동일 트리거 이력 없음)인 사건을 독립 발동 사유로 추가하고, §1-1-2 의 `unmatched` 상태를 보수적 발동 사유에 포함함. 판정 순서는 `bot/GATEWAY_GUIDE.md` §8-3.
- **부수 발견 및 조치:** 발동 조건 확장 과정에서 기존 보수적 발동 경로(조회 실패)에 발동량 제한이 부재함을 확인함. 관측 소스 1종이 장기 중단되면 전체 알림이 LLM 분석 경로로 유입되는 구조이며, 사내 이벤트 발생량 기준 일 400건 이상 규모에 해당함. 신규 사유와 조회 실패 사유에 각각 독립적인 시간당 상한을 적용함(`INCIDENT_GATE_NEW_MAX_PER_HOUR` 기본 20건 / `INCIDENT_GATE_DEGRADED_MAX_PER_HOUR` 기본 30건, 최근 1시간 이동 창 기준). 두 예산은 분리 운영하여 한쪽 소진이 다른 쪽 발동을 차단하지 않도록 구성함.

### ~~1-1-5. 프로세스 종료 시 열린 인시던트 강제 마감 (Flush) `[제안]`~~ — **반영 완료 (2026-08-11)**
- **현상 및 문제점:** 프로세스 재기동 시 디바운스 대기 창에 머물러 있던 오픈 인시던트 데이터가 소실됨.
- **개선 방안:** 프로세스 종료 시그널(SIGTERM) 수신 시 인메모리 버퍼 내 오픈 인시던트를 즉시 마감 및 전송 처리하는 Graceful Shutdown Flush 로직을 추가함.
- **반영 내용:** 종료 이벤트에서 대기 중인 사건을 일괄 마감함(`IncidentManager.flush`). 제한 시간 `INCIDENT_FLUSH_TIMEOUT_S`(기본 25초) 초과분은 대기 파일에 잔존하여 재기동 후 처리됨.
- **부수 결함 수정:** 구현 중 대기 목록 제거가 `finally` 절에 위치하여, 마감 제한 시간 초과로 취소된 경우에도 제거가 실행되어 **처리하지 않은 알림이 소실되는** 경로를 확인함. 처리 완료 이후로 제거 시점을 한정함. 데이터 소실 경로이므로 §1-1-1 의 설계 의도와 직접 충돌하던 사항임.
- **미적용 시 영향(기록):** 데이터는 대기 파일이 보존하므로 소실되지 않으나, 재기동마다 디바운스 창이 초기화되고 재투입 시도 횟수가 1씩 증가함. 배포 등으로 반복 재기동 시 미처리 알림이 상한에 도달하여 폐기될 수 있음.

- **현상 및 문제점:** 현행 병합 키가 호스트를 포함하므로 **서로 다른 장비에서 동시 발생한 알림은 구조적으로 병합되지 않음.** 상관 마이닝 결과 통계적으로 유의한 호스트 간 조합이 다수 확인됨(이중화 코어 장비 쌍, 라우트 서버 쌍, 분산 처리 노드 3중 등).
- **선행 확인 결과:** 트리거 유형 축에서 산출된 유의 조합은 **전부 동일 호스트 쌍**이었고, 이는 현행 `(host, incident_class)` 병합이 이미 처리하는 범위임(백엔드 상태 점검 7창·감시 서버 폴러 항목 9창·BGP 주소체계 쌍 3창 모두 교차 호스트 0건). **즉 마이닝의 실질 산출은 신규 규칙이 아니라 현행 병합 동작의 검증이며, 미처리로 남은 것은 교차 호스트 축뿐임.**
- **개선 방안:** 병합 키에 호스트를 강제하지 않는 예외 축을 정의함. 다만 무조건 확대하면 무관한 사건이 한 인시던트로 묶이므로, 마이닝으로 유의 판정되고 `--pair` 로 관계 성격이 확인된 조합에 한해 허용 목록 방식으로 적용함.
- **미채택 판정 (2026-08-11, 4개 관점 교차 검토):** 아래 사유로 구현하지 않음.
  - **발동 가능성:** 실효 병합 창은 최대 300초가 아니라 **마지막 알림 후 90초**임(디바운스). 반면 `--profile` 로 방향이 확인된 교차 호스트 관계의 시차 최다 구간은 2400~3600초로, 창의 8~12배 밖임. 창 안에 드는 유일한 실측 사례(+241초)는 인터페이스 오류 계열이라 마이닝 기본 제외 대상이며, 인과가 아닌 수집 주기 오프셋으로 이미 판정됨.
  - **규칙 산출 불가:** 근거로 인용된 이중화 쌍·라우트 서버 쌍은 **호스트 축** 산출물로 유형 정보가 없음. 병합 키는 `(호스트, 유형)` 이므로 현행 근거로는 허용 목록 항목을 1건도 구성할 수 없음. `--emit-rules` 도 `--by cls` 전용이라 산출 경로 자체가 부재함.
  - **컨텍스트 오염:** 수집기가 첫 호스트 1대만 잡아 로그·보안·열린 문제를 1회 조회하므로, 나머지 호스트는 조회되지 않은 채 `sources` 에는 `ok` 로 기록됨. §1-1-2 의 조회 상태 계약이 호스트 축에서 무력화되며, 조회하지 않은 호스트에 대해 침해 배제를 단언하게 됨.
  - **테넌트 경계:** 병합 키에 테넌트 개념이 없어 서로 다른 고객사 호스트가 단일 사건이 될 수 있음. 동일 동작을 Keep 기본 상관에서 이미 부적합 판정한 바 있음(ADR-001 KR-3).
  - **발동 조건 우회:** `is_merged()` 는 조건 없이 발동하므로, 병합 확대는 시간당 상한이 적용되지 않는 사건 부류를 신설함.
- **대체 방안:** 병합 대신 **동일 유형이 동일 호스트그룹 내 몇 대에서 동시 개방 중인지**를 컨텍스트와 카드에 부가함. 호스트명을 전송하지 않고 개수와 그룹만 사용하므로 마스킹 대상이 증가하지 않으며, 조회 범위가 그룹 내로 한정되어 테넌트 격리가 조회 조건으로 보장됨. 지문·조치 대상·전송 화이트리스트 미변경.
- **부수 반영 (§1-1-13-1):** 검토 과정에서 병합 키에 감시 영역이 없어 **서로 다른 감시 서버의 동일 호스트명이 현재도 병합되는** 잠재 결함을 확인함. 병합 키와 지문에 영역을 추가함(상세는 다음 항목).

### ~~1-1-14. 감시 영역 미구분에 의한 교차 테넌트 병합~~ — **반영 완료 (2026-08-11)**

- **잔여 해소 (2026-08-11):** 컨텍스트 수집 시 알림 수신 서버를 선택하도록 반영함. 호스트 명부에 감시 서버 절(`sources`)을 두어 소스별 주소와 토큰 참조를 지정하며, 토큰 값은 파일이 아닌 환경 변수에서 조회함(명부는 형상 관리 대상). 미지정 시 기존 단일 인스턴스 조회로 동작함.
- **호스트 속성 통합 (2026-08-11):** 동일 성격의 호스트 속성이 환경 변수 4종에 분산되어 있던 것을 명부 파일 1개로 통합함(`HOST_REGISTRY_FILE`). 초안은 `probe.py registry` 로 Zabbix·Loki·Wazuh 실 조회를 통해 생성함. 명부 미등재 호스트도 정상 동작하며, 식별은 명부가 아닌 `(감시 서버, 호스트명)` 조합이 담당함(Zabbix 가 호스트명 유일성을 강제).
- **UUID 미도입 사유:** 식별력이 증가하지 않으며(위 조합이 이미 유일), 자동등록 기반 환경에서는 식별자를 발급할 등록 시점이 부재함. 명부 미등재 호스트를 위한 대체 경로가 필수이므로 명부가 식별의 필수 조건이 될 수 없음. 이름 변경 시 이력 연속성 확보 용도로는 유효하나, 이는 게이트웨이가 기록을 축적하는 저장소(§2-1-1)가 선행되어야 함. 형식만 정의 (`id` 필드)하고 미사용 상태로 둠.

### ~~1-3-1. Loki Compactor 기반 데이터 보존(Retention) 정책 설정 `[문서]`~~ — **반영 완료 (2026-08-10)**

- **반영 내용:** `compactor.retention_enabled: true` 및 `delete_request_store: filesystem`(보존 활성화 시 필수 항목), `limits_config.retention_period: 744h`(31일) 를 적용함. 보존 기간은 MSP 월간 리포트가 한 달 단위 로그 근거 커버리지를 산출하므로 해당 기간을 하회하면 리포트가 대상 기간을 조회할 수 없다는 점을 기준으로 산정함. 적용 후 컴팩터 활성화 및 수집 정상 동작을 확인함. 스트림별 차등 보존(`retention_stream`)은 고객사별 보존 요건이 확정되지 않아 미적용함.

### 1-3-2. Loki Stream 및 유입량 상한(Limits Config) 제어 `[코드]` — **도입 로드맵 이관 (2026-08-11)**
- **⚠️ 전제 정정 (2026-08-10):** 본 항목의 기존 기술("유입량 제한 설정 미비")은 사실과 다름. 랩 구동 인스턴스의 `/config` 엔드포인트 조회 결과, 명시적 설정이 없어도 Loki 기본값이 적용되어 있음 — `ingestion_rate_mb: 4`, `ingestion_burst_size_mb: 6`, `per_stream_rate_limit: 3MB`, `max_global_streams_per_user: 5000`, `max_label_names_per_series: 15`, `max_line_size: 256KB`. 상한 자체는 존재하며, 실제 과제는 **해당 값이 대상 환경에 적정한지 판단할 근거의 부재**임.
- **현상 및 문제점:** 현행 기본값은 Loki 의 범용 기본값으로, 대상 환경의 유입 규모를 반영하여 산정된 값이 아님. 실환경 로그 유입량은 Loki 미도입 상태이므로 측정 불가함.

- **개선 방안:** 실환경 도입 시 파일럿 대상 호스트군의 유입량을 측정한 후 상한을 산정함. 산정 시 Loki 3.x 가 자동 부여하는 `service_name`·`detected_level` 라벨을 스트림 수 계산에 포함해야 함(§1-3-0 참조). 측정 없이 값을 변경하는 것은 근거 없는 설정 변경에 해당하므로 수행하지 않음.

Ansible 배포 시 Zabbix 호스트 태그(예: `axis:logs`·`axis:security`)를 자동 부여하고, 수집기가 환경 변수 대신 해당 태그를 조회하여 판단하는 구조로 전환함. 태그는 이미 분류 선언(`incident_class`)에서 동일한 방식으로 사용 중이므로 신규 개념 도입에 해당하지 않음. 실환경 Zabbix 는 읽기 전용 접근만 허용되므로 태그 부여 권한 확보가 선행 조건이며, 미확보 시 현행 환경 변수 방식을 유지하되 `probe.py names` 정기 실행을 운영 절차에 포함함.
- **적용 범위 참고:** 컨테이너 기반 호스트의 경우 로그 축은 Alloy 라벨 변환으로 논리 호스트 귀속이 가능하나, Wazuh 는 에이전트가 OS 인스턴스 단위로 배포되어 동일한 귀속이 불가함. 두 축의 커버리지는 구조적으로 일치하지 않으므로 축별 개별 관리가 필요함.

### 2-4-4. 데이터 기반 연관 브리지 룰 자동 재탐색 `[제안]`
- **목적:** 동일 호스트 내 동시 발화되는 알림 패턴 및 수동 피드백 이력을 분석하여 정밀 연관 브리지 룰 후보를 데이터 기반으로 자동 제안함.
- **선행 실측 (2026-08-07) `[코드]`:** 본 항목의 전제였던 "1회 측정 결과 유효 조합 0건"은 **집계 입도 문제였음**이 확인됨. 사건 유형 축(8종)은 조합이 28개뿐이라 신호가 접히고, 트리거명 원문은 인터페이스 번호·임계값·측정값이 이름에 포함되어 **고유율 95%** 로 통계가 서지 않음. 숫자·IP 치환만으로 고유율이 1% 미만으로 수렴하고, 5회 이상 등장하는 유형이 전체 이벤트의 98.9%를 덮음. 이 축에서 후보가 산출됨. 도구에 `--by {cls,tmpl,name,host}` 축 선택과 `--scope {host,global}` 창 범위 선택을 추가함.
- **호스트 간 상관 `[코드]`:** 기존 구현은 시간창을 **호스트별로** 잘랐으므로, 진단에서 확인된 최대 구조(감시 미등록 상류 1대 → 하위 29대 파생 알림)가 서로 다른 창으로 흩어져 **구조적으로 관측 불가능**했음. `--scope global` 추가로 호스트를 가로지르는 조합이 측정 범위에 들어옴.
- **우연 기준선 `[코드]`:** 상관 지표에 "이 정도는 우연 아닌가"를 판정할 기준이 없었음. 축 라벨만 섞고 시각·빈도를 보존한 뒤 동일 마이닝을 반복하는 셔플 검정(`--null N`)을 추가함. **실측 결과가 기존 순위를 뒤집음** — 공동 발생 빈도 상위 18쌍 중 우연 천장을 넘은 쌍은 1개이며, **최다 공동 발생 쌍의 leverage 는 음수**(우연보다 덜 붙음)였음. 빈도 정렬을 후보 순위로 쓰면 안 됨. 기존 임계값 필터(`together>=5, lift>=2.0`)가 산출한 18쌍과 셔플 검정이 산출한 18쌍은 **교집합이 8쌍**으로, 임계값 방식이 우연 쌍 10건을 올리고 유의 쌍 10건을 누락하고 있었음.
- **셔플 층화 `[코드]`:** 위 셔플을 전 구간 균일 방식으로 구현했을 때 **일주기 구조가 파괴되어 검정이 느슨해지는 결함**을 실측으로 확인함 — 인터페이스 오류와 디스크 응답 지연이 각각 15~19시에 40% 이상 몰려 있어, 두 알림이 무관해도 천장을 넘음. 시간대별로 나눠 섞도록 수정하여 시각·빈도에 더해 **일주기까지 보존**함. 수정 후 천장이 상승하고(유형 축 0.0019 → 0.0100) 유의 판정이 4쌍에서 1쌍으로 축소됨. 층화 전 결과는 과대 판정이었음.
- **선별 이원화 `[코드]`:** leverage 단독 선별이 **소량·완전 동반 조합을 구조적으로 누락**함을 확인함. 백엔드 상태 점검 3종은 발생한 창 10개 **전부에서 셋이 함께** 떴으나 발생량이 적어 관측·기대 빈도 차이가 작았고, 회선 이중화 쌍은 양방향 조건부확률이 0.85 이상인데 leverage 는 미미했음. 대량·부분 상관(leverage + 셔플 천장)과 소량·완전 동반(양방향 조건부확률 0.8 이상 · 5일 이상 · 5회 이상)을 **분리 선별**하도록 수정함. 후자는 셔플에서 통과 쌍이 **0건**으로 오탐이 없음. 실측 산출 예: 감시 서버 자체의 폴러 사용률 항목 2종이 양방향 조건부확률 1.000(8일)으로 **동일 대상 이중 계측** 확인.
- **쌍 상세 분석 `[코드]`:** 유의 판정된 쌍이 (a) 같은 사건의 양면인지 (b) 공통 원인인지 (c) 무관한지는 지표만으로 갈리지 않으므로, 쌍 하나의 공동 발생 창을 원본 이벤트 수준으로 펼치는 `--pair A B` 를 추가함. 선후 횟수·시차 중앙값·**시차 집중도**·양측 트리거 유형을 산출함. 시차 집중도가 판별 축임 — 인과 사슬은 시차가 흩어지지만 관측 시점만 어긋난 쌍은 항상 같은 만큼 벌어짐. 실측에서 최상위 쌍이 **시차 +241초에 93% 집중**으로 나타나 인과가 아닌 **수집 주기 오프셋**으로 판정됨(양측 트리거 유형도 3종 일치). 이 구분이 없으면 "A가 근원"으로 오독함.
- **지표군 확장 `[코드]`:** 초기 구현은 lift 와 조건부확률만 산출했고, 희귀 조합에서 lift 가 부풀려지는 현상을 실측으로 확인함(`disk_space + service_down` 이 표본 확대에 따라 5.53 → 3.87 → 1.22 로 수렴). 연관 규칙 표준 정의를 따라 **leverage**(관측·기대 빈도 차이)와 **Zhang's metric**(−1~1, 희귀성에 덜 민감)을 추가함 — 식은 [mlxtend `association_rules`](https://rasbt.github.io/mlxtend/user_guide/frequent_patterns/association_rules/) 와 동일하되 읽기 전용 가드와 비중첩 시간창 로직을 유지하기 위해 **도구 교체 없이 지표만 자체 산출**함. 조합 폭증 시 FP-Growth 전환 여지는 기록만 유지함.
- **검정 방식 교체 — 최대값 기준에서 쌍별 FDR 로 `[코드]`:** 위 셔플 천장은 **전 쌍을 통틀어 한 번도 틀리지 않는 선**(family-wise)이라, 검정 대상이 수백 쌍이면 지나치게 높아짐. 실측상 이 방식은 데이터를 늘릴수록 둔감해짐 — 관측 기간이 늘면 검정 가능한 축이 늘고 쌍은 그 제곱으로 늘어 천장이 함께 상승하는 반면(60일 0.0068 → 90일 0.0103), 실제 관계의 leverage 는 확률값이므로 기간이 늘어도 커지지 않음. 쌍마다 순열 p값을 산출하고 Benjamini-Hochberg 절차로 목표 오탐율을 통제하는 방식으로 교체함. **동일한 90일 데이터에서 통과 조합이 1쌍 → 52쌍**(오탐율 5% 기준)으로 변화했고, 상위에 산출된 것이 **BGP 피어의 IPv4·IPv6 쌍**임 — 동일 세션의 두 주소체계이므로 병합 대상임이 자명하나, leverage 가 0.0001~0.0003 수준이라 최대값 기준으로는 구조적으로 검출 불가능했음. **데이터를 늘리지 않고 검정 방식만 바꿔 52배**임.
- **부재를 유의로 세던 결함 `[코드]`:** 순열 검정 최초 구현에서 **음의 상관 조합이 후보로 산출되는 현상**을 실측으로 확인함(leverage 가 음수인데 통과). 원인은 셔플 결과에서 해당 조합이 한 번도 함께 나타나지 않으면 결과 목록에 존재하지 않고, 그 부재를 "셔플이 관측값에 미달"로 집계한 것임. 실제로는 동시 발생 0 이므로 `leverage = −P(A)P(B)` 로 산입해야 함. 부재 시 단독 등장 빈도로 값을 복원하도록 수정하고, 검정 대상을 **leverage 양수 조합으로 한정**함(음의 상관은 병합 후보가 아니며, 대상 축소로 다중 검정 부담도 감소함).
- **셔플 횟수 부족과 관계 부재의 구분 `[코드]`:** 순열 p값의 해상도는 `1/(셔플횟수+1)` 이므로 횟수가 적으면 p값이 바닥에 깔려 BH 문턱에 도달하지 못하고 **"통과 0쌍"이 출력됨**. 이는 관계가 없다는 뜻이 아니라 판정이 성립하지 않은 상태임(실측: 100회에서 0쌍, 200회에서 52쌍). 필요 횟수를 역산해 경고하고 **"관계 없음이 아니라 판정 불가"임을 명시**하도록 구현함 — §1-1-7(조회 결과 0건 처리)과 동일한 원칙을 통계 판정에 적용한 것임.
- **측정 방식의 구조적 한계 확인 및 대체 `[코드]`:** 검출력을 먼저 측정한 결과 도구 감도는 충분함이 확인됨 — 노이즈 94% 포함 상태에서도, "드문 원인 → 흔한 결과" 형태에서도 공동 발생 3회 조합을 탐지함. **원인은 감도가 아니라 시간 구간 분할 방식이었음.** 강도를 지정한 조합을 시차별로 삽입해 측정한 결과, 겹치지 않는 고정 구간은 시차가 구간 크기에 근접하면 급격히 손실되고 구간을 넘으면 전혀 포착되지 않음(구간 600초 기준 시차 5분 35% 손실 · 10분 80% 손실 · 20분 이상 0). 따라서 당초 "교차 증상 조합 미산출"은 **시차 10분 이내에 한정된 결과**였음. 구간 확대는 구간 수 감소로 정밀도가 저하되므로(6시간 구간에서 190개), 알림 하나하나를 기준점으로 삼아 이후 시차 구간별로 후속 알림을 집계하는 방식(`--profile`)으로 대체함 — 경계 손실이 없고 A→B·B→A 를 분리 집계하여 방향이 지표에서 산출됨. **동일 데이터에서 통과 조합 32개 → 80개.** 산출 예: 감시 대상 호스트 응답 없음 → 감시 서버 unreachable 폴러 사용률(7회·비율 70%·역방향 0), CPU 부하 → 프로세스 수 과다(22회·비율 73%·역방향 0·최다 구간 2400~3600초).
- **구간 겹침 측정 신설 `[코드]` `[문서]`:** 기준점 방식으로도 **만성 문제가 열려 있는 상태에서 다른 장애가 발생하는 형태**는 포착되지 않음 — 두 시작 시각이 며칠 떨어져 있어 시차 설정과 무관함. 이벤트 객체에 지속 시간 필드가 없고 `r_eventid`(복구 이벤트)의 시각과 비교해 산출하도록 규정되어 있음([event object](https://www.zabbix.com/documentation/7.0/en/manual/api/reference/event/object)). 수집부에 복구 이벤트 조회를 추가하고 겹침 집계·검정을 구현함. **기존 수집분에는 해소 시각이 전혀 없으므로 재수집 후 측정 가능.** 미해소 이벤트는 집계 제외 — 열린 상태로 두면 이후 모든 이벤트가 겹침으로 계상됨.
- **노이즈가 선별을 가림 — 정비 선행의 정량 근거 `[코드]`:** 트리거 유형 축 전체 측정에서 우연 천장을 넘는 조합은 **1쌍뿐**이며 그마저 천장의 2배 경계임. 원인은 알고리즘이 아니라 입력 분포임 — **인터페이스 오류 계열 한 종류가 전체 이벤트의 94.0%**이고, **호스트 2대가 전체의 74.6%**, 그중 1대는 10분 창 기준 **94.5%의 창에 등장**함. 해당 계열을 제외하고 재측정하면 유의 조합이 4쌍으로 늘고 **전부 서로 다른 증상 간 조합**으로 바뀜(전체 측정에서는 인터페이스 오류끼리의 조합이 대부분). 즉 **§4 의 임계치·의존성 정비는 마이닝의 선행 조건**이며, 이는 판단이 아니라 측정 결과임.
- **재측정 자동화 + 승인 게이트 `[코드]`:** 측정 결과를 규칙 파일로 주고받는 구조는 갖췄으나 **재측정이 수동**이므로, 환경이 변해 규칙이 맞지 않게 되어도 이를 인지할 수 없음. 정기 실행 자체는 기계적이나, 규칙이 무단 변경되면 판정 근거가 바뀌어도 인지할 수 없고 부실한 측정이 그대로 반영될 위험이 있음(실측상 통과 조합의 81%가 단일 사건에서 산출된 사례 존재). 따라서 **자동 재측정 + 사람 승인** 구조로 구성함. 승인 계층은 신규 구축하지 않고 시스템 변경 승인(데모 B)·고객 발송 승인(월간 리포트)에 사용한 Keep 워크플로를 **세 번째로 재사용**함.
  - **변경분만 제시** — 전체 파일을 제시하면 차이를 찾는 부담으로 검토가 형해화됨. 추가·변경·삭제만 산출
  - **주의 항목 자동 표기** — 비율 30% 이상 변동, 관측 일수 5일 미만 하락, 규칙 전량 소멸 시 별도 표시(차단이 아닌 표시. 판단은 사람이 수행)
  - **승인 대상과 반영 대상의 동일성 보장** — 승인과 반영 사이 재측정이 실행되면 검토한 내용과 다른 파일이 반영되므로, 승인 시점 해시 불일치 시 거부. 월간 리포트의 초안 고정 방식과 동일한 원칙
  - **되돌리기** — 이전 파일을 시각 기준으로 보존
  - **변경 없으면 승인 요청 미생성** — 빈 요청이 누적되면 검토 자체가 형식화되어 실제 변경도 함께 통과됨
  - **부수 효과** — 규칙 변경 이력이 곧 인프라 변화의 신호가 됨(관계가 약해졌다는 것은 환경이 달라졌다는 의미)
  - **실행 시점 `[코드]`** — 수집·마이닝·산출·승인 요청을 단일 명령으로 통합하고 측정 조건을 한 곳에 고정함(조건이 달라지면 이전 규칙과 비교가 성립하지 않음). 90일 창 기준이므로 매일 실행 시 창이 89일 중복되어 값이 거의 변하지 않음 — **정기는 월 1회**, 그보다 중요한 것은 임계치 정비·분류기 변경·관측 소스 추가·인프라 변경 직후의 수동 실행임. 수집 실패 시 승인 요청을 생성하지 않음(부분 측정은 미수집 기간을 "신호 없음"으로 둔갑시키므로 기존 규칙보다 열등함)
  - **호스트명 불일치 검사 `[코드]`** — 두 소스에 데이터가 있어도 호스트명이 일치하지 않으면 교차 조합이 구조적으로 0건이며, 이를 "관계 없음"으로 오독할 수 있었음(§1-1-2 와 동일한 형태). 소스 간 호스트명 교집합 비율을 산출해 경고하도록 추가함. **사이트 정보가 불필요한 범용 검사**이며, 실제 명칭 변환은 환경변수로 주입하고 근본 해결은 배포 시 FQDN 통일임
- **잔여 과제:** 창 크기에 따라 leverage 절대값이 함께 커지므로(창 60초 0.005 → 600초 0.053) **창을 가로지르는 비교는 불가**하며, 창별 셔플 천장 대비 배수로만 비교해야 함. 창 크기 선정 기준은 미확정임. 유의 판정된 쌍 중 다수가 선후 방향이 갈리지 않아 공통 원인 후보로 남아 있으며, 상류 요소 식별에는 구성 정보(랙·전원·상류 회선)가 필요하나 감시 데이터만으로는 확보되지 않음.
  **또한 최다 알림 계열(인터페이스 오류, 전체의 94%)이 마이닝에서 제외된 상태이므로 해당 계열은 연계 대상 밖임.** 계열 내부만 별도 측정하는 방식(포함 필터 신설)과 호스트 분할 측정(기존 기능으로 가능)으로 부분 해소가 가능하나, 근본 해소는 발행 측 임계치·의존성 정비(§4)가 선행 조건임 — 노이즈를 측정하면 노이즈 관계가 산출됨.

- **Ollama 온프레미스 폴백 성능 실측:** Cold/Warm Start 응답 지연 시간 정량 측정 (예산 초과 시 온프렘 사양 상향 필요성을 로드맵에 기재)
- **LLM 모델(Opus vs Sonnet) 정량 평가:** 모델별 지연 시간, API 소모 비용, 분석 품질 트레이드오프 실측

# 5. 명시적 제외 및 보류 범위 (Out of Scope)

의도적 아키텍처 판단에 의해 개발 범위에서 제외(Inactivation) 처리된 항목입니다.

| 제외 항목 | 제외 및 보류 사유 |
|---|---|
| **규칙 없는 자율 이상 탐지** | **입력 데이터 품질이 선행 조건 미충족** — 실측상 네트워크 알림이 전체 이벤트의 89.5%를 차지하는 상태에서 이상 탐지를 적용하면 노이즈가 축소되지 않고 확대됨. 알림 임계·의존성 정비(§4)가 선행되어야 함. *(단, LLM 기반 자율 판정은 환각 위험으로 별도 제외 — Elastic·OpenSearch 등의 통계 기반 ML 이상 탐지는 이 사유에 해당하지 않으므로 정비 완료 후 재검토 대상임. §2-2-2 가 결정론적으로 판정 가능한 범위만 선취함)* |
| **별도 GUI 워크플로 엔진 추가 (n8n 등)** | Keep 내장 승인 제어 워크플로 재사용을 통해 요구사항을 이미 충족함 |
| **Suricata 랩 직접 구축** | 관측 사각지대 분석을 통해 네이티브 관측 활성화라는 고효율 대안을 선순위로 정의함 |
| **Active Response 및 외부 해시 연동** | Active Response 는 위탁 계약상 임의 조치가 금지된 자산이 존재하여 제외. 외부 해시 연동은 데이터 외부 반출 통제 원칙에 위배됨 |
| **컨테이너 및 클라우드 커넥터 확장** | 현재 관측 대상 인프라(온프레미스 VM 및 물리 서버) 범위를 준수함 |
| **진행 중 인시던트 데이터 지속화** | 검증된 타이밍 로직 영향 최소화를 위해 프로세스 종료 시 마감(Flush) 처리로 대체함 *(완료된 분석 이력 저장소 구축과는 별개 항목)* |
| **Keep AI 상관 분석 도입** `[문서]` | Keep Cloud 및 Enterprise On-Premises 전용 기능으로 **오픈소스 배포판에서는 제공되지 않음** ([docs.keephq.dev/overview/ai-correlation](https://docs.keephq.dev/overview/ai-correlation)) |
| **OpenSearch Anomaly Detection 플러그인** `[문서]` | Wazuh 가 **완전한 통합을 구현하지 않아 기본 비활성** 상태로 배포함. 수동 설치는 가능하나 공식 통합이 아니므로 버전 변경 시 파손 위험이 남음 |
| **Aurora (Arvo AI) 솔루션 직접 도입** `[문서]` | **동일 역할을 HolmesGPT 로 이미 벤치마크했고 하이브리드 운용 결론까지 실측 확보함** — 교체를 정당화할 근거가 없음. 부차적으로 조사 대상이 퍼블릭 클라우드(AWS·Azure·GCP)와 Kubernetes 중심이며 통합 목록에 Zabbix 가 포함되지 않음. *(온프레미스 배포 자체는 가능함 — Docker Compose 자체 호스팅 및 에어갭 번들 지원. 제외 사유는 배포 방식이 아니라 조사 대상 범위임)* |
| **Prometheus · Mimir · Tempo · Kafka · Kubernetes 도입** | 기술 선정 3단 필터(기존 자산 활용 → 실측 근거 → 가역성) 미통과. 실측 알림 발생량이 초당 0.005건 수준으로 메시지 큐·분산 처리 도입 기준에 크게 미달하며, 수집 계층 대체 시 프록시 경유 사설망 고객사·SNMP Trap·테넌트 권한 체계를 전면 재구축해야 함 (발표자료 부록 5 판정 유지) |

# 6. 미확인 및 의존성 항목 (Unverified Dependencies)

외부 회신 및 사양 검증이 필요한 항목입니다.

- **[해소] 상관 분석 관측 기간(90일)의 근거** — 실환경 `housekeeping.get` 조회 결과 `hk_events_mode=1`·`hk_events_trigger=365d` 로, 트리거 이벤트는 1년간 보관되며 이후 삭제됨. 즉 현행 90일 창은 데이터 보관 한계에 의한 제약이 아니라 임의 설정값이었음. 연장 시 최대 365일까지 가능하나, 관측 기간 연장의 효과 한계(15일 17종 → 90일 83종, 전체 대비 비율은 20~30% 에서 개선되지 않음 — `bot/BRIDGE_MINER_GUIDE.md` §6)와 트리거 구성 변경에 따른 과거 관계의 유효성 저하를 고려하여 현행 유지함. **180일 재측정 후 산출 규칙 수를 비교하여 근거를 확정하는 것을 후속 과제로 둠.**
- **실환경 지표 데이터 실제 보존 기간** — `hk_history_mode=0`·`hk_trends_mode=0` 으로 Zabbix 내부 정리 기능이 비활성 상태임(이벤트만 활성). 대규모 환경에서 DB 파티셔닝을 적용할 때 나타나는 구성과 일치하나, 파티셔닝 적용 여부는 API 로 확인 불가함. `history.get` 으로 과거 시점의 데이터 존재 여부를 확인하여 실제 보존 기간을 실측하는 것이 확인 방법임(분석 파이프라인에는 영향 없음 — 마이닝은 이벤트 기반이며 이벤트 정리는 활성 상태임)
- 관측 인프라망에서 외부 LLM API 서비스로의 Outbound Egress 통신 허용 여부
- Zabbix 8.0 이벤트 처리 엔진 내 제공 예정 Operations 세부 기능 목록
- Zabbix API `countOutput` 파라미터 연산 가용성 검증
- Wazuh Integrator 데몬의 자체 재시도 및 메시지 큐 동작 스펙
- Keep Self-hosted 환경 내 워크플로 생성 수량 제한 여부 (Cloud 버전 기준 5개 제한)
- Grafana 사내 전용 플러그인 개발 시 서명(Signature) 요건 및 Proxy Route 가용 여부
- Aurora 의 Grafana 통합 경유 시 Zabbix 데이터 간접 조회 가능 여부 (직접 통합 부재는 확인, 우회 경로는 미검증)
- **이중화 짝 장비 간 감시 항목 갱신 주기 불일치 여부** — 상관 마이닝 실측(2026-08-07)에서 이중화 구성 코어 장비 2대의 동일 유형 인터페이스 오류 알림이 **시차 약 241초에 93% 집중**되어 발화함. 인과가 아니라 관측 시점 차이로 판단되나, 원인이 Zabbix 아이템 갱신 주기 설정 차이인지 장비 측 카운터 갱신 주기 차이인지는 미확인. 확인 시 §2-4-4 의 병합 처리 대상이 확정되며, 갱신 주기 설정 차이로 확인되면 발행 측 정비 항목(§4)으로 이관함

# 7. 과제 목록 관리 규약

본 목록 자체를 유지·검증하기 위한 규약입니다. 개별 과제의 내용이 아니라 **목록이 정확한 상태를 유지하는 방법**을 정의합니다.

## 7-1. 완료 조건 명시

**각 과제에는 "무엇이 관측되면 완료인가"를 착수 시점에 정의합니다.** 외부 도구는 하드 요건 채점표로 정량 평가했으나(ADR-001·002·003) 자체 과제에는 완료 정의가 없어, 구현 종료 시점을 판단할 근거가 부재한 상태입니다.

| 과제 | 완료 조건 예시 |
|---|---|
| §2-2-1 신호 부재 감지 | 게이트웨이를 의도적으로 정지시킨 뒤 정의된 시간 내 알림 수신 확인 |
| §2-3-1 통계 요약 전송 | 수집 상한 초과 사건에서 분석 본문이 등급 분포·반복 패턴을 인용 |
| §2-4-5 주석 발행 | 사건 구간이 대시보드 타임라인에 표시되고 태그 필터로 조회 |

작업 상태는 기존 3단계(**랩 실증 / 코드 존재·미실증 / 미구현**)를 따르며, "완료" 표현은 사용하지 않습니다 ([evidence-policy §4](../02-design/evidence-policy.md)).

## 7-2. 효과 측정 — §2-4-1 의 이중 역할

**§2-4-1(판정 정확도 정량 측정)은 봇의 채점기인 동시에 다른 고도화 과제의 효과 계측기입니다.** 통계 요약 전송·변경 이력 반영·과거 결론 활용이 실제로 분석 품질을 개선했는지는 이 지표로만 판별할 수 있습니다.

따라서 §2-4-1 은 분석 품질 과제(§2-3) 착수에 **선행하는 것이 유리합니다.** 계측기 없이 먼저 적용하면 개선 여부를 사후에 증명할 수 없습니다.

## 7-3. 폐기 트리거 — 목록이 줄어드는 조건

**미확인 항목이 해소될 때 어느 과제가 축소·폐기되는지를 사전에 정의합니다.** 정의하지 않으면 확인이 완료되어도 목록이 감소하지 않습니다.

| 미확인 항목 해소 시 | 영향받는 과제 |
|---|---|
| Zabbix 8.0 이벤트 처리 Operations 확인 | §1-1-11 진행 여부 확정. 제품 기능과 중복 시 폐기 |
| 8.0 이벤트 그룹핑 기능 제공 확인 | 병합 계층 중 Zabbix 내부 처리분 축소, **교차 소스 전용으로 범위 재정의** |
| Grafana 플러그인 서명 요건 확인 | §2-4-3 진행 또는 §2-4-5 로 대체 확정 |
| 관제망 외부 Egress 불가로 확인 | 외부 모델 경로 폐기 및 온프렘 전환, §2-1-3 의 성격 변경 |
| `countOutput` 미지원으로 확인 | §1-1-7 대안 필요, §2-4-1 산출 범위 축소 |

## 7-4. 재점검 주기 및 트리거

- **정기:** 분기 1회 전수 재점검 (코드·문서·발표자료 대조)
- **트리거:** ① Zabbix LTS 신규 출시 ② 스택 구성요소 메이저 업그레이드 ③ 과제 5건 이상 진행 완료 ④ 실환경 구성 변경(로그 스택 도입 등)

재점검 시 **`[문서]` 근거의 유효성도 함께 확인합니다** — 참조 URL 생존 여부와 제품 버전 변동으로 인한 내용 변경. 근거는 시간 경과에 따라 유효성이 소실됩니다.

## 7-5. 신규 항목 추가 요건

[evidence-policy §2-1](../02-design/evidence-policy.md) 의 확인 순서(저장소 → 기존 산출물 → 외부 조사 → 제안)를 거친 항목만 추가합니다. 2026-08-06 재점검에서 제안 항목의 상당수가 이미 구현·문서화된 상태였으며, 저장소 확인 미선행이 원인이었습니다.

# 8. 추천 추진 순서 및 실행 가이드

1. **최우선 단기 과제 실행 (공수 0.5일~1일 소요 5개 항목):**

  - Loki 조회 결과 0건 상태 분류 세분화 (§1-1-2)

  - 단일 소스 환경 발동 조건 확장 (§1-1-4)
  - 관측 파이프라인 신호 부재 감지 파이프라인 구축 (§2-2-1)
  - 알림 분류기 오분류 정정 (§1-1-12) — 분류 결과가 병합 범위와 발동 조건을 결정하므로 후속 과제의 선행 조건임
2. **기반 구조 4대 기둥 수립:**
  - 판정 이력 저장소 구축 (§2-1-1)
  - 텔레메트리 수집 데이터 표준화 스키마 적용 (§2-1-2)
  - 외부 LLM 전송 경로 단일 Egress Proxy 일원화 (§2-1-3)
  - 배포 및 도입 표준 패키징 구성 (§2-1-4)
3. **효과 계측기 확보:** 판정 정확도 정량 측정 (§2-4-1) — 이후 분석 품질 과제의 개선 여부를 판별할 기준선을 먼저 확보함 (§7-2)
4. **분석 품질 고도화 과제 단계적 적용** — 통계 요약 전송 · 변경 이력 반영 · 지시문 계층 분리 · 과거 결론 활용
5. **표현 계층 확장:** 판정 주석 발행 (§2-4-5) 선행 후, 미확인 항목 해소 여부에 따라 판정 정정 UI (§2-4-3) 진행 여부 확정

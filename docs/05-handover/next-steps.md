# 1. 개선 과제 (Correction / Fix) — 현행 결함 및 오류 수정

## 1-1. 게이트웨이 파이프라인 (Bot Engine)

### 1-1-1. 웹훅 수신 응답(HTTP 200) 처리 시점 재조정 ★ `[코드]` `[문서]`
- **현상 및 문제점:** 게이트웨이가 알림 수신 직후(처리 완료 전) 즉시 HTTP 200 OK를 반환함. 디바운스 대기 중 프로세스가 재기동될 경우 해당 인시던트 데이터가 소실되나, Zabbix는 이미 성공 응답을 수신했으므로 재전송을 수행하지 않음.
- **개선 방안:** Zabbix 미디어 타입의 기본 재시도 메커니즘(기본 3회, 최대 100회 수신 재시도 스펙)을 활용하도록 파이프라인을 수정함. 수신 알림의 파일 인메모리 기록 성공 시점에 200 OK를 반환하고, 실패 시 에러 응답을 반환하여 Zabbix의 자동 재시도 파이프라인을 유도함. *(소요 공수: 0.5일)*

### 1-1-2. Loki 조회 결과 0건 상태 분류 세분화 ★ `[코드]`
- **현상 및 문제점:** 호스트명과 Loki 라벨 불일치 발생 시 API가 HTTP 200 OK + 빈 리스트(`[]`)를 반환함. 수집기는 이를 정상 조회(`ok`)로 간주하여 LLM에 "로그 상 기록 없음"으로 왜곡 전달함.
- **개선 방안:** 수집 계약 메타데이터(`sources`)에 기존 3종(`ok` / `unavailable` / `disabled`) 외에 **"조회 성공 및 대상 식별 실패 (`unmatched_label` / `not_found`)"** 상태 구분을 추가함. 라벨 불일치 시 봇이 판단을 보류하고 보수적 라우팅을 타도록 게이트 제어를 보완함. *(소요 공수: 0.5일)*

### 1-1-3. 수동 온디맨드 분석 요청 워크플로 신설 ★ `[코드]`
- **현상 및 문제점:** 라우팅 게이트 조건에 의해 스킵(Skip)된 인시던트에 대해 담당 관제 인력이 사후에 수동으로 심층 분석을 호출할 수 있는 경로가 부재함.
- **개선 방안:** Keep UI 내 수동 트리거 버튼을 추가하여, 관제 담당자가 원하는 시점에 즉시 LLM 초동 분석을 재호출할 수 있도록 구현함 (Keep 승인 워크플로 구조 재사용). *(소요 공수: 0.5일)*

### 1-1-4. 단일 관측 소스 환경 내 발동 조건 확장 ★ `[코드]`
- **현상 및 문제점:** 현행 트리아지 발동 조건(`should_triage`)이 교차 상관 분석(다중 소스)을 전제로 설계되어 있어, 단일 Zabbix 알림만 존재하는 인프라 환경에서는 대부분의 알림이 스킵됨.
- **개선 방안:** 단일 소스 환경 수용을 위해 **지식 공백(신규 장애 선판정)** 축을 발동 사유에 추가하여, 처음 발생하는 단일 장애에 대해서도 분석 파이프라인이 구동되도록 제어 로직을 확장함. *(소요 공수: 0.5일)*

### 1-1-5. 프로세스 종료 시 열린 인시던트 강제 마감 (Flush) `[제안]`
- **현상 및 문제점:** 프로세스 재기동 시 디바운스 대기 창에 머물러 있던 오픈 인시던트 데이터가 소실됨.
- **개선 방안:** 프로세스 종료 시그널(SIGTERM) 수신 시 인메모리 버퍼 내 오픈 인시던트를 즉시 마감 및 전송 처리하는 Graceful Shutdown Flush 로직을 추가함.

### 1-1-6. LLM API 호출 동시성 세마포어 한도 적용 `[제안]`
- **현상 및 문제점:** 동시 다발적 인시던트 마감 시 LLM API 병렬 호출 제어가 없어 Rate Limit(429) 및 비용 급증 위험 존재.
- **개선 방안:** 전역 세마포어(Semaphore, N=2~3)를 도입하여 동시 LLM API 호출 수를 제한함.

### 1-1-7. 만성 장애 이력 카운트 정확도 개선 (Limit 200 포화 해소) `[제안]`
- **현상 및 문제점:** 과거 이벤트 조회 API 호출 시 `limit: 200` 제약으로 인해 최근 90일간 200건 이상 발생한 만성 장애의 카운트가 200건으로 포화됨 (G3 결함).
- **개선 방안:** Zabbix API의 `countOutput` 파라미터를 활용해 수량 집계 연산을 분리하거나 Limit 상향을 적용함 (단, `countOutput` 스펙 사전 검증 필요).

### 1-1-8. LLM 프롬프트 내 데이터 절단(Truncation) 상태 명시 `[코드]` `[문서]`
- **현상 및 문제점:** 프롬프트 전달 시 로그/보안 수집 상한(로그 40줄, 보안 20건)을 적용하나, 데이터가 절단되었다는 메타 정보를 LLM에 전달하지 않아 잘못된 결론을 유도함.
- **개선 방안:** 프롬프트 수집 컨텍스트 헤더에 절단 여부 및 전체 발생 건수 메타데이터를 명시적으로 전달함.

### 1-1-9. Zabbix 호스트 목록 기반 가명화 정규식 동적 갱신 `[코드]`
- **현상 및 문제점:** 현행 마스킹 정규식이 랩 명명 규칙(`vm-*`, `node*` 등)으로 고정되어 있어 실환경 호스트명 마스킹 재현율이 미검증 상태임.
- **개선 방안:** Zabbix API를 통해 전체 호스트명 목록을 수집하고, 이를 기반으로 가명화 매핑 테이블을 동적 생성/갱신하도록 파이프라인을 개선함.

### 1-1-10. 만성 장애 선판정 기준의 환경별(사내/MSP) 분리 `[코드]`
- **현상 및 문제점:** 심각도는 사내/MSP를 분리 적용했으나, 만성 장애 선판정 임계치(5회/90일)는 단일 기준으로 적용되어 데이터 분포 왜곡 발생.
- **개선 방안:** 사내 인프라와 MSP 관제 인프라의 알림 발생 밀도 분포에 맞춰 만성 장애 선판정 임계치를 세트별로 분리 정의함.

### 1-1-11. 연쇄 알림 억제 및 정비 창(Maintenance Window) 제어 `[보류]`
- **현상 및 문제점:** 상위 인프라 장애 시 파생되는 하위 서비스 알림 폭증 억제 및 정비 작업 시 알림 침묵 기능 미비.
- **보류 사유:** Zabbix 8.0의 내장 이벤트 처리 엔진(Filter, Auto-close, Grouping) 도입 검토 후 중복 개발 방지를 위해 착수를 보류함.

## 1-2. Wazuh 보안 축

### 1-2-1. Wazuh 보안 알림 대상 만성/신규 선판정 구현 `[코드]`
- **현상 및 문제점:** Wazuh 보안 알림은 Zabbix 트리거 ID가 없어 과거 이력 선판정이 전량 "미상(Unknown)"으로 처리됨 ([`rules-inventory.md §1-6`](../02-design/rules-inventory.md) 명시 한계).
- **개선 방안:** Wazuh Indexer를 대상으로 `rule.id` + `agent.name` 기준 과거 90일 발생 이력을 집계하는 선판정 파이프라인을 구현함.

### 1-2-2. FIM(파일 무결성 검사) 감시 타임라인 정밀도 향상 `[문서]`
- **현상 및 문제점:** FIM 기본 스캔 주기가 12시간(`frequency: 43200`)으로 설정되어 있어, 실시간 실증 분석을 위한 시간 정밀도가 미달함.
- **개선 방안:** 주요 보안 설정 경로(`/etc/ssh`, `/etc/passwd` 등)에 대해 Inotify 기반 `realtime` 및 `whodata`(변경 주체 추적) 옵션을 선별 적용함.

### 1-2-3. 보안 및 로그 관측 축 간 원본 수집 경로 일원화 `[코드]`
- **현상 및 문제점:** Wazuh는 `/var/log/secure` 파일을 직접 참조하고 Alloy는 `systemd-journald`를 참조하여 관측 축 간 수집 데이터 불일치 발생 가능성 존재.
- **개선 방안:** Wazuh 에이전트 로그 수집 소스를 `journald` 방식으로 일원화함.

### 1-2-4. Wazuh Integrator 전송 실패 시 재시도 파이프라인 보완 `[코드]`
- **현상 및 문제점:** Wazuh Manager 연동 스크립트 실행 실패 시 재시도 없이 단순 예외 종료되어 전송 유실 발생.
- **개선 방안:** 연동 스크립트 내 로컬 큐(Queue) 및 재시도(Retry) 로직을 추가하여 네트워크 일시 장애 시 알림 유실을 방지함.

## 1-3. Loki 로그 축

### 1-3-1. Loki Compactor 기반 데이터 보존(Retention) 정책 설정 `[문서]`
- **현상 및 문제점:** Loki 기본 보존 정책 미설정(`0s`)으로 인해 수집된 로그가 영구 누적되어 스토리지 포화 위험 존재.
- **개선 방안:** Loki `compactor` 및 `limits_config` 내 보존 기간(`retention_period`) 및 스트림별 차등 보존 정책(`retention_stream`)을 정의함.

### 1-3-2. Loki Stream 및 유입량 상한(Limits Config) 제어 `[코드]`
- **현상 및 문제점:** 특정 호스트의 로그 폭증 시 시스템 보호를 위한 유입량 제한(Rate Limit) 설정 미비.
- **개선 방안:** `limits_config` 내 초당 유입량, 스트림 수 및 라벨 카디널리티 제한 설정을 강화함.

### 1-3-3. Loki Reverse Proxy 인증 계층 탑재 `[문서]`
- **현상 및 문제점:** Loki 3100 포트가 별도 인증 없이 노출되어 비인가 접근 및 주입 위험 존재.
- **개선 방안:** Nginx/Envoy 기반 Reverse Proxy를 전면에 배치하여 Basic Auth 및 IP 접근 제어 계층을 구성함.

# 2. 고도화 과제 (Enhancement) — 신규 기능 및 분석 정밀도 확장

## 2-1. 기반 구조 (Core Infrastructure)

### 2-1-1. 판정 및 분석 이력 전용 저장소 구축 `[코드]` `[제안]`
- **목적:** 게이트웨이가 수행한 판단 결과(병합, 선판정, 조회 상태, LLM 분석, 조치 결과)를 정형화하여 보관할 내부 RDB/SQLite 저장소를 신설함.
- **기술적 의의:** Keep 데이터에 문자열 형태 의존을 탈피하여 데이터 정합성을 보장하고, 원본 텔레메트리 데이터 복제 없이 분석 메타데이터만 효율적으로 보관함.

### 2-1-2. 텔레메트리 수집 데이터 표준화 스키마 적용 `[코드]` `[제안]`
- **목적:** 3개 관측 소스의 상이한 수집 데이터 구조를 표준 스키마(시각, 심각도, 메시지, 대상 FQDN)로 정규화하는 어댑터 레이어를 도입함.
- **기술적 의의:** 수집 소스 추가에 따른 LLM 프롬프트 변경 공수를 제거하고 파이프라인 결합도를 낮춤. (G4 호스트명 정규화 과제 포함)

### 2-1-3. 외부 LLM 전송 경로의 단일 Egress Proxy 일원화 `[코드]` `[제안]`
- **목적:** 봇 파이프라인 및 HolmesGPT 등 모든 외부 LLM 호출 트래픽이 마스킹 이그레스 프록시(LiteLLM)를 통과하도록 단일화함.
- **기술적 의의:** 토큰 사용량 통합 집계, 비용 통제 및 데이터 외부 반출 통제를 아키텍처 수준에서 강제함.

### 2-1-4. 배포 및 도입 표준 패키징 구성 `[제안]`
- **목적:** Docker Compose 및 Ansible Role 기반으로 게이트웨이 파이프라인의 단일 명령 설치/갱신 패키지를 구현함.
- **주요 포함 항목:** 관제망 통신 요건 명세서, 환경변수 파일 단일화, 롤백 절차 및 Read-only 검증 스크립트 제공.

## 2-2. 감시 사각지대 해소 (Observability Gap)

### 2-2-1. 관측 파이프라인 신호 부재 (Heartbeat Drop) 감지 ★ `[제안]`
- **목적:** 관측 에이전트 중단 또는 알림 통로 실패로 인한 "조용한 유실" 상태를 감지하는 헬스체크 파이프라인을 구축함.
- **구현 방식:** 사내 Zabbix와 MSP Zabbix 간 상호 주기적 Trapper 하트비트 신호를 전송하고 `nodata()` 트리거로 수집 중단을 즉시 탐지함. *(소요 공수: 1일)*

### 2-2-2. 무효/상수 신호 (Stale Data) 감지 로직 탑재 `[제안]`
- **목적:** 수집 데이터값 변화가 없거나(상수 고정) 임계치에 도달하지 않는 무효 트리거 규칙을 자동 식별함.
- **구현 방식:** Zabbix `history.get` 데이터를 분석하여 일정 기간 표준편차 0인 아이템 및 미발화 트리거 항목을 추출하여 모니터링 정비 리포트를 산출함.

### 2-2-3. 게이트웨이 파이프라인 자체 상태 지표화 `[코드]` `[제안]`

# 3. 랩 검증 대기 과제 (Lab Verification Backlog)

구현 완료된 소스 코드에 대한 실험 인프라 환경 검증 작업입니다.

- **TLS/SSL 인증서 만료 감시 랩 검증:** Zabbix Agent2 기반 웹사이트 인증서 모니터링 템플릿 및 Grafana 패널 동작 검증
- **Wazuh 매니저 측 추가 룰 적용 및 검증:** FIM 무결성 예외 처리 룰, SCA 회귀(통과➔실패) 승격 룰 적용 및 Indexer 레플리카(Replica=1) 설정 변경을 통한 고가용성 검증
- **데모 A 드릴다운 다중 호스트 환경 강화:** 복수 노드 환경에서 FQDN 기반 드릴다운 필터링 시각 효과 검증
- **Ollama 온프레미스 폴백 성능 실측:** Cold/Warm Start 응답 지연 시간 정량 측정 (예산 초과 시 온프렘 사양 상향 필요성을 로드맵에 기재)
- **LLM 모델(Opus vs Sonnet) 정량 평가:** 모델별 지연 시간, API 소모 비용, 분석 품질 트레이드오프 실측

- **알림 임계치 및 의존성 정비:** 발행 측 Zabbix 트리거 심각도 및 의존성 관계 재설계를 통해 원천 노이즈 축소

# 5. 명시적 제외 및 보류 범위 (Out of Scope)

의도적 아키텍처 판단에 의해 개발 범위에서 제외(Inactivation) 처리된 항목입니다.

| 제외 항목 | 제외 및 보류 사유 |
|---|---|
| **규칙 없는 자율 이상 탐지** | LLM 환각 및 오탐 위험이 '코드 기반 결정론적 선판정' 원칙과 충돌함 |
| **별도 GUI 워크플로 엔진 추가 (n8n 등)** | Keep 내장 승인 제어 워크플로 재사용을 통해 요구사항을 이미 충족함 |
| **Suricata 랩 직접 구축** | 관측 사각지대 분석을 통해 네이티브 관측 활성화라는 고효율 대안을 선순위로 정의함 |
| **Active Response 및 외부 해시 연동** | Active Response 는 위탁 계약상 임의 조치가 금지된 자산이 존재하여 제외. 외부 해시 연동은 데이터 외부 반출 통제 원칙에 위배됨 |
| **컨테이너 및 클라우드 커넥터 확장** | 현재 관측 대상 인프라(온프레미스 VM 및 물리 서버) 범위를 준수함 |
| **진행 중 인시던트 데이터 지속화** | 검증된 타이밍 로직 영향 최소화를 위해 프로세스 종료 시 마감(Flush) 처리로 대체함 *(완료된 분석 이력 저장소 구축과는 별개 항목)* |
| **Keep AI 상관 분석 도입** `[문서]` | Keep Cloud 및 Enterprise On-Premises 전용 기능으로 **오픈소스 배포판에서는 제공되지 않음** ([docs.keephq.dev/overview/ai-correlation](https://docs.keephq.dev/overview/ai-correlation)) |
| **OpenSearch Anomaly Detection 플러그인** `[문서]` | Wazuh 가 **완전한 통합을 구현하지 않아 기본 비활성** 상태로 배포함. 수동 설치는 가능하나 공식 통합이 아니므로 버전 변경 시 파손 위험이 남음 |
| **Aurora (Arvo AI) 솔루션 직접 도입** `[문서]` | **조사 대상이 퍼블릭 클라우드(AWS·Azure·GCP)와 Kubernetes 중심이고 통합 목록에 Zabbix 가 없음** — 우리 스택의 주 수집원을 읽지 못한다. *(온프레미스 배포 자체는 가능하다 — Docker Compose 자체 호스팅과 에어갭 번들을 지원한다. 제외 사유는 배포 방식이 아니라 조사 대상 범위다.)* |

---

# 6. 미확인 및 의존성 항목 (Unverified Dependencies)

외부 회신 및 사양 검증이 필요한 항목입니다.

- 관측 인프라망에서 외부 LLM API 서비스로의 Outbound Egress 통신 허용 여부
- Zabbix 8.0 이벤트 처리 엔진 내 제공 예정 Operations 세부 기능 목록
- Zabbix API `countOutput` 파라미터 연산 가용성 검증
- Wazuh Integrator 데몬의 자체 재시도 및 메시지 큐 동작 스펙
- Keep Self-hosted 환경 내 워크플로 생성 수량 제한 여부 (Cloud 버전 기준 5개 제한)
- Grafana 사내 전용 플러그인 개발 시 서명(Signature) 요건 및 Proxy Route 가용 여부

# 구조적 함정 및 한계점 — 조용히 발생하는 오류 유형 (Silent Failures)

본 디렉토리는 시스템상 정상 동작처럼 보이나 실제로는 논리적/구조적 오류를 내포한 사례들을 수집한 공간입니다. 명시적인 에러(Crash)를 동반하는 문제는 쉽게 인지하여 조치할 수 있지만, 이곳에서 다루는 항목들은 인지가 지연되어 조용히 시스템의 신뢰성을 훼손하는 은밀한 함정(Pitfalls)들입니다.

## 1. 식별된 오류의 3가지 주요 유형

본 프로젝트에서 식별된 함정들은 크게 3가지 성격으로 분류됩니다. 신규 장애 현상을 마주할 경우 아래 유형 중 어디에 속하는지 우선 판단합니다.

**① 설정은 정확하나 화면 표시만 누락/왜곡된 경우 (Visual & Caching Issues)**
가장 많은 트러블슈팅 시간을 소모하게 만드는 유형입니다. 원인을 백엔드 코드나 데이터 수집단에서 찾으려 하지만 실제 원인은 관측 뷰(View) 층에 존재합니다.
*(예: Grafana Zabbix 데이터소스의 조회 캐시 기본값이 1시간으로 설정되어 있어, 지표가 정지된 것처럼 보인 사례가 두 차례 발생했으며 두 경우 모두 데이터 수집 장애로 오인되었습니다.)*

**② 실패가 성공으로 위장되는 경우 (False Positives / False Negatives)**
시스템 신뢰성에 가장 치명적인 영향을 미치는 유형입니다. 데이터 조회에 실패했음에도 빈 값을 반환하여 "정상적인 신호 없음" 상태로 오인하게 만듭니다 ([`structural-gaps.md`](structural-gaps.md) G1 항목 참조).
데이터 산출 실패 시 빈 값을 그대로 전송하면, 고객 리포트 문서에 과거 집계 수치가 그대로 이월 표기되는 데이터 오염이 발생합니다. **수치 0(Zero), 데이터 없음(None), 조회 실패(Error)는 기술적으로 명확히 다른 상태이며, 이를 엄격하게 구별 처리하지 않으면 시스템이 거짓 데이터를 생성하게 됩니다.**

**③ 공식 문서 예시의 맹신에 따른 재현 오류 (Blind Copy-Paste)**
공식 문서의 예시 설정값이 현재 인프라 환경과 충돌하여 사고를 유발하는 경우입니다.
*(예: 로그 파일 권한 예시값을 환경 검증 없이 적용하여, 로그 수집기 데몬이 파일 접근 권한을 상실한 사례)*
**공식 문서의 예시는 참조용일 뿐 특정 인프라 환경의 권장 기본값이 아님을 인지해야 합니다.**

## 2. 신규 함정 기록 규약

새로운 함정 발견 시 아래의 작성 규약을 준수하여 문서화합니다.

- **현상(Symptom) ➔ 원인(Root Cause) ➔ 검증/해결 방법(Resolution)** 순서로 작성합니다. 문제 발생 시 작업자의 1차 검색어는 '현상'이므로 현상을 최우선으로 기재합니다.
- **원인 파악이 어려웠던 이유(Why it was hard to find)**를 반드시 1줄 이상 기재합니다. 이 기록이 후속 작업자에게 가장 가치 있는 정보 자산이 됩니다.
- 명확한 출처 관리를 위해 근거 표기(`[문서]`/`[코드]`/`[제안]`) 규약을 준수합니다 (참조: [`../02-design/evidence-policy.md`](../02-design/evidence-policy.md)).

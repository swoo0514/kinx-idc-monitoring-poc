## 세 가지 유형

이 리포에서 발견한 함정은 성격이 셋으로 갈립니다. 새 함정을 만나면 어디에 속하는지 먼저
봅니다.

**① 설정은 맞는데 화면만 틀린 것**
가장 시간을 많이 잡아먹습니다. 원인을 코드에서 찾게 되는데 원인이 코드에 없습니다.
Grafana 조회 캐시가 1시간이라 값이 멈춰 보인 사고가 **두 번** 있었고, 두 번 다 처음에는
수집이 죽은 줄 알았습니다.

**② 실패가 성공처럼 보이는 것**
가장 위험합니다. 조회에 실패했는데 빈 값을 돌려주면 "신호가 없다"로 읽힙니다
([G1](structural-gaps.md#g1-조용한-열화가-거짓-안심으로-바뀐다--️-해결됨)).
값을 안 보내면 지난 집계의 숫자가 그대로 남아 고객 문서에 틀린 값이 실립니다.
**0과 "없음"과 "실패"는 서로 다른 값이고, 그 셋을 구분하지 않으면 조용히 거짓말을 합니다.**

**③ 문서를 그대로 베끼면 재현되는 것**
공식 문서의 예시값이 우리 상황에서는 사고를 만드는 경우입니다. 로그 파일 권한 예시를 그대로
쓰면 수집기가 파일을 못 읽습니다. **예시는 예시일 뿐 기본값이 아닙니다.**

## 함정을 만나면 여기에 적는 방법

- **증상 → 원인 → 확인 방법** 순서로 씁니다. 증상이 검색어가 되기 때문에 증상이 먼저입니다.
- **왜 찾기 어려웠는지**를 한 줄 적습니다. 그것이 다음 사람에게 가장 값집니다.
- 근거 표기(`[문서]`/`[코드]`/`[제안]`)를 붙입니다 —
  [`../02-design/evidence-policy.md`](../02-design/evidence-policy.md).

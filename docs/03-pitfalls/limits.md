# 봇의 한계 및 경계 — 기술적 제약 사항 및 관측 범위 명세

본 문서는 게이트웨이 파이프라인 및 분석 봇 엔진의 **기술적 한계점(Limitations)과 관측 수용 범위(Boundaries)**를 명확히 정의합니다. 명시된 제약 사항은 실제 랩 시뮬레이션 및 실증 과정에서 확인된 사실에 기반합니다.

---

## 1. 주요 기술적 한계점 (Limitations)

1. **수집 컨텍스트 제약 (Context Window Limit):** 토큰 소모 및 30초 처리 지연 시간(Latency) 예산을 준수하기 위해, 최근 시간 창 및 건수 상한(로그 최대 40줄/300자, 최근 15분 창) 데이터만 수집합니다. 해당 수집 범위를 벗어난 시점의 데이터는 근본 원인 분석에 반영되지 않습니다.
2. **사전 정의 연관 관계 기반 알림 병합 (Rule-based Incident Merging):** 환각 방지를 위해 `BRIDGE_GROUPS`에 명시된 인과 연관 조합만을 단일 사건으로 병합합니다. 실제로 상관관계가 존재하더라도 사전 정의 규칙에 포함되지 않은 유형 간 알림은 독립된 인시던트로 분리되어 처리됩니다.
3. **설명 생성 시 환각 가능성 (Hallucination Risk in Interpretation):** 알림 병합 및 만성/신규 장애 선판정은 코드 로직으로 결정하지만, LLM이 생성하는 인과관계 '설명(Interpretation)' 문장은 데이터 오독이나 과신 가능성이 존재합니다. (이로 인해 실제 자동 조치 실행 시 명시적인 사용자 승인을 거치도록 설계되었습니다.)
4. **심각도 컷오프 게이트 의존성 (Severity Gate Dependency):** `SEV1` / `SEV2` 등급 항목에 한해서만 초동 분석(Triage)을 실행합니다. 실제 주요 장애 발생 시 원본 심각도 설정이 낮게 평가되어 있을 경우 분석 대상에서 누락될 수 있습니다. (심각도 설정의 정확도가 분석 봇의 관측 유효성을 결정합니다.)
5. **LLM API 의존성 및 응답 지연 (API Latency & Dependency):** 외부 LLM API 호출 지연 또는 서비스 장애 발생 시 열화(Degraded) 모드로 전환되어 원인 분석 문장이 누락됩니다. 수집 컨텍스트 크기 증가 시 30초 처리 예산을 초과할 위험이 존재합니다.
6. **운영 가용성 및 메모리 버퍼 한계 (In-memory State Limitations):** 단일 프로세스 기반으로 동작하며, 멱등성 매핑 키 및 인시던트 디바운스 버퍼가 메모리(In-memory) 상에 유지됩니다. 게이트웨이 재시작 시 진행 중이던 알림 병합 상태가 초기화됩니다. (고가용성 HA 및 외부 분산 스토리지 미적용)
7. **수집 데이터 품질 및 정합성 의존성 (Data Quality Dependency):** 호스트명 불일치, 라벨링 오류, API 조회 권한 미비 시 수집 데이터가 누락되어 분석 정확도가 저하됩니다. (FQDN 정규화 및 Zabbix/Grafana 권한 설정 필수)
8. **수동 자문 역할에 한정 (No Unsanctioned Execution):** 설계상 시스템 변경 조치를 직접 수행하지 않으며 분석 정보 제공 및 추천 플레이북 제시 역할에 국한됩니다. 자동 조치는 승인 워크플로(Keep + Ansible)를 거치는 경우에만 실행됩니다. (운영 제약 조건 반영)

## 2. 감시 대상 VM 로그 수집 및 분석 범위 (Agent Boundary)

**"에이전트 배포 VM의 모든 로그를 자동 분석하는가?"에 대한 기술적 구분:**

- **시스템 로그 (기본 수집):** Alloy 에이전트가 `systemd-journald`를 조회하여 시스템 로그(`syslog`, `sshd`, `sudo`, `logger` 등)를 Loki로 자동 수집합니다.
- **애플리케이션 파일 로그 (추가 설정 필요):** 개별 애플리케이션이 파일 형태로 출력하는 로그(`/var/log/app/*.log` 등)는 systemd 저널에 포함되지 않으므로, Alloy 수집 파일 경로(`targets`)에 해당 경로를 명시해야 수집됩니다. (자동 파일 스캔 미지원)
- **분석 입력 범위:** 수집된 로그 전체를 분석하는 것이 아니라, 정의된 시간 창 및 건수 상한(최근 15분 창, 최대 40줄) 내의 로그 슬라이스만 LLM 분석 입력으로 전달합니다.

*요약:* **"에이전트에 명시적으로 지정된 로그만 수집되며, 애플리케이션 파일 로그는 별도 설정이 필요하고, 분석 봇은 수집 데이터 중 최근 관련 슬라이스만 선별하여 분석합니다."**

---

## 3. 향후 고도화 추진 과제

- **인시던트 연관 로그 선별 수집 (Log Relevance Filtering):** 복수 알림 동시 발생 시 단순 최근 N줄 추출 방식 대신, 인시던트 유형 및 핵심 키워드와 연관성이 높은 로그만 추출하여 프롬프트에 주입하는 방식을 적용합니다. (수집 컨텍스트 제약 개선)
    - *추진 방안:* 인시던트 클래스별 키워드 필터링 매칭 또는 임베딩 기반 유사도 랭킹 적용
    - *핵심 목표:* 노이즈 로그 데이터로부터 유의미한 분석 신호 로그 선별 수집

## 4. 제약 사항의 성격별 분류 (의도적 설계 vs 기술적 한계)

명시된 제약 사항 중 일부는 기술적 미비가 아닌 **의도적 아키텍처 설계 판단(Intentional Design Decision)**에 해당합니다.

| 제약 사항 | 구분 | 결정 사유 및 판단 근거 |
|---|---|---|
| **사전 정의 조합 병합 (#1-2)** | **의도적 설계** | 규칙 기반이 아닌 LLM 자율 상관 분석 적용 시 환각이 판정 로직에 개입하는 문제 방지 (판단은 코드, 설명은 LLM 원칙 준수) |
| **자동 조치 미실행 (#1-8)** | **의도적 설계** | MSP 계약 제약상 임의 자동 조치가 불가능한 관측 대상 존재 (`scope=notify_only` 라우팅 제어 적용) |
| **열화 모드 제공 (#1-5)** | **의도적 설계** | LLM API 호출 전면 실패 시에도 시스템이 정지하지 않고 코드 기반 선판정 결과를 유지 회신하도록 안전 장치 적용 |
| **인메모리 상태 유지 (#1-6)** | **미구현 과제** | PoC 검증 범위에 따른 우선순위 조정 결과 (향후 외부 분산 스토리지 적용 로드맵 과제) |
| **컨텍스트 수집 상한 (#1-1)** | **트레이드오프** | 30초 이내 응답 지연 시간(Latency) 예산 준수를 위한 리소스 타협 (연관성 기반 필터링을 통해 개선 예정) |

# 구조 갭 카탈로그 — 조용히 틀리는 것들

개선 목록을 만든 뒤, **그 목록 자체에 빠진 것이 없는지 게이트웨이 코드를 전수로 다시 읽어**
찾아낸 갭들입니다. 전부 파일·라인으로 확인했고, 분류기 오분류는 실제로 실행해 출력을
확인했습니다(추정 아님).

각 항목은 **문제 → 근거 → 해결 → 왜 중요한가** 순서입니다. 근거 표기는
[`../02-design/evidence-policy.md`](../02-design/evidence-policy.md).

> **공통 성격: 여기 있는 것들은 에러를 내지 않습니다.** 전부 정상처럼 보이면서 틀립니다.
> 그래서 코드를 읽지 않으면 발견되지 않고, 발견하는 것 자체가 산출물입니다.

---

## G1. 조용한 열화가 "거짓 안심"으로 바뀐다 — ✅ 해결됨

**이 점검의 최대 수확입니다.**

- **문제** — 수집기가 Loki·Wazuh 조회 실패를 예외 삼킴으로 처리하고 빈 리스트를 돌려줬습니다.
  그래서 **"신호가 없다"와 "조회에 실패했다"가 코드상 구분 불가능**했습니다.
- **근거 `[코드]`** — `collector.py`의 로그·보안 조회가 모두 `except Exception: return []`.
  상태 필드가 없었습니다.
- **파급이 두 갈래로 번졌습니다**:
  1. **LLM 프롬프트가 빈 값을 긍정으로 해석하라고 명시 지시했습니다** — "security가 비어
     있으면 '침해·비인가 변경 흔적 없음'으로 해석하라". 즉 **Wazuh 인덱서가 죽어 있으면 봇이
     침해를 배제했다고 단언**합니다. 데모 C의 핵심 장면이 "Wazuh 정상 → 침해 배제"라
     정확히 그 장면이 무너집니다.
  2. **발동 게이트도 같은 빈 값으로 판단했습니다** — 관측 백엔드가 죽으면 교차 신호가 0으로
     보여 **봇이 조용해집니다. 가장 필요한 순간에 침묵합니다.**
- **해결 `[코드]`** — 조회 상태 3종(`ok` / `unavailable` / `disabled`) 계약을 도입하고
  수집기·프롬프트·게이트·Slack 카드·폴백에 전파했습니다. 자료형은 건드리지 않고 `sources`
  필드를 옆에 붙이는 **가산 변경**이라 검증된 e2e는 그대로입니다. **프롬프트가 상태를 안 보는
  형태로 되돌아가면 실패하는 검사**를 셀프테스트에 넣어 회귀를 잠갔습니다.
- **랩 실측** — Wazuh 클러스터는 건드리지 않고 게이트웨이의 인덱서 주소만 닫힌 포트로 돌려
  조회 실패를 강제했습니다(실제 장애와 같은 예외 분기). 실 이벤트 1건 투입 결과 세 층이
  모두 확인됐습니다.
  1. 수집기가 실패를 삼키지 않고 기록 → `sources={'logs':'ok','security':'unavailable'}`
  2. 게이트가 `교차 소스 조회 실패(security) — 신호 없음이 아니라 미상, 보수적 발동`
  3. 카드에 경고 배지가 붙고, 본문이 **한 축은 근거로 쓰고 다른 축은 미상으로 구분해 진술**

  **대조군까지 확보했습니다.** 인덱서 주소를 원복하고 같은 이벤트를 재투입했더니, 변경한
  변수는 Wazuh 도달 가능성 하나뿐인데 결론이 갈렸습니다.

  | | `security: unavailable` | `security: ok` |
  |---|---|---|
  | 카드 배지 | ⚠️ 조회 실패: 보안(Wazuh) | 없음 |
  | 보안 축 진술 | "침해 여부 미상 — **조회 실패를 근거로 안심할 수 없음**" | "침해·비인가 변경 흔적 없음 → 순수 운영 이슈" |
  | 자동 조치 판단 | "부적합(원인 미상 + 보안 미상)" | "조회성 명령만 자동화 가능" |

  봇이 본문에 **상태를 직접 인용**했습니다 — 빈 값을 근거로 쓸 수 있는지를 상태로 판단하고,
  그 판단이 조치 권고까지 갈랐다는 증거입니다.

- **왜 중요한가** — 봇이 틀리는 것보다 **틀린 줄 모르고 자신 있게 틀리는 것**이 도입 심사에서
  치명적입니다. Slack 배지 문구에서 이 위험을 한 번 언급한 적은 있었지만, **정작 프롬프트와
  게이트에 같은 결함이 있다는 것은 개선 목록에 없었습니다.**

## G2. 분류기 오분류 — 병합의 전제가 흔들린다 — ✅ 대부분 해결됨

- **문제** — `classify()`는 키워드 우선순위 규칙인데, 우선순위와 키워드 선택 때문에 흔한
  트리거 이름이 엉뚱한 유형으로 갑니다. **분류가 틀리면 병합 키가 갈리므로 병합도 브리지도
  발화하지 않습니다.**
- **근거 `[코드]` — 실제 실행 결과**:

  | 알림명 | 실제 분류 | 기대 |
  |---|---|---|
  | `Linux: SSH service is down` | `auth_security` | `service_down` |
  | `메모리 사용률 95% 초과` | `disk_space` | (메모리 유형 부재) |
  | `Linux: High memory utilization` | `other` | (메모리 유형 부재) |
  | `Zabbix agent is not available` | `other` | `service_down` 계열 |

  원인은 셋입니다. ① `auth_security`의 키워드 `"ssh"`가 `service_down`보다 앞줄이라 SSH
  **서비스 장애**를 보안 사건으로 오인 ② `disk_space`의 키워드 `"사용률"`이 지나치게 넓어
  디스크가 아닌 사용률 알림을 흡수 ③ **메모리 유형이 아예 없음** — 표준 Linux 템플릿의 메모리
  트리거가 `other`로 떨어져 어떤 브리지에도 못 낍니다.
- **해결 `[코드]`** — 키워드를 좁히고(`ssh`→`sshd`, `사용률`→`디스크 사용률`)
  `memory_pressure` 유형을 신설했으며, `network`를 `service_down` 앞으로 옮겨 "Link down"
  오분류를 없앴습니다. **짧은 ASCII 토큰(5자 이하)은 단어 경계 매칭**으로 바꿔
  `fim`↔confirm, `oom`↔room, `down`↔shutdown 같은 부분 일치를 차단했습니다.
  셀프테스트 분류 케이스를 4 → 23으로 확대했습니다.
- **남은 것 `[제안]`** — `classify(alert_name, item_key)`는 item_key를 받도록 설계됐지만
  **호출부가 이름만 넘깁니다.** 아이템 키(`vfs.fs.size[...]`·`system.cpu.util`)는 이름보다
  훨씬 안정적인 분류 근거인데 쓰이지 않고 있습니다. 웹훅 페이로드에 item key가 없어
  **미디어타입 파라미터 추가와 랩 재배선이 함께 필요**합니다.
- **왜 중요한가** — 브리지 룰을 추가하는 작업은 이 교정 **뒤에** 해야 합니다. 교정 전에
  브리지를 넣으면 `SSH service is down`이 `auth_security`로 빠져 **데모 B 시나리오의 병합이
  조용히 실패합니다.**

## G3. 만성 판정 횟수가 200에서 잘린다 — 실환경에서 바로 걸린다

- **문제** — 선판정용 과거 이벤트 조회에 `limit: 200`이 걸려 있습니다. 90일 창에 200건이 넘는
  트리거는 **횟수가 200으로 포화**됩니다.
- **근거 `[코드]`** — `collector.py`의 `event.get`(`sortorder: DESC`, `limit: 200`).
  실환경은 상위 2개 트리거가 전체 이벤트의 78.6%를 만드는 분포라, 90일 창이면 상위 트리거는
  전부 200으로 포화됩니다.
- **판정 자체는 안전합니다(정직하게)** — 200 ≥ 만성 기준(5)이므로 verdict는 여전히 "만성"입니다.
  깨지는 것은 **횟수의 정확도**입니다.
- **파급 `[제안]`** — "만성으로 판정된 것 중 반복 최다 유형을 랭킹해 자동화 후보로 삼는다"는
  구상이 이 숫자에 의존합니다. **상위 트리거가 전부 200 동률이면 랭킹이 성립하지 않습니다.**
  즉 그 산출물이 조용히 무의미해집니다.
- **해결 `[제안]`** — `countOutput`으로 개수만 별도로 정확히 세거나(샘플 200건은 최근성
  판단용으로 유지), limit을 창 규모에 맞춰 올립니다. 어느 쪽이든 응답 크기·타임아웃 영향을
  실측한 뒤 정합니다. **`countOutput` 동작은 공식 문서 확인 필요(현재 미확인).**

## G4. "3소스"는 수집 3소스이지 병합 3소스가 아니다

**서술 정확도 문제입니다. 말을 잘못하면 그 자체가 결함이 됩니다.**

- **문제** — 병합 키가 **원문 호스트 문자열**을 그대로 씁니다. 호스트명 정규화는 수집 단계에만
  적용되고 병합 키에는 적용되지 않습니다.
- **근거 `[코드]`** — `incident_key(host, cls)`가 호스트 문자열을 가공하지 않습니다.
  `HOST_LABEL_MAP` 파싱은 `collector.py`에만 있고 `incident.py`에는 없습니다.
  Zabbix 알림의 host는 웹훅 매크로 값이고 Wazuh 알림의 host는 `agent_name`이라,
  **이름이 다르면 같은 물리 호스트여도 영원히 별개 인시던트**입니다.
- **부분 해소** — "Wazuh 웹훅 미배선"은 해결됐습니다. 매니저에 게이트웨이 연동을 배선해
  **Wazuh는 이제 사건을 시작하고 사건에 묶일 수 있습니다.** 남은 것은 병합 키 정규화입니다.
- **Loki는 여전히 병합 참여자가 아니고, 그것은 결함이 아니라 구조입니다.** 게이트웨이 웹훅은
  Zabbix·Wazuh 둘뿐이고 소스 상수도 셋뿐이라 Loki는 알림을 만들 수 없습니다.
  **로그는 발화하지 않기 때문입니다 — 판정은 트리거가 하고 로그는 근거를 댑니다.**
  로그를 판정 주체로 올리려면 Loki Ruler / Grafana Alerting이 필요하고, 그때는 심각도 매핑표에
  Loki 행을 먼저 만들어야 합니다.
- **정확한 문장** — *"두 소스가 사건을 만들고, 세 소스가 사건을 설명한다."*
- **완화되어 있는 부분** — Ansible로 배포한 호스트는 세 에이전트에 같은 FQDN을 심으므로 이름이
  일치합니다. 문제는 **손으로 설치한 호스트뿐**입니다. 따라서 이 갭은 결함이라기보다
  **FQDN 정규화가 왜 필수인지의 추가 증거**로 쓰는 편이 옳습니다.
- **해결 `[제안]`** — **게이트웨이 입구에서 호스트명을 한 번 정규화**해 이후 전 경로가 같은
  이름을 쓰게 합니다. 수집·병합·Keep fingerprint를 한꺼번에 정합시킵니다.

## G5. 게이트에서 걸린 알림은 저장소에도 안 남는다 — ✅ 해결됨

- **문제** — 게이트가 스킵을 반환하면 즉시 return이라 Slack 카드도, **Keep 저장도 없었습니다.**
- **왜 문제인가** — 통보 관점에서는 "원 알림은 팀 기존 경로로 보이니 사라지는 게 아니다"가
  맞습니다. 그러나 **Keep을 알림 저장소로 쓴다는 전제와 충돌합니다.** 게이트에 걸리는 것은
  정의상 "단일 축 + 교차 신호 없음"인데, 이는 **만성 노이즈 알림의 전형**입니다.
  즉 **랭킹하려는 바로 그 대상이 저장소에 안 들어갑니다.**
- **해결 `[코드]`** — 게이트 스킵 시에도 분석 없이 **판정·유형·알림 수만** 실어 Keep에 보냅니다.
  LLM을 안 부르는 것이 게이트의 목적이고 저장은 LLM과 무관하므로 **비용은 0**입니다.
  fingerprint를 사건 지문으로 고정해, 같은 사건이 나중에 분석까지 가면 같은 행에 모입니다.
  덤으로 **"봇이 판단해서 조용히 넘겼다"는 기록**이 남아 게이트 자체의 정당성을 사후 검증할
  수 있습니다.

## G6 · G9. 심층조사가 "이미 아는 문제"에서만 돈다 — ✅ 해결됨

**제기된 질문이 정확했습니다** — *"브리지 룰은 결국 사람이 모니터링하다가 '이 문제들
연관돼 있네' 하고 알아채서 넣는 것이다. 그런데 심층조사가 병합에 걸려 있다면, 결국
이유가 이미 밝혀진 문제만 깊이 분석하는 것 아닌가?"*

- **사실 확인 `[코드]`** — 절반은 맞습니다. `merged`는 "알림 2건 이상"이라 같은 유형 반복은
  룰 없이도 병합됩니다. 그러나 **서로 다른 유형의 교차 상관은 손으로 넣은 조합에서만**
  일어나고, 그 경로가 심층조사의 주 발동 조건이었습니다. 즉 **가장 비싼 분석의 발동 조건이
  사람의 사전 지식에 묶여 있었습니다.**
- **다만 룰이 담는 것은 원인이 아닙니다 `[문서]`** — 브리지 룰은 "이 둘은 같이 볼 가치가
  있다"는 **의심**만 담습니다. 실제 인과는 매번 다르고 그것이 LLM의 몫입니다. 근거는
  심층조사 벤치마크 — 룰에 없던 백업 I/O 경합, 슬레이브 SQL 스레드의 대량 DELETE,
  장치 사용률 포화, lag 0 시점의 iowait 붕괴로 인과를 증명했습니다.
  따라서 정확한 서술은 **"같이 볼 후보는 사람이 정하고, 이번엔 왜 그랬는지는 AI가 판정한다"**
  입니다.
- **해결 `[코드]` — 발동 기준을 뒤집었습니다.** 지금까지는 **지식이 있는 곳**에서 조사가
  돌았습니다. 반대로 **지식이 없는 곳**에 배분합니다. 선판정이 이미 신규/재발/만성을 결정적으로
  판정하므로 새 지능이 필요 없습니다.
  - 만성(아는 문제) → **억제** (비용·소음 절감)
  - 신규(처음 보는 문제) → **발동** (정보 이득 최대)
  - 위중(SEV1)과 봇 열화는 **지식 여부와 무관**하므로 만성 억제보다 앞
- **구조적 해결은 별개 `[제안]`** — 위는 발동 배분만 고칩니다. 순환 자체 — "사람이 알아챈
  조합만 룰이 된다" — 를 끊는 것은 **co-occurrence → 브리지 룰 후보 제안**입니다.
  **데이터가 제안하고 사람이 확정하면 룰의 출처가 사람에서 관측으로 바뀝니다.**

## G7. 동시 인시던트 마감 시 LLM 호출이 무제한 병렬이다

- **문제** — 여러 인시던트의 디바운스 창이 동시에 닫히면 각각 LLM을 부릅니다.
  **동시성 상한이 없습니다.**
- **근거 `[코드]`** — 호출 수를 제한하는 코드가 없습니다. `max_alerts`는 인시던트 **내부**
  알림 수만 제한합니다.
- **해결 `[제안]`** — 모듈 전역 세마포어(N=2~3)로 LLM 구간만 감쌉니다. 대기는 30초 예산에
  영향을 주지만, 폭주 시에는 429·비용 급증보다 대기가 낫습니다.
- **왜 중요한가** — **랩(호스트 1~2대)에서는 절대 재현되지 않고 감시 호스트가 많은
  실환경에서만 터지는 종류**입니다. "PoC에서 안 겪은 도입 리스크"로 적어 두는 것 자체가
  산출물입니다.

## G8. 재기동하면 열린 인시던트가 통째로 사라진다

- **문제** — 인시던트 버퍼와 멱등 캐시가 전부 프로세스 메모리입니다. 창이 열린 상태에서
  재기동하면 **그 사건의 분석은 영영 나가지 않습니다**(조용한 유실).
- **상호작용 `[제안]`** — 자동 재기동(`Restart=always`)을 켜면 크래시 시 자동 복구되는데,
  그 순간 열려 있던 인시던트는 복구되지 않고 사라집니다. **자동 재기동이 유실을 조용하게
  만듭니다.**
- 지속화(SQLite 등)는 검증된 타이밍 로직을 건드릴 위험이 있어 뒤로 미뤘고 그 판단은
  유효합니다. 다만 **"재기동 = 열린 인시던트 유실"을 알려진 한계로 명시**하는 것은 미룰
  이유가 없습니다. 최소 조치로 **종료 시그널에서 열린 인시던트를 즉시 마감(flush)** 하는 것은
  값쌉니다.

## 정직한 한계로 문서화만 하는 것 (구현 대상 아님)

- **확인 명령 3개는 본질적으로 생성물입니다 `[코드]`** — 프롬프트가 "지금 즉시 실행할 확인
  명령 3개"를 요구합니다. 컨텍스트에 없는 명령을 만들어내는 것이라 **환각 통제 밖**입니다.
  실행 주체가 사람이라 위험은 낮지만, **"판정은 코드·설명은 LLM" 원칙의 유일한 예외**이므로
  먼저 밝히는 편이 낫습니다.
- **마스킹은 등록된 식별자만 지웁니다 `[코드]`** — Zabbix에서 받은 host·IP·group을 등록해
  치환하고, 그 밖에는 IP 정규식만 있습니다. **로그 라인에 사용자명·도메인·이메일이 있으면
  통과합니다.** 실질 보완은 마스킹 프록시 경로이며, 즉 **직결 경로와 프록시 경로의 마스킹
  강도가 다릅니다.**

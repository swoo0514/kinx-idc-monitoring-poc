# 구조적 결함 카탈로그 — 게이트웨이 파이프라인 정적/동적 전수 점검 결과

게이트웨이 소스 코드 및 파이프라인 로직 전수 점검(Static/Dynamic Audit)을 통해 식별된 **구조적 결함(Structural Gaps) 카탈로그**입니다. 명시적 예외(Exception)를 발생시키지 않고 정상 동작처럼 보이나 실제로는 논리적 오작동을 유발하는 '은밀한 결함(Silent Failures)' 사례를 분류하여 기술합니다.

각 항목은 **문제 현상 ➔ 기술적 근거 ➔ 파급 효과 ➔ 해결 방안** 순서로 기술되었으며, 근거 표기 규약([`../02-design/evidence-policy.md`](../02-design/evidence-policy.md))을 준수합니다.

---

## G1. 예외 수용에 따른 무응답 상태의 '거짓 안심' 오인 (해결 완료)

- **문제 현상:** 수집 모듈(`collector.py`)이 Loki·Wazuh API 조회 실패 시 발생 예외를 포획(Catch)하여 빈 리스트(`[]`)를 반환함에 따라, **"정상적인 보안 신호 없음" 상태와 "시스템 조회 실패" 상태를 코드상에서 구별하지 못하는 결함**이 존재했습니다.
- **기술적 근거 `[코드]`:** `collector.py` 내 로그 및 보안 조회 함수 전체가 `except Exception: return []` 구조로 구현되어 별도의 상태 플래그를 반환하지 않음.
- **파급 효과:**
  1. **LLM 프롬프트 오판 유발:** 수집 데이터 부재 시 "침해 흔적 없음"으로 해석하도록 프롬프트가 지시되어 있어, **Wazuh Indexer 장애 발생 시 봇이 보안 위협 배제를 단정하는 오류**가 발생했습니다.
  2. **라우팅 게이트 오동작:** 관측 백엔드가 가용하지 않을 때 교차 신호 수집 건수가 0으로 처리되어, 정작 초동 분석이 가장 필요한 장애 상황에서 알림 처리가 스킵되는 현상이 발생했습니다.
- **해결 방안 `[코드]`:** 명시적 조회 상태 3종 (`ok` / `unavailable` / `disabled`) 정의 및 `sources` 메타데이터 객체를 추가하여 전파했습니다. 기존 e2e 파이프라인 정합성을 유지하면서 상태 기반 보수적 라우팅이 수행되도록 회귀 테스트를 추가했습니다.
- **실측 및 검증 (의도적 장애 주입):** 인덱서 포트 차단을 통해 조회 실패(`unavailable`)를 강제 발생시킨 후 실시간 이벤트를 투입하여 아래와 같이 정상적으로 제어됨을 입증했습니다.

| 구분 | `security: unavailable` (조회 실패) | `security: ok` (정상 수집) |
|---|---|---|
| **Slack 카드 배지** | ⚠️ 조회 실패: 보안(Wazuh) | 정상 표기 (배지 없음) |
| **보안 축 진술** | "침해 여부 미상 — **조회 실패를 근거로 안심할 수 없음**" | "침해·비인가 변경 흔적 없음 ➔ 순수 운영 이슈" |
| **자동 조치 권고** | "부적합 (원인 미상 및 보안 상태 불확실)" | "조회성 명령에 한해 자동화 가능" |

- **기술적 의의:** 수집 실패 상태를 명시적으로 구별하여, 관측 시스템 장애 시 거짓 안심(False Confidence)에 기반한 잘못된 의사결정이 내려지는 위험을 차단했습니다.

## G2. 알림 분류기(Classify) 오분류에 따른 알림 병합 실패 (부분 해결 완료)

- **문제 현상:** `classify()` 함수의 키워드 매칭 우선순위 오류로 인해 알림 유형이 잘못 분류되어, 알림 병합 키(`incident_key`) 생성이 무효화되고 연관 브리지 룰이 발화하지 않는 현상이 발생했습니다.
- **기술적 근거 `[코드]` (실행 검증 결과):**

| 수신 알림명 | 실제 오분류 결과 | 기대 정분류 |
|---|---|---|
| `Linux: SSH service is down` | `auth_security` | `service_down` |
| `메모리 사용률 95% 초과` | `disk_space` | `memory_pressure` (유형 부재) |
| `Linux: High memory utilization` | `other` | `memory_pressure` (유형 부재) |
| `Zabbix agent is not available` | `other` | `service_down` |

- **원인 분석:**
  1. `auth_security` 키워드(`ssh`)가 `service_down`보다 우선순위가 높아 **SSH 서비스 중단 장애**를 보안 침해 사건으로 오인
  2. `disk_space` 키워드(`사용률`)의 범주가 너무 넓어 메모리·CPU 등 타 자원 사용률 알림까지 흡수
  3. **`memory_pressure` 전용 유형 미정의**로 표준 메모리 알림이 `other` 분류로 탈락
- **해결 방안 `[코드]`:** 매칭 키워드 정밀화(`ssh` ➔ `sshd`, `사용률` ➔ `디스크 사용률`), `memory_pressure` 유형 신설, 단어 경계(Word Boundary) 매칭을 적용하여 부분 일치 오류를 차단하고 테스트 케이스를 23개로 확장했습니다.
- **향후 과제 `[제안]`:** 웹훅 미디어 타입 파라미터 확장을 통해 알림명 문자열 추정 방식에서 `item_key` (`vfs.fs.size`, `vm.memory.utilization` 등) 직접 참조 방식으로 분류 로직을 전환할 필요가 있습니다.

## G3. 선판정 이력 조회 상한(Limit 200) 포화에 따른 랭킹 왜곡

- **문제 현상:** 만성/신규 장애 선판정을 위한 과거 이벤트 조회 시 `limit: 200` 제약이 걸려 있어, 최근 90일간 200건 이상 발생한 고빈도 장애 트리거의 카운트가 200건으로 포화(Saturation)되는 현상이 발생합니다.
- **기술적 근거 `[코드]`:** `collector.py` 내 `event.get` API 호출 시 `limit: 200` 고정 파라미터 사용.
- **파급 효과 `[제안]`:** 선판정 결과(`만성`) 자체는 유지되나, "만성 장애 발생 건수 기준 상위 인시던트 랭킹"을 산출할 때 상위 트리거 항목들이 모두 200건으로 동률 처리되어 **만성 장애 우선순위 산출 데이터가 왜곡**됩니다.
- **해결 대안 `[제안]`:** Zabbix API의 `countOutput` 파라미터를 활용하여 누적 발생 건수를 별도 정밀 측정하거나, 조회 창(Time Window)에 맞춰 Limit 상향 조정을 검토합니다.

## G4. 3개 관측 소스 간 호스트 식별자 불일치에 따른 알림 병합 제약

- **문제 현상:** 알림 병합 키 생성 시 원본 호스트 문자열을 직접 참조함에 따라, 수집 시스템 간 호스트명 표준화(FQDN)가 미적용된 경우 동일 호스트의 알림이 개별 사건으로 분리되는 제약이 존재합니다.
- **기술적 근거 `[코드]`:** `incident_key(host, cls)` 로직 내 호스트명 정규화 처리 부재 (`HOST_LABEL_MAP` 변환은 `collector.py`에만 존재).
- **관측 계층 역할 재정의:**
  - **Zabbix 및 Wazuh:** 알림을 발화하여 **사건(Incident)을 생성하는 주체**
  - **Loki (로그):** 스스로 알림을 발화하지 않으며, 발생한 사건의 **인과관계를 증명하는 근거 데이터 제공 주체**
  - *정확한 개념 정의:* **"2개 소스가 사건을 생성하고, 3개 소스가 사건을 종합 설명한다."**
- **해결 대안 `[제안]`:** 게이트웨이 파이프라인 진입 시점에 호스트명 정규화(FQDN)를 일괄 적용하여 수집·병합·Keep 저장소 간 식별자 정합성을 확보합니다.

## G5. 게이트 필터링 조건 미부합 알림의 영구 손실 (해결 완료)

- **문제 현상:** 게이트 라우팅 로직에서 분석 스킵(Skip) 반환 시, 파이프라인이 즉시 종료되어 Slack 카드 발송뿐만 아니라 **Keep 관제 저장소로의 데이터 저장까지 누락**되는 현상이 발생했습니다.
- **파급 효과:** 게이트에서 스킵되는 항목은 주로 '단일 축 노이즈 알림'에 해당하며, 이는 만성 장애 랭킹 분석을 위한 핵심 수집 대상에 해당하므로 **통계 수집의 사각지대가 발생**했습니다.
- **해결 방안 `[코드]`:** 게이트 스킵 발생 시에도 LLM 호출을 제외한 **판정·유형·알림 수 메타데이터**를 Keep 저장소로 전송하도록 파이프라인을 수정했습니다 (추가 연산 비용 없이 통계 데이터 유실 차단).

## G6 · G9. 심층 조사 발동 조건의 기지 장애 편중 문제 (해결 완료)

- **문제 현상:** 심층 조사(HolmesGPT) 발동 조건이 사전 정의된 '알림 병합 사건'에 집중되어 있어, 사람이 이미 인지하고 있는 기존 장애 유형에만 고비용 분석 리소스가 투입되는 아키텍처적 불균형이 존재했습니다.
- **해결 방안 `[코드]`:** 선판정 결과를 활용하여 **정보 이득(Information Gain)이 극대화되는 영역**으로 조사 리소스를 재배분했습니다:
  - **만성 장애 (기지 장애):** 심층 조사 발동 **억제** (비용 및 노이즈 절감)
  - **신규 장애 (미지 장애):** 심층 조사 **우선 발동** (분석 가치 극대화)
  - **SEV1 및 열화(`degraded`) 상태:** 장애 위중도 및 1차 분석 미비에 따라 **무조건 발동**

## G7. 동시 디바운스 마감 시 LLM API 병렬 호출 제어 부재

- **문제 현상:** 다수 인시던트의 디바운스 창(Debounce Window)이 동일 시점에 마감될 경우, 동시성 제어(Concurrency Limit) 없이 무제한 LLM API 병렬 호출이 실행되어 API Rate Limit(429) 및 비용 급증을 유발할 위험이 존재합니다.
- **기술적 근거 `[코드]`:** 게이트웨이 내 LLM API 호출 세마포어 제어 로직 부재.
- **해결 대안 `[제안]`:** 모듈 전역 세마포어(Semaphore, N=2~3)를 도입하여 동시 LLM 분석 수행 건수를 제한합니다.

## G8. 프로세스 재기동 시 인메모리 버퍼 내 오픈 인시던트 유실

- **문제 현상:** 알림 병합 버퍼 및 멱등성 캐시가 인메모리(In-memory) 구조로 관리되어, 디바운스 대기 상태에서 게이트웨이 프로세스 재기동 시 수집된 인시던트 데이터가 소실되는 현상이 발생합니다.
- **해결 대안 `[제안]`:** 프로세스 종료 시그널(SIGTERM) 수신 시 인메모리 버퍼 내 디바운스 대기 중인 인시던트를 즉시 마감(Flush) 및 전송 처리하는 Graceful Shutdown 로직을 구현합니다.

## 기술적 한계 및 예외 사항 명시

- **추천 검증 명령어 생성 로직:** 프롬프트가 임의의 CLI 검증 명령어를 생성하는 로직은 결정론적 코드 통제 범위를 벗어난 생성적 영역임을 명시합니다 (단, 실행 주체가 관제 담당자이므로 위험도는 낮음).
- **마스킹 필터링 범위의 직결/프록시 경로 간 차이:** 수집된 가명화 대상 외에 로그 원문 내 이메일/사용자명 등은 직결 파이프라인에서 통과될 수 있으므로, 마스킹 프록시 계층의 보완 역할이 필요합니다.

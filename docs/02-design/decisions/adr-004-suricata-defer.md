# ADR-004 — Suricata: 랩 구축을 하지 않고 설계서까지만. 로드맵 1순위는 Suricata가 아니다

**판정: 실환경 로드맵의 1순위는 "dnsdist 네이티브 관측을 켜는 것"이고, Suricata는 그것으로도
구조적으로 못 보는 축에만 정당성이 있다.**

이 ADR의 본체는 **착수 가정이 조사로 무너진 기록**입니다. 그 정정 자체가 산출물입니다.

## 1. 무너진 가정

착수 시 가정은 이랬습니다.

> "실환경 DNS는 dnsdist 그룹 QPS 집계만 보고 있으니 질의 내용은 아무도 못 본다.
> Suricata가 그 공백을 메운다."

이 가정을 공식 문서로 깨보게 했더니 **깨졌습니다.** dnsdist는 per-query 관측을 네이티브로
**다섯 경로** 갖고 있습니다.

| 경로 | 공식 문서 원문 |
|---|---|
| `LogAction` | "Log a line for each query" (timestamp·query ID·qname·qtype·remote address/port) |
| 내장 웹서버 **rings API** | `GET /api/v1/servers/localhost/rings` — "Get the most recent queries and responses from the in-memory ring buffers" |
| protobuf | `RemoteLogAction` — qname·클라이언트·rcode·응답 RR |
| dnstap | "dnsdist supports dnstap since version 1.3.0" |
| dynblocks | `setRCodeRate(DNSRCode.NXDOMAIN, ...)` — 클라이언트 IP 단위 추적·**차단** |

**rings API가 결정적입니다.** 수신 데몬 0대로 HTTP 폴링만으로 per-query JSON을 줍니다.
"수신 데몬이 필요해서 무겁다"는 방어 여지까지 막습니다. NXDOMAIN 급증 탐지도 dynblocks가
클라이언트별로 하고, 탐지에 그치지 않고 차단까지 합니다.

**왜 이 절이 첫 절인가.** 심사에서 "dnsdist rings로 되는데요" 한 마디가 나오면 논거 전체가
무너지는 지점이었습니다. **먼저 인정하고 그 위에 남는 것만 주장하는 것이 방어 가능한 유일한
형태입니다.** 조사 없이 썼으면 발표장에서 깨졌을 것을 미리 깼습니다.

### 프레임 교체

| | 폐기 | 채택 |
|---|---|---|
| 격차 매트릭스 | "현행이 못 보는 7항목" (2열) | **3열** — ① 지금 켜져 있는 것 ② 네이티브로 켤 수 있는데 안 켠 것 ③ 와이어에서만 보이는 것 |
| Suricata 정당성 | "질의 내용을 처음 보이게 한다" | **네이티브가 구조적으로 못 보는 축**만 |
| 실환경 1순위 | Suricata 도입 | **dnsdist 네이티브 관측 활성화** — 더 싸고 더 빠름 |

## 2. 관측 격차 매트릭스 (3열)

**읽는 법.** ①→② 는 **설정을 켜는 일**입니다. ②→③ 은 **관측 지점을 바꾸는 일**입니다.
**Suricata의 자리는 ③뿐입니다.**

| # | 관측 항목 | ① 지금 | ② 네이티브 가능(안 켬) | ③ 와이어에서만 |
|---|---|---|---|---|
| 1 | 질의명 per-query | 그룹 QPS 집계 | **가능** — LogAction / rings / protobuf | — |
| 2 | NXDOMAIN 급증 + 원인 도메인 | 없음 | **비율·차단 가능** — dynblocks | 이름 이력 장기 보관 (링버퍼 한계) |
| 3 | **호스트 자신의 아웃바운드 질의·세션** | 없음 | **구조적 불가** — DNS 소프트웨어는 자기 소켓만 본다 | `event_type: dns` + `flow` |
| 4 | **53 이외 포트 / DNS 아닌 프로토콜** | 없음 | **구조적 불가** | `tls.sni` / `http.hostname` / `flow` |
| 5 | **캐시 히트로 응답된 질의의 응답 내용** | 없음 | **링버퍼는 못 봄(문서 확정)** | 와이어는 캐시 히트·미스를 구분하지 않는다 |
| 6 | **Authoritative 계층 응답 데이터** | 없음 | **불가** — protobuf가 "without answer data", dnstap 미지원 | `dns.answers[].rdata` |
| 7 | 알려진 위협 지문(시그니처) | 없음 | 없음 — 레이트·suffix 매칭이지 위협 인텔 개념이 없다 | `alert.signature` (ET Open) |
| 8 | 질의명 어휘 특성(엔트로피·길이) | 없음 | 계산 안 해줌 | **계산 안 해줌** — 원문이 재료일 뿐 |
| 9 | 증폭 반사기 악용 여부 | 없음 | **레이트 가능** | 크기비 (`bytes_toclient`/`bytes_toserver`) |
| 10 | DNS 데몬이 죽은 구간 | 없음 | **구조적 불가** — 로깅이 데몬과 운명을 함께한다 | 독립 프로세스라 계속 기록 |
| 11 | 관측 도구 자신의 신뢰도 | 해당 없음 | 다른 층 (OS 카운터) | `capture.kernel_drops` |

### 어디까지 주장하고 어디서 멈추는가

- **1~2행은 인정하고 넘어갑니다.** 갭이 "제품이 못 한다"가 아니라 **"우리가 안 켰다"** 입니다.
  이 두 행의 결론은 Suricata가 아니라 **dnsdist rings API를 켜는 것**입니다.
  다만 2행에 실질 차이는 남습니다 — dynblocks는 임계 초과 클라이언트를 즉시 막지만, 사후
  조사용 **이름 이력은 링버퍼 크기에 갇힙니다.** IDC/IX 사업자에게 이 차이는 곧
  **고객 문의 대응과 사후 보고서 작성 가능 여부**입니다.
- **3행이 정당성의 본체입니다.** MITRE ATT&CK T1071.004의 Data Sources는 Network Traffic
  두 줄뿐이고 호스트 로그·프로세스 계열이 없습니다. **네트워크 관측 없이는 구조적으로 못
  본다**는 뜻입니다. 데모 C가 3축으로도 못 잡는 것이 정확히 이것입니다.
  소관도 깨끗합니다 — 스위치가 아니라 **우리 DNS 서버 자신의 인터페이스**입니다.
- **5행은 반증 조사가 찾아낸 가장 강한 잔여 근거입니다.** 문서 원문: "answers from the packet
  cache are not stored in the response ring buffer". 캐시 히트율이 높은 계층에서 이 공백은
  큽니다. **단 과장 금지** — 응답 액션이 캐시 히트에 적용되는지는 문서에 서술이 없어
  미확인입니다. 쓸 수 있는 문장은 "링버퍼는 못 본다(문서 확정) + 응답 액션은 미확인"까지입니다.
- **6행 — 3계층 비대칭이 실제 명분입니다.** Authoritative 설정 문서에 dnstap이라는 단어
  자체가 없고 protobuf가 "without answer data"입니다. 즉 **"dnsdist로 되는데요"는 프론트엔드
  계층 한정 반박**이고, Authoritative 계층은 네이티브 공백이 문서로 실재합니다.
- **8행은 과장 방지용입니다.** 얻는 것은 지표가 아니라 **지표를 계산할 재료**입니다.
  이 구조는 우리 봇의 원칙과 같습니다 — **판정은 코드, 설명은 LLM.**
- **9행이 소관 경계를 지키면서 보안을 말하는 지점입니다.** RFC 5358(BCP 140)은 서버 운영자
  책임을 표준화하고, 위조 출처 차단(BCP 38)은 라우팅 경계 = 네트워크팀 소관입니다.
  우리는 **"우리 서버가 반사기인가"만** 봅니다.
- **11행은 도입 요건이지 부가 패널이 아닙니다.** drop이 있으면 "신호 없음"과 "못 봄"이
  구분되지 않는데, 이는 게이트웨이에서 이미 고친 것과 **같은 종류의 결함**입니다.
  같은 실수를 새 축에서 반복하지 않습니다.

## 3. 왜 랩을 세우지 않았나

- **정당성이 ③으로 좁혀지면서 1컷의 프레임도 바뀌었습니다.** "질의 내용을 처음 보이게"가
  아니라 **"DNS 질의와 DNS 아닌 트래픽이 같은 스키마·같은 타임라인으로"** 입니다.
- 남은 일정에서 랩 구축은 패키징을 밀 위험이 있었고, **설계서가 있으면 나중에 짧게 세울 수
  있습니다.** 그래서 "설계서까지만"이 정해진 범위였습니다.

## 4. 나중에 세울 때 반드시 지킬 것

- **버전을 고정합니다.** EPEL9 계열은 EVE 스키마 v2 전용이고, 상위 버전은 v3에서 필드가
  이동해 **LogQL과 패널을 전부 다시 써야 합니다.**
- **공식 문서의 `filemode` 예시를 그대로 베끼지 않습니다.** 미지정이 기본이고, 예시값을
  넣으면 로그 수집기가 파일을 못 읽는 권한 사고를 스스로 재현합니다(랩에서 겪은 것과 같은 종류).
- **질의명을 라벨로 쓰지 않습니다.** 카디널리티가 폭발합니다.
- 요청/응답 구분은 `dns.type`으로만 합니다.
- **Wazuh 이중 경로는 켜도 조용히 사라집니다** — 관련 룰이 팀 컷라인(레벨 10) 아래라
  대시보드에 안 나타납니다. Wazuh 고도화에서 내린 결론("수집은 넓게, 알림은 좁게")과
  같은 구조입니다. 랩은 **로그 단일 경로**로 갑니다.

## 5. 프레이밍 주의

**"네트워크를 감시한다"로 한 번이라도 읽히면 소관 경계와 충돌합니다.** 네트워크 장비 관제는
네트워크팀이 각 센터에서 24시간 수행합니다. 항상 **"우리 자산(DNS 서버)의 트래픽 내용"** 으로
말합니다.

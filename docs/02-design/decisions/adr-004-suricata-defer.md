# ADR-004 — Suricata: 랩 환경 직접 구축 배제 및 설계서 작성 중심 접근 (로드맵 1순위 재정의)

**판정: 실환경 로드맵 1순위는 'dnsdist 네이티브 관측 기능 활성화'로 정의하며, Suricata는 네이티브 기능으로 수집 불가능한 구조적 사각지대에 한해 제한적으로 도입함**

본 ADR은 초기 전제 가정이 검증 과정을 통해 기각되고 요구사항이 정제된 이력을 기록한 의사결정 문서입니다.

---

## 1. 초기 전제 가정의 검증 및 수정

### 1-1. 초기 가정의 기각

초기 착수 단계의 전제 가정은 다음과 같았습니다:

> *"실환경 DNS 인프라는 dnsdist 그룹 QPS 집계 지표만 관측하고 있어 질의 세부 내용을 파악할 수 없다. 따라서 Suricata 도입을 통해 해당 관측 공백을 보완해야 한다."*

공식 문서 검증 결과, dnsdist는 단일 질의(Per-query) 단위 관측을 위한 **5가지 네이티브 수집 경로**를 자체 제공하고 있음을 확인했습니다.

| 수집 경로 | 공식 문서 명세 |
|---|---|
| **`LogAction`** | 개별 질의에 대한 상세 로그 출력 (Timestamp, Query ID, Qname, Qtype, Remote Address/Port) |
| **내장 웹서버 `rings` API** | `GET /api/v1/servers/localhost/rings` — 인메모리 링 버퍼 기반 최신 질의 및 응답 데이터 JSON 반환 |
| **Protobuf (`RemoteLogAction`)** | Qname, 클라이언트 IP, RCode, 응답 Resource Record 수집 지원 |
| **Dnstap** | dnsdist v1.3.0 이상 버전부터 Dnstap 프로토콜 지원 |
| **`dynblocks`** | `setRCodeRate(DNSRCode.NXDOMAIN, ...)` — 클라이언트 IP 단위 추적 및 자동 차단 제어 |

특히 **`rings` API**를 활용할 경우 별도의 수집 데몬 추가 없이 HTTP 폴링 방식만으로 질의 단위 JSON 데이터를 확보할 수 있습니다. 또한, NXDOMAIN 급증 탐지 및 차단 역시 `dynblocks` 기능을 통해 클라이언트 단위로 수행할 수 있습니다.

### 1-2. 관측 프레임워크 재정의

초기 논거의 오류를 바로잡고 아래와 같이 프레임워크를 수정·채택했습니다.

| 구분 | 기각된 기존 프레임 | 수정·채택된 신규 프레임 |
|---|---|---|
| **관측 격차 분석** | "현행 시스템 미관측 7개 항목" (2열 방식) | **3열 관측 격차 매트릭스** 적용 (① 현행 활성화 항목 / ② 네이티브 가능 항목 / ③ 와이어 전용 항목) |
| **Suricata 도입 정답성** | "질의 내용을 최초로 가시화함" | **dnsdist 네이티브 관측으로 수집 불가능한 구조적 사각지대로 한정** |
| **실환경 로드맵 1순위** | Suricata 파이프라인 신규 구축 | **dnsdist 네이티브 관측 기능 활성화** (비용 및 구현 속도 측면 우수) |

## 2. 3열 관측 격차 매트릭스 (Observability Gap Matrix)

*매트릭스 해석 방법:*
- ① ➔ ② 이동: **시스템 설정 변경(활성화) 영역**
- ② ➔ ③ 이동: **관측 수집 지점 전환 영역 (Suricata 적용 대상 영역은 ③ 항목으로 한정)**

| # | 관측 항목 | ① 현행 가용 | ② 네이티브 가능 (미활성화) | ③ 와이어(Wire) 전용 수집 |
|---|---|---|---|---|
| 1 | 단일 질의명 (Per-query) | 그룹 QPS 집계 | **가능** (`LogAction` / `rings` / Protobuf) | — |
| 2 | NXDOMAIN 급증 및 원인 도메인 | 미수집 | **비율 추적 및 차단 가능** (`dynblocks`) | 질의 이력 장기 보관 (링 버퍼 용량 한계 보완) |
| 3 | **호스트 자체 아웃바운드 질의 및 세션** | 미수집 | **구조적 불가능** (DNS 데몬은 바인딩 소켓만 관측) | `event_type: dns` + `flow` |
| 4 | **Non-Port 53 / 비 DNS 프로토콜** | 미수집 | **구조적 불가능** | `tls.sni` / `http.hostname` / `flow` |
| 5 | **캐시 히트(Cache-hit) 응답 데이터** | 미수집 | **링 버퍼 수집 불가 (공식 스펙 명시)** | 와이어 레벨 수집 (Cache Hit/Miss 구분 없이 패킷 수집) |
| 6 | **Authoritative 계층 응답 데이터** | 미수집 | **불가능** (Protobuf는 "Without answer data", Dnstap 미지원) | `dns.answers[].rdata` |
| 7 | 알려진 위협 시그니처 탐지 | 미수집 | 미지원 (Rate/Suffix 매칭만 지원, 위협 인텔리전스 미지원) | `alert.signature` (ET Open 룰셋 연동) |
| 8 | 질의명 어휘적 특성 (엔트로피·길이) | 미수집 | 연산 미지원 | **원문 데이터 제공** (별도 연산 필요) |
| 9 | 증폭 반사 공격(Reflector) 악용 여부 | 미수집 | **임계치 관측 가능** | 트래픽 크기 비율 관측 (`bytes_toclient` / `bytes_toserver`) |
| 10 | DNS 데몬 장애 시 관측 지속성 | 미수집 | **구조적 불가능** (데몬 중단 시 로깅 중단) | 독립 프로세스 기반 지속 관측 가능 |
| 11 | 관측 도구 자체 수집 신뢰도 | 해당 없음 | 타 계층 관리 (OS 커널 카운터) | `capture.kernel_drops` 패킷 유실 지표 관리 |

### 세부 항목별 정밀 검증 및 수용 범위

- **항목 1~2 (네이티브 기능 우선):** 네이티브 제어 범위(`rings` API 활성화)로 수용하며 Suricata 적용 대상에서 제외합니다. 단, `dynblocks`는 사후 분석용 이력 보관 용량이 링 버퍼 크기로 제한되므로 사후 보고서 작성 용도에 한해 와이어 기반 장기 보관 필요성이 유지됩니다.
- **항목 3 (핵심 도입 근거):** MITRE ATT&CK T1071.004 관측 출처 기준, 네트워크 트래픽 관측 없이는 구조적으로 탐지가 불가능한 영역입니다. (DNS 서버 자체 인터페이스 대상 수집으로 네트워크 관리 영역과의 경계를 준수합니다.)
- **항목 5 (캐시 응답 공백):** dnsdist 공식 스펙에 **패킷 캐시 응답은 링 버퍼에 저장되지 않음**이 명시되어 있습니다. 다만 `LogResponseAction` / `RemoteLogResponseAction`이 캐시 히트에도 적용되는지는 공식 문서에 서술이 없어 **미확인** 상태이므로, 주장 가능한 범위는 "링 버퍼는 수집 불가(확정) + 응답 액션 적용 여부는 미확인"까지입니다. 와이어 수집을 유일한 대안으로 단정하지 않습니다.
- **항목 6 (Authoritative 계층 공백):** Authoritative 계층의 경우 Protobuf 응답 데이터 미포함 및 Dnstap 미지원 제약이 공식 문서로 확인되어 패킷 수집 정당성이 확보됩니다.
- **항목 8 (데이터 추출 원칙):** 수집 시스템은 메트릭 연산 재료(원문)를 수집하는 역할에 한정하며, 지표 산출 및 판정은 분석 파이프라인(코드)에서 수행합니다.
- **항목 9 (운영 책임 경계 준수):** RFC 5358 (BCP 140) 기준, DNS 서버 운영자 책임 범위인 "자사 DNS 서버의 증폭 반사 공격 악용 여부" 관측으로 범위를 한정합니다.
- **항목 11 (유실 관리):** 수집 도구 자체의 패킷 드롭(`kernel_drops`)을 지표화하여 "신호 없음"과 "수집 유실" 상태를 명확히 구별합니다.

## 3. 랩 직접 구축 배제 사유

- 관측 정당성이 매트릭스 ③ 영역(구조적 사각지대)으로 정제됨에 따라, 1차 목표가 "질의 가시화"에서 **"DNS 및 비 DNS 트래픽의 통합 스키마 타임라인 구현"**으로 전환되었습니다.
- 한정된 일정 내 패키징 리스크를 방지하고자 **상세 설계서 작성 단계까지만 과업을 수행**하며, 향후 해당 설계서를 기반으로 신속한 인프라 구축이 가능하도록 준비했습니다.

## 4. 향후 인프라 구축 시 필수 준수 사항

1. **버전 고정 (Version Locking):** EPEL9 계열 사용 시 EVE 스키마 v2 사양으로 고정합니다. 상위 버전 전환 시 v3 스키마 필드 이동으로 인해 LogQL 및 대시보드 패널 수정 공수가 발생합니다.
2. **권한 및 Filemode 설정:** 공식 문서의 `filemode` 예시 구문을 검증 없이 적용할 경우 로그 수집기의 파일 접근 권한 오류가 발생하므로 미지정 기본값을 유지합니다.
3. **라벨 카디널리티(Cardinality) 관리:** 질의명(Qname) 항목을 Loki 라벨로 직접 할당하는 것을 금지합니다 (카디널리티 폭발 방지).
4. **트래픽 방향 구별:** 요청/응답 구별은 `dns.type` 필드 단일 기준으로 처리합니다.
5. **Wazuh 수집 경로 일원화:** Wazuh 단순 중계 방식은 관련 알림 레벨 제약으로 대시보드 표출 대상에서 제외되므로, **Loki 단일 수집 파이프라인**으로 구성합니다.

## 5. 운영 경계 표기 지침 (Domain Boundary)

본 시스템의 수집 대상 및 목적 표현 시 **"네트워크 전체 감시" 용어 사용을 금지**합니다. 네트워크 장비 관제 영역(네트워크운용팀 소관)과의 충돌을 방지하기 위해, 항상 **"DNS 서버 자산 인터페이스 기준 트래픽 세부 관측"**으로 범위를 명확히 정의하여 표현합니다.

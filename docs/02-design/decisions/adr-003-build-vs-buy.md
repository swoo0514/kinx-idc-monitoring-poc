# ADR-003 — AIOps: 자체 구축(Build) vs 상용 도입(Buy) 의사결정 배경

**판정: PoC 단계에서는 자체 구축 방식 채택 (단, 자체 봇은 영구 운영 제품이 아닌 요구사항 검증용 자산)**

본 문서는 기존 AIOps 솔루션과의 차별성 및 프로덕션 환경 도입 시 Build vs Buy 판단의 근거를 기술합니다.

---

## 1. AIOps 시장 현황 및 성숙도

AIOps 기술 영역은 크게 3가지 분야로 분류되며, 본 프로젝트의 자체 봇 엔진은 이 중 '이벤트 상관 분석'과 'LLM 기반 근본 원인 분석' 영역을 경량 통합한 형태입니다.

- **이벤트 상관 관계 분석 및 알림 노이즈 감축 (알림 병합):** 상용 솔루션(Moogsoft, BigPanda, PagerDuty AIOps) 및 오픈소스(Keep)를 중심으로 10년 이상 기술 성숙도가 축적된 영역입니다.
- **LLM 기반 근본 원인 분석 (초동 분석 회신):** 최신 기술 영역으로, 상용 서비스(Grafana SIFT, Datadog Bits AI) 및 오픈소스(HolmesGPT, k8sgpt) 솔루션이 활발히 도입되고 있습니다.
- **로그 및 메트릭 이상 탐지:** OpenSearch ML Commons(Wazuh Indexer 기반 연동 가능), Elastic ML, Prophet/PyOD 등을 활용한 이상 탐지 기술 영역입니다.

---

## 2. 주요 오픈소스(OSS) 솔루션의 기술 스택 적합성 평가

| 솔루션명 | 담당 역할 | 기술 스택 적합성 (Zabbix/Loki/Wazuh, IDC 물리·VM 환경) |
|---|---|---|
| **Keep** | 알림 상관 분석 · 관리 · 워크플로 | **높음** — 인프라 스택 비의존적 구조, Zabbix 공식 연동 지원 |
| **HolmesGPT** | LLM 기반 근본 원인 분석 | **높음** — VM 및 베어메탈 지원, Zabbix·Loki·OpenSearch·MySQL Toolset 내장 |
| **k8sgpt** | LLM 기반 클러스터 진단 | **낮음** — Kubernetes 전용 환경으로 설계됨 |
| **OpenSearch Anomaly Detection** | 이상 탐지 | **높음** — Wazuh Indexer(OpenSearch 기반)와 직접 연동 가능 (단, LLM 트리아지 미지원) |

> **기술 스택 검증 시 유의사항:**  
> 다수의 오픈소스 AIOps 솔루션이 Kubernetes 및 Cloud-Native 환경을 전제로 개발되었습니다. 따라서 IDC 내 물리 서버, VM 및 Zabbix 중심의 레거시/온프레미스 인프라 환경과의 호환성을 최우선으로 검증해야 합니다.  
> *참고: HolmesGPT의 경우 초기 착수 시 K8s 전용 솔루션일 것이라는 우려가 있었으나, 공식 문서 검증을 통해 온프레미스 VM 및 베어메탈 환경을 공식 지원함("any infrastructure: VMs, bare metal, cloud")을 확인하고 검증 대상에 포함했습니다.*

---

## 3. 상용 솔루션 미채택(Build) 사유

1. **데이터 주권 및 온프레미스 보안 제약:**  
   대다수의 상용 AIOps 솔루션은 SaaS 형태로 제공되어 텔레메트리 데이터가 외부 벤더 클라우드로 전송됩니다. 사내 및 MSP 고객 인프라 데이터의 외부 유출 방지를 위해 사내 보관 및 **데이터 마스킹 처리된 파이프라인 구성**이 필수적이었습니다.
2. **비용 효율성:**  
   호스트 및 데이터 수집 용량 기반의 상용 과금 모델(Datadog, Dynatrace, Splunk, Moogsoft 등)은 다수의 MSP 고객사를 수용하기에 비용 부담이 큽니다. 이에 기존 오픈소스 관측 스택과 LLM API 종량제 모델을 결합하여 비용을 최적화했습니다.
3. **기존 스택과의 호환성 (재플랫폼 방지):**  
   상용 플랫폼은 자사 시스템으로의 데이터 이관을 요구하는 경우가 많습니다. 자체 봇은 기존 Zabbix/Loki/Wazuh 스택 위에 API 연동 방식으로 탑재되어 인프라 재구축 비용이 발생하지 않습니다.
4. **PoC의 목적 달성:**  
   본 프로젝트의 목적은 최소 비용으로 개념 및 가치를 검증(PoC)하고 상세 요구사항을 도출하는 것이며, 완제품을 직접 개발하는 것이 아닙니다.

---

## 4. 자체 구축 봇의 포지셔닝 및 한계점

- **자체 봇의 포지션:** Keep(이벤트 상관 분석)과 HolmesGPT(LLM 근본 원인 분석)의 핵심 기능을 추출하여 사내 스택 및 MSP 심각도 체계에 맞게 경량화한 형태입니다.
- **추진 전략:** "AIOps 시장 및 솔루션 분석 ➔ 제약 조건(온프레미스, MSP, 비용) 기반의 경량 PoC 검증 ➔ 도출된 요구사항 바탕의 최적 OSS/상용 도입 판정"의 단계적 접근을 적용했습니다.
- **운영 한계 인정:** 장기적인 시스템 운영 측면에서는 지속적으로 유지보수되는 전용 솔루션을 도입하는 것이 바람직합니다. **자체 개발 봇은 요구사항 정의를 위한 검증용 자산이며 영구 유지 대상 제품이 아닙니다.**

---

## 5. PoC 주요 성과 및 후속 연계

PoC를 통해 확보한 핵심 산출물은 봇 엔진 자체가 아니라 **운영 환경에 필요한 기술 요구사항의 정립**입니다:
* 데이터 마스킹 및 거버넌스 체계
* 온프레미스 LLM 수용성
* Zabbix API 깊은 연동 범위
* 환각 방지 및 결과 재현성 통제
* 30초 이내 처리 지연 시간(Latency) 예산

도출된 요구사항 기준은 이후 **오픈소스 솔루션 평가 기준**으로 활용되었으며, 이에 따른 실측 결과는 [ADR-001 (Keep 채택)](adr-001-keep-adopt.md) 및 [ADR-002 (HolmesGPT 하이브리드 채택)](adr-002-holmesgpt.md)에 반영되었습니다.

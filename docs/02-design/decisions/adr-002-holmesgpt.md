# ADR-002 — HolmesGPT: 하이브리드 (실시간·MSP는 자체 봇, 심층 조사는 에이전틱)

**판정: 하드 요건 3개에서 막혔으나 원인 정확도는 우리 봇보다 깊다. 단순 도입도 단순 기각도
아닌 역할 분담.**

## 왜 쟀나

HolmesGPT는 우리 봇과 **개념상 가장 가까운 OSS**(LLM 근본원인 분석, Apache 2.0)입니다.
"이미 있는데 왜 만들었냐"에 답하려면 문서 논쟁이 아니라 **같은 시나리오·같은 모델로 재는 것**이
유일한 방법입니다.

핵심 아키텍처 차이가 곧 비교 축입니다.

- **HolmesGPT = 에이전틱** — LLM이 무엇을 조회할지 스스로 정하고 자율 조사
- **우리 봇 = 결정적 파이프라인** — 병합·만성 판정은 코드, LLM은 설명만 (환각 통제)

→ **자율성 vs 환각 통제·재현성**의 트레이드오프.

## 측정 조건

같은 복제 경합 시나리오(복제 지연 High + 부하 High 동시 발화)를 HolmesGPT docker CLI
(`anthropic/claude-opus-4-8`, Zabbix + Loki toolset)로 실행하고 데모 C의 우리 봇 결과와
대조했습니다. HolmesGPT는 **tool 30콜 · 3분 31초**가 걸렸습니다.

## 채점표

| 요건 | 우리 봇 | HolmesGPT | 하드 | 우위 |
|---|---|---|---|---|
| 원인 정확도 | 병합 + 인과 맞힘 (브리지룰 의존) | **더 깊음** — iowait vs CPU 구분, 백업 I/O 경합 발견, lag=0 순간 iowait 붕괴로 인과 증명, **룰 없이 도달** | 필수 | HolmesGPT |
| 온프렘 로컬 LLM | 파이썬 3.9 네이티브·단일 호출 | 네이티브 설치 불가(컨테이너 강제), Ollama는 experimental | **하드** | 우리 봇 |
| 마스킹·거버넌스 | 토큰 치환 왕복 | 호스트명·IP·DB명 **원문 그대로 전송** | **하드(MSP)** | 우리 봇 |
| Zabbix 조회 깊이 | 90일 이력·만성 판정(코드) | hostid·트리거 매핑·item·history·trend 자율 조회 | 필수 | 둘 다 통과 |
| 환각·재현성 | 판정이 코드 → 재현 100% | 갭을 정직하게 명시하고 침해 배제 근거 제시(강). 단 **조사 경로가 실행마다 변동** | 필수 | 혼합 |
| 지연 | ~15초 | **3분 31초** (30콜 + 콜드스타트) | 필수 (30초 예산) | 우리 봇 |
| 설정·유지비용 | 핀만 완화해 네이티브 | 저장소 갭 → 컨테이너, toolset 배선 마찰 | 참고 | 초기는 우리 봇 / 장기는 HolmesGPT |

## 핵심 발견

- **에이전틱이 룰 없이 인과에 도달했습니다.** 우리 봇의 "브리지룰 = 사람 큐레이션" 한계를
  HolmesGPT가 실제로 넘었습니다. **이 벤치마크의 가장 중요한 결과**이고, 자체 봇 고도화의
  타깃이 여기서 정해졌습니다.
- **깊이 우위** — 슬레이브 SQL 스레드의 대량 DELETE, 백업 덤프의 I/O 경합, 디스크 포화율까지
  스스로 캐냈습니다.
- **하드 3개에서 막혔습니다** — 지연(30초 예산 초과), 마스킹 전무(MSP 하드), 온프렘 네이티브
  불가. 특히 마스킹은 사설 IP·DB명·호스트명이 통째로 외부 LLM에 나가 **MSP 데이터에는
  현 상태로 도입 불가**입니다.
- **환각 방지는 강합니다.** 데이터소스 미연결을 숨기지 않고 명시한 뒤 다른 근거로 침해를
  배제했고, 데이터가 없을 때는 "추정은 fabrication"이라며 거부했습니다.
- **운영성 마찰(도입 리스크 실측)** — 고정 저장소가 최신 파이썬을 못 줘 컨테이너 강제 /
  커스텀 toolset이 캐시 로드 시 **조용히 사라져** 직전까지 되던 조사가 실패(`--refresh-toolsets`
  필요) / toolset의 `description` 필드 누락 시 검증 실패.

## 확정 결론 — 하이브리드

- **30초 실시간 초동 트리아지 · MSP 데이터** → **우리 경량 봇 유지.** 저지연·마스킹·온프렘이
  하드 요건이고 여기서 우리 봇이 이깁니다. **자체 봇이 헛수고가 아니라는 실측 근거가 이것입니다.**
- **엔지니어가 수 분을 쓸 수 있는 심층 온디맨드 조사** → **HolmesGPT 접근이 우월.** 단
  마스킹·온프렘 LLM을 해결해야 프로덕션 도입이 가능하며, 현 상태로는 사내 비민감 대상 한정입니다.
- **자체 봇 고도화의 방향** = HolmesGPT가 룰 없이 해낸 에이전틱 인과 도달을, 우리의 결정적
  안전판(마스킹·저지연·코드 판정) 위에 얹는 것. **"룰 큐레이션" 한계의 정답을 경쟁 도구가
  실증해 줬습니다.**

한 문장으로: *"선도 OSS를 우리 랩에서 같은 시나리오로 실측했다. 원인 분석은 그쪽이 더
깊었고 우리가 걸렸던 룰 큐레이션 한계도 넘었다. 그러나 30초 예산·MSP 마스킹·온프렘이라는
우리 하드 요건에서 막혔다. 그래서 실시간·MSP는 경량 자체 봇, 심층 조사는 그 에이전틱
접근 — 실측으로 고른 하이브리드다."*

## 결정 규칙 (판단을 재사용할 때)

- 하드 전부 통과 + 기능 대체로 통과 → 도입하고 자체 봇은 검증 자산으로 마무리
- **하드 하나라도 불통과** → 그 지점이 자체 개발을 정당화하는 근거. 그 요건에 맞춰 계속 고도화
- **혼합 결론도 유효**합니다. 어느 쪽이든 **실측 근거로 고른 것**이 산출물의 가치입니다

## 잔여

- 각 toolset의 정확한 config 키는 개별 문서 페이지에서 확정
- Ollama 대신 tool-calling 지원이 나은 로컬 서빙(vLLM 등)을 쓰면 온프렘 판정이 달라질 수 있음

# ADR-002 — HolmesGPT: 하이브리드 아키텍처 채택 (실시간·MSP는 자체 봇, 심층 조사는 에이전틱 방식)

**판정: 조건부 역할 분담 (하이브리드 채택)**  
필수 요건(Hard Requirements) 중 일부 미충족 항목이 있으나, 근본 원인 분석의 깊이 측면에서 자체 봇 대비 우수한 성능을 확인하였으므로 단일 선택/기각이 아닌 기능별 역할 분담 구조를 적용합니다.

---

## 1. 평가 배경 및 검토 목적

HolmesGPT는 자체 개발 봇과 **개념적으로 가장 유사한 오픈소스 솔루션**(LLM 기반 근본 원인 분석, Apache 2.0 라이선스)입니다. 기존 오픈소스 대비 자체 개발의 타당성 및 차별성을 입증하기 위해 **동일 시나리오 및 동일 LLM 모델 환경에서 실증 평가**를 수행했습니다.

두 방식의 핵심 아키텍처 차이는 다음과 같습니다:

- **HolmesGPT (에이전틱 방식):** LLM이 조회 대상을 자율적으로 판단하여 조사를 수행함
- **자체 개발 봇 (결정적 파이프라인 방식):** 데이터 병합 및 만성 장애 판정은 코드 로직으로 처리하고, LLM은 분석 결과의 설명 생성 용도로만 활용함 (환각 통제)

➔ **자율적 탐색 기능 vs 환각 통제 및 결과 재현성** 간의 트레이드오프 검증을 핵심 평가 축으로 설정했습니다.

---

## 2. 측정 환경 및 검증 조건

동일한 DB 복제 경합 시나리오(복제 지연 High + I/O 부하 High 동시 발생)를 대상으로 HolmesGPT Docker CLI (`anthropic/claude-opus-4-8`, Zabbix + Loki Toolset)를 실행하여 분석을 진행하고, 데모 C 환경에서의 자체 봇 수행 결과와 비교 검증했습니다. HolmesGPT 분석 시 **Tool 호출 30회 / 약 148초**가 소요되었습니다.

---

## 3. 평가 결과 비교표

| 평가 항목 | 자체 개발 봇 | HolmesGPT | 필수 요건 (Hard) | 우위 구분 |
|---|---|---|---|---|
| **원인 분석 정확도** | 데이터 병합 및 인과 추론 성공 (브리지 룰 정의에 의존) | **우수** — iowait vs CPU 수치 구별, 백업 I/O 경합 탐지, lag=0 시점의 iowait 급증으로 인과 입증 (사전 정의 룰 없이 도달) | 필수 | **HolmesGPT** |
| **온프레미스 로컬 LLM** | Python 3.9 네이티브 및 단일 호출 구조 | 네이티브 설치 불가 (컨테이너 환경 강제), Ollama 연동은 실험적(Experimental) 단계 | **하드** | **자체 봇** |
| **데이터 마스킹·거버넌스** | 토큰 양방향 치환 처리 | 호스트명·IP·DB명 등 원문 데이터를 그대로 외부에 전송 | **하드 (MSP)** | **자체 봇** |
| **Zabbix 조회 깊이** | 최근 90일 이력 및 만성 장애 판정 (코드 기반) | hostid·트리거 매핑·Item·History·Trend 데이터 자율 조회 | 필수 | **양사 충족** |
| **환각 방지 및 재현성** | 코드 기반 판단으로 재현성 100% 보장 | 데이터 미비 시 추정을 거부하는 환각 방지는 우수하나, **조사 경로가 실행 시마다 변동됨** | 필수 | **혼합** |
| **처리 지연 시간 (Latency)** | 약 15초 이내 | **약 148초** (Tool 호출 30회) | 필수 (30초 처리 예산) | **자체 봇** |
| **설정 및 유지보수성** | 파이썬 네이티브 환경 구성 | 저장소 버전 제약으로 컨테이너 강제, Toolset 설정 간 마찰 존재 | 참고 | **초기: 자체 봇 / 장기: HolmesGPT** |

## 4. 주요 실증 결과 (Key Findings)

- **규칙(Rule)에 의존하지 않는 인과관계 분석 달성:** 자체 봇의 한계점인 '브리지 룰(사전 정의 큐레이션)' 없이도 HolmesGPT가 자율 탐색을 통해 정확한 인과관계에 도달했습니다. 이는 자체 봇 고도화를 위한 기술적 목표 설정의 실증적 근거가 됩니다.
- **원인 분석 깊이의 우수성:** 슬레이브 SQL 스레드의 대량 DELETE 작업, 백업 덤프에 의한 I/O 경합, 디스크 포화율까지 스스로 탐색하여 원인을 규명했습니다.
- **3개 필수 요건(Hard Requirements) 미충족:** 응답 지연 시간(30초 처리 예산 초과), 데이터 마스킹 부재(MSP 요구사항 미충족), 온프레미스 네이티브 실행 불가 문제가 확인되었습니다. 특히 사설 IP, DB명, 호스트명 등 보안 민감 정보가 외부 LLM으로 직접 전송되는 구조로 인해 **MSP 운영 데이터에의 직접 적용은 불가능**합니다.
- **강한 환각 방지 성능:** 데이터소스 미연결 시 이를 명시적으로 표기하고 타 근거를 통해 데이터 침해 가능성을 배제하였으며, 데이터가 부족한 경우 추정 답변(Fabrication)을 거부하는 동작을 확인했습니다.
- **운영적 제약 사항 (도입 리스크):** 고정 저장소 패키지의 파이썬 버전 제약으로 컨테이너 환경이 강제되며, 커스텀 Toolset 캐시 로드 시 등록 정보가 누락되어 조사가 실패하는 현상(`--refresh-toolsets` 옵션 필요) 및 Toolset `description` 필드 누락 시 검증 실패 오류가 확인되었습니다.

## 5. 최종 결론 — 하이브리드 아키텍처 채택

- **30초 이내 실시간 초동 분석 및 MSP 데이터 처리 ➔ 자체 경량 봇 유지:** 저지연 처리, 데이터 마스킹, 온프레미스 구성이 필수 요건인 영역으로, 자체 봇의 유효성이 실증되었습니다.
- **엔지니어용 심층 온디맨드 조사 ➔ HolmesGPT 에이전틱 방식 채택:** 수 분의 분석 시간을 활용할 수 있는 영역에서는 HolmesGPT 방식이 우수합니다. 단, 마스킹 및 온프레미스 LLM 연동 문제 해결 전까지는 사내 비민감 대상 시스템으로 적용 범위를 한정합니다.
- **자체 봇 고도화 방향성:** HolmesGPT가 입증한 '규칙 미의존 자율 인과 분석' 방식을 자체 봇의 결정적 안전판(마스킹, 저지연 처리, 코드 기반 판정) 구조 위에 단계적으로 통합합니다.

*핵심 요약:* "동일 시나리오 실측 결과, 원인 분석 깊이 및 규칙 미의존 탐색 측면에서는 HolmesGPT가 우수함을 확인했습니다. 그러나 30초 응답 예산, MSP 데이터 마스킹, 온프레미스 독립 실행이라는 필수 요건을 충족하지 못하므로, 실시간/MSP 영역은 자체 경량 봇을 유지하고 심층 조사 영역에 HolmesGPT의 에이전틱 접근을 결합하는 하이브리드 구조를 채택합니다."

---

## 6. 의사결정 재사용 규칙 (Decision Rules)

- 모든 필수 요건(Hard Requirements)을 충족하고 기능적 요구사항을 대체할 수 있는 경우 ➔ 해당 솔루션을 즉시 도입하고 자체 개발은 최소화함
- **단 하나의 필수 요건이라도 불충족하는 경우 ➔ 해당 미충족 항목을 자체 개발의 당위성 근거로 활용**하고 관련 기능을 고도화함
- **실증 데이터에 기반한 하이브리드(혼합) 채택 결론 역시 정당한 아키텍처 판정 결과로 인정함**

---

## 7. 향후 과제 및 미결 항목

- 개별 Toolset의 세부 Configuration Key 정보 확정 및 가이드화
- Ollama 외 Tool-calling을 지원하는 로컬 서빙 프레임워크(vLLM 등) 검토를 통한 온프레미스 수용 가능성 재평가

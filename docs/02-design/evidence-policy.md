# 근거 표기 규약 — 근거 기반 문서 작성 및 상태 구분 가이드

본 프로젝트의 문서 내 모든 기술적 주장에는 **출처 및 근거 표기**를 명시합니다. 이는 검증된 기술 사실, 소스 코드 기반 확인 내용, 추후 반영할 제안 항목을 명확히 구분하여 문서 전체의 신뢰성을 확보하기 위함입니다.

---

## 1. 근거 표기 3종 및 검증 상태 정의

| 표기 유형 | 정의 및 의미 | 검증 및 확인 방법 |
|---|---|---|
| `[문서]` | 제품 공식 스펙 또는 표준 문서 기반 검증 완료 | 관련 URL 또는 공식 문서 경로 명시 |
| `[코드]` | 소스 코드 및 설정 파일 직접 검증 완료 | 파일 경로:행 번호 또는 실행 결과 로그 명시 |
| `[제안]` | 아이디어 단계의 미구현 항목 | 기술적 근거가 존재하더라도 구현 전 상태로 기술 |

기술 검증 상태는 **검증됨** / **확인됨** / **미확인** / **근거 미발견**의 4가지 단계로 구분하여 정리합니다.

- **미확인:** 아직 조사를 수행하지 않은 상태
- **근거 미발견:** 조사를 수행했으나 관련 근거를 찾지 못한 상태 (단정적인 "없음" 표기 금지)

## 2. 규약 도입 배경 (가설 검증 실패 사례)

프로젝트 진행 중 사전 가설이 공식 검증 과정을 통해 기각된 대표적 사례는 다음과 같습니다:

- **가설 1: "실환경 DNS 인프라는 질의 세부 내용을 관측할 수 없다."**  
  ➔ **기각:** dnsdist가 단일 질의 단위 관측을 위한 5가지 네이티브 수집 경로를 기본 제공함을 확인했습니다 ([ADR-004](decisions/adr-004-suricata-defer.md) 참조).
- **가설 2: "Wazuh FIM 기능을 활성화하면 레벨 11 알림이 대량 발생하여 Slack에 과부하를 준다."**  
  ➔ **기각:** 공식 문서의 "11 = Integrity checking warning"은 레벨 정의일 뿐이며, 실제 FIM 룰 레벨은 5~7 수준이었습니다. 실제 문제는 알림 폭증이 아닌 수집 누락 현상이었습니다 ([severity-normalization §3-4](severity-normalization.md) 참조).
- **가설 3: "HolmesGPT는 Kubernetes 전용 솔루션이므로 본 인프라 스택과 호환되지 않는다."**  
  ➔ **기각:** 공식 스펙상 온프레미스 VM, 베어메탈, 클라우드 환경을 모두 공식 지원함을 확인했습니다 ([ADR-002](decisions/adr-002-holmesgpt.md) 참조).

모두 타당해 보이는 가설이었으나, 공식 문서 검증 과정을 통해 사실이 아님이 입증되었습니다. 이에 따라 모든 기술적 주장에 대한 명확한 근거 표기 규약을 적용합니다.

## 2-1. 중복 제안 방지 규약 (2026-08-06 추가)

위 사례들이 **주장의 근거**에 관한 것이라면, 아래는 **제안의 신규성**에 관한 것입니다.

**발생 사례:** 2026-08-06 후속 과제 도출 과정에서 제안 항목의 상당수가 이미 구현·문서화된 상태였습니다 — 마스킹 이그레스 프록시(`masking/` 구축 및 실측 완료), 브리지 룰 마이닝 도구(`bot/bridge_miner.py`, 실환경 측정 완료), 자기감시 및 자동화 후보 과제(발표자료 Part 5·부록 4 기재). 외부 문서 조사는 수행했으나 **저장소 및 기존 산출물 확인을 선행하지 않은 것이 원인**입니다.

**적용 규약 — 제안 전 확인 순서를 고정합니다.**

1. **저장소 확인** — 해당 기능의 구현체·설정·도구가 이미 존재하는지 파일 탐색으로 확인
2. **기존 산출물 확인** — 인수인계 문서, 설계 문서, 발표자료에 이미 기재된 항목인지 대조
3. **외부 조사** — 공식 문서 및 타사 사례 조사
4. **제안** — 위 세 단계를 거친 뒤에만 신규 항목으로 기술

**표기 의무:** 모든 제안 항목에는 `[코드]` / `[문서]` / `[제안]` 등급을 부여하여, 확인을 거친 내용과 미확인 내용을 문서상에서 구별할 수 있게 합니다.

**용어 사용 기준:** "고도화"는 **현재 수행 불가능한 기능이 신규로 가능해지는 경우**에만 사용하고, 기존 동작의 오류 수정은 "개선"으로 구분합니다. 명칭 혼용은 과제 규모와 성격을 왜곡합니다.

## 3. 수치 및 지표 작성 규약

1. **비율 및 구조 지표 중심 기재:** 공개 문서에는 **비율·분포·구조 정보**만 기재합니다. (특정 조직 식별이 가능한 호스트 대수, 총 이벤트 수 등 절대 모수 데이터는 기재 금지)
2. **측정 기간(Time Window) 명시:** 실행 시점에 따라 측정 데이터가 변동되므로 측정 창을 반드시 병기하며, **서로 다른 측정 기간의 수치를 단일 문장에 혼용하지 않습니다.**
3. **용어 정의의 명확화:** "이벤트 발생 건수 (트리거 발화)"와 "알림 발송 건수"는 개별 조건 필터링에 따라 결과값이 다르므로 명확히 구분하여 작성합니다.
4. **재산출 가능성 보장:** 수치 데이터는 원본 데이터 기반으로 재산출이 가능해야 하며, 측정 유틸리티의 원시 로그(Raw Log)를 보관합니다.
5. **환경 구별 표기:** 랩 환경의 실측값과 운영 환경의 수치 데이터를 엄격히 구별하여 표기합니다.

## 4. 문서 상태 및 한계 기술 규약

- **완료 표기 지양:** 작업 상태는 **랩 실증** / **코드 존재·미실증** / **미구현**의 3가지 상태로만 구분하며, 모호한 "완료" 표현은 사용하지 않습니다.
- **가변적 수치 고정 금지:** 셀프테스트 통과 건수 등 커밋에 따라 변동되는 수치는 작성 시점 재산출 또는 "명령 실행을 통한 실시간 확인" 형태로 기재합니다.
- **의도적 미구현과 한계점의 구별:** 의도적 설계 판단으로 제외된 항목과 기술적 한계로 구현하지 못한 항목을 명확히 구별하여 기재합니다 ([limits.md §4](../03-pitfalls/limits.md) 참조).

## 5. 검증 상태 표 작성 예시

문서 말미에는 아래와 같이 검증 상태 표를 첨부하여 기술 검증 상태를 명시합니다:

| 기술적 주장 및 명제 | 출처 구분 | 검증 상태 |
|---|---|---|
| Zabbix 내 `forecast()`, `timeleft()` 예측 함수 존재 | 문서 | 검증됨 |
| 현행 봇 파이프라인 내 예측 기능 미탑재 | 코드 | 확인됨 |
| Grafana ML Forecasting 기능의 Cloud 전용 제공 여부 | 문서 | 검증됨 |
| Keep의 최근 90일 만성 장애 랭킹 네이티브 제공 여부 | 문서 | **근거 미발견** (단정적 미제공 표기 아님) |
| `countOutput` 옵션을 통한 정확한 개수 취득 가용 여부 | 문서 | **미확인** |
| 만성 장애 자동화 후보 랭킹 산출 기능 | 제안 | **미구현** |

*단, '검증됨' 및 '확인됨' 상태의 항목만 확정된 사실로 진술하며, '제안' 항목은 정직하게 로드맵 과제로 구분하여 작성합니다.*

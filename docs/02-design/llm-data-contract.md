# LLM 전송 데이터 계약 — 외부 LLM 데이터 반출 및 통제 명세

본 문서는 외부 LLM(Large Language Model) 서비스로 전송되는 데이터 항목 및 보안 통제 정책을 정의하는 Single Source of Truth (Owner) 명세서입니다. 본 문서의 정의를 바탕으로 구현 코드(`bot/gateway/masking.py`, `bot/gateway/collector.py`)가 동작하며, 셀프테스트 검증을 통해 문서와 코드 간의 정합성을 유지합니다.

---

## 1. 데이터 통제 3대 원칙

1. **단일 반출 경로 (Single Egress Gateway):** 외부 LLM 통신은 게이트웨이 모듈 한 곳에서만 전담하여 수행합니다. 수집 에이전트, Zabbix, Wazuh 등 개별 관측 시스템의 외부 직접 통신을 원천 차단합니다.
2. **화이트리스트 기반 직렬화 (Whitelist-based Serialization):** 명시적으로 허용된 필드만 직렬화하여 전송합니다 (`build_llm_context` 함수 기반). 허용 목록에 포함되지 않은 데이터는 코드 구조상 전송이 불가능하여 유출 가능성을 근본적으로 차단합니다.
3. **양방향 가명화 (Bi-directional Anonymization):** 주요 식별자(호스트명, IP, 그룹명)는 `[host-1]` 형태의 가명 토큰으로 치환하여 외부 전송합니다. 회신 데이터 수신 시 게이트웨이가 토큰을 역치환하여 Slack에 실명으로 출력합니다. (가명 매핑 정보는 게이트웨이 프로세스 메모리에만 국한되어 존재합니다. 단 **역치환이 끝난 분석 결론 원문은 판정 이력 저장소에 실명으로 보관**됩니다 — 아래 4절.)

## 2. 전송 허용 데이터 명세 (화이트리스트)

| 전송 항목 | 데이터 예시 | 데이터 처리 및 통제 방식 |
|---|---|---|
| **알림명** | `Filesystem /data 사용률 92% on [host-1]` | 호스트명 부분 가명화 처리 |
| **통합 심각도** | `SEV2` | 원본 유지 (통합 표준 눈금) |
| **발생 시각** | Unix Timestamp | 원본 유지 |
| **호스트 식별자** | `[host-1]` | **가명화 처리** |
| **호스트 그룹** | `[group-1]` | **가명화 처리** (MSP 고객사 식별 정보 보호) |
| **트리거 설명 및 조건식** | `last(/[host-1]/vfs.fs.size[...])>90` | 조건식 내부 호스트 식별자 가명화 처리 |
| **메트릭 키·단위·추이** | `vfs.fs.size[/data,pused]`, `%`, 수치 배열 | 원본 유지 (비식별 지표 수치 데이터) |
| **로그 라인 (Loki)** | `{t, line, why, n}` — `{"t":1700000000, "line":"... [host-1] backup from [ip-2]", "why":"error", "n":137}` | 라인 내 호스트명·IP 가명화 + **라인당 300자 제한**. 수집 상한과 전송 상한을 분리함 — 창에서 최대 300줄(또는 누적 2MB)을 조회하고 그중 40줄을 선별하여 전송. `why`(선별 사유)와 `n`(같은 형태의 창 내 총 건수)을 함께 전송함 — 미전송 시 모델이 선별된 표본을 창 전체로 해석하고, 반복 발생을 단건으로 읽음. **비교용 정규화 형태는 전송하지 않음**(아래 차단 항목) |
| **보안 경보 (Wazuh)** | `{level:10, desc:"brute force on [host-1]"}` | 설명 항목 내 식별자 가명화 + **최대 20건 제한** |
| **보안 경보 규칙 식별자** | `{rule_id:"550", groups:"syscheck,pci_dss_11.5"}` | 원본 유지 — 비식별 공통 사양 (규칙 번호 및 그룹명). 봇이 보안 이벤트 유형을 인지하여 노이즈성 변경과 유의미한 변경을 구별하기 위한 필수 정보 |
| **파일 변경 경로 (FIM)** | `syscheck.path` ➔ `/etc/ssh/sshd_config`<br/>`syscheck.event` ➔ `modified` | **경로 문자열 가명화 필터 적용** — 경로 내 호스트명·IP 포함에 따른 유출 방지 |
| **선판정 결과** | `신규 — 최근 90일 내 발생 이력 없음...` | 원본 유지 (코드 기반 자동 생성 문장) |
| **교차 소스 조회 상태** | `{"logs":"ok","security":"unavailable"}` | 원본 유지 — 지정 상태 문자열 3종(`ok`/`unavailable`/`disabled`)만 허용하며, 기타 미정의 값은 `unknown`으로 강등 처리 |
| **로그 수집·전송 범위** | `logs_fetched: 263`, `logs_selected: 40`, `logs_fetch_capped: false`, `logs_clipped: 2` | 원본 유지 — 수치·불리언. 조회 상태(`ok`)만으로는 전량 수집과 상한 절단이 구분되지 않으므로, 미전송 시 모델이 실린 범위의 부재를 사실의 부재로 해석함. **한 필드에 두 의미를 담지 않음** — 창에서 몇 줄을 읽었는지(`fetched`), 그중 몇 줄을 보냈는지(`selected`), 조회 자체가 상한에 닿았는지(`fetch_capped`)를 각각 전달함 |
| **위탁 계약 제약** | `scope: "notify_only"` | 원본 유지 — 고정 라벨이며 식별자를 포함하지 않음. 미전송 시 조치가 금지된 고객사 사건에도 시스템 변경 권고가 생성됨(실행은 라우팅에서 차단되나 담당자에게 전달되는 문장은 통제되지 않음) |
| **자동 조치 등록 여부** | `automate: false` | 원본 유지 — 불리언. 회신 형식이 "자동 조치 가능 여부"를 요구하므로, 미전송 시 모델이 근거 없이 추정함 |
| **과거 분석 결론 (구조화)** | `{match:"동일 사건", verdict:"만성", days_ago:12, 확인:"미확인(봇 출력)"}` | 원본 유지 — 자유 서술이 없는 구조화 필드이며 식별자를 포함하지 않음. 매칭 강도와 사람 검증 여부를 함께 전송하여 모델이 과거 판정의 신뢰도를 구분하도록 강제 |
| **과거 분석 결론 (본문)** | `2일 전 결론: [host-1] 상류 지연` | **조건부 전송** — `GATEWAY_PRIOR_MODE=full` + 사람이 정답으로 확인한 결론 + 전역 이름 표 보유 + 가명화 후 잔여 식별자 검사 통과 시에만 전송. 하나라도 미충족 시 본문을 제외하고 구조화 필드만 전송(Fail-closed). 최대 2건 · 건당 600자 |

> **교차 소스 조회 상태 통제 목적:** "시스템 장애로 인한 조회 실패"와 "실제 보안 신호 없음" 상태를 구별하지 않을 경우, Wazuh Indexer 장애 시 봇이 "침해 흔적 없음"으로 잘못 단정하는 오류가 발생하므로 해당 조회의 상태 구별을 계약 수준에서 강제합니다.

## 2-1. 로그 선별 규칙 (무엇을 보내고, 무엇을 접고, 무엇을 안 보내는가)

한 사건에 실을 수 있는 로그 분량이 제한되어 있으므로 선별이 필요합니다. 아래는 그 규칙
전체이며, 구현은 `bot/gateway/collector.py` 의 `select_logs`·`log_level`·`log_shape` 입니다.

### 2-1-1. 읽는 범위

| 항목 | 값 | 설명 |
|---|---|---|
| 시간 구간 | 장애 발생 시각 기준 **뒤로 15분** | 게시 시각이 아니라 장애 시각 기준임 |
| 대상 | 그 서버의 **모든 로그** | 내용으로 미리 거르지 않음 |
| 읽는 상한 | **300줄 또는 2MB** 중 먼저 닿는 쪽 | 상한에 닿으면 `logs_fetch_capped` 를 참으로 전달함 |
| 줄 길이 | **300자**까지 | 초과분은 잘리며 잘린 줄 수를 `logs_clipped` 로 전달함 |
| 보내는 상한 | **40줄** | 이 40줄을 아래 규칙으로 고름 |

### 2-1-2. 보내는 로그 — 네 몫으로 나눠 선택

읽어 온 300줄 중 40줄을 아래 배분으로 고릅니다. 어떤 몫이 배정을 다 쓰지 못하면 남은
자리는 버리지 않고 다음 몫으로 넘어갑니다.

| 선택 사유(`why`) | 배정 | 선택 대상 | 선택 이유 |
|---|---|---|---|
| `error` | 14줄 | 심각도가 오류로 판정된 줄 | 무슨 오류가 났는지 |
| `novel` | 8줄 | 심각도가 경고로 판정된 줄 | 오류 직전의 이상 징후 |
| `pre` | 12줄 | 첫 오류 **직전**의 연속된 줄(심각도 무관) | 왜 났는지. 오류에 가까운 쪽부터 선택함 |
| `recent` | 6줄 | 구간의 마지막 줄부터(심각도 무관) | 현재 상태가 어떤지 |
| `all` | — | 구간이 40줄 이하일 때 전부 | 고를 필요가 없는 경우 |

**심각도가 낮은 로그가 제외되는 구조가 아닙니다.** `pre` 와 `recent` 는 심각도를 보지
않으므로 정보성 로그가 이 자리로 들어옵니다. 오류에게는 자리를 보장할 뿐입니다.

### 2-1-3. 접는 로그 — 같은 모양은 3줄까지, 대신 개수를 함께 전달

같은 모양의 줄은 최대 3줄만 싣고, **그 모양이 읽어 온 범위에 몇 개 있었는지를 `n` 으로
함께 보냅니다.** 접기만 하고 개수를 안 보내면 260줄이 3줄로 줄어든 사실이 드러나지
않습니다.

"같은 모양"은 아래 값을 지운 뒤 비교해 판정합니다.

| 지우는 값 | 예 |
|---|---|
| 시각 | `2026-08-13 10:00:00` · `2026/08/13 10:00:00` · `Aug 13 10:00:00` · `13/Aug/2026:10:00:00` · `2:13:33` |
| 날짜 단독 | `2026-08-13` |
| IP 주소 | `10.0.0.5` |
| UUID | `550e8400-e29b-...` |
| 8자 이상 16진수 | `a1b2c3d4e5` |
| 4자리 이상 숫자 | `123456` |
| 크기·소요시간 | `57ms` · `1.2MB` |
| `이름=숫자` 형태의 값 | `retry=0` · `pid=41` |
| 경로의 숫자 구간 | `/v1/pay/151` → `/v1/pay/<N>` |

**지우지 않는 값**과 그 이유는 다음과 같습니다. 이 값들이 지워지면 서로 다른 사건이 같은
모양으로 합쳐집니다.

| 지우지 않는 값 | 예 | 지우면 생기는 문제 |
|---|---|---|
| HTTP 상태 코드 | `GET /a 500` vs `GET /a 200` | 오류 줄과 정상 줄이 같은 모양이 되어 선별이 무의미해짐 |
| 오류 번호 | `errno=1062` vs `errno=1236` | 중복 키 오류와 릴레이 로그 손상이 같은 사건으로 합쳐짐 |
| 종료 코드·신호 번호 | `sig=9` vs `sig=11` | 강제 종료와 메모리 접근 위반이 합쳐짐 |
| 사용자 번호 | `uid=0` vs `uid=1000` | 관리자 작업과 일반 사용자 작업이 합쳐짐 |
| 경로의 디렉토리 이름 | `/etc/shadow` vs `/tmp/junk` | 보안 관련 판단이 무너짐 |

이 비교용 형태는 **내부 계산에만 쓰이며 전송하지 않습니다.**

### 2-1-4. 안 보내는 로그 — 자리는 남기고 개수와 시간 범위를 전달

선택되지 않은 줄은 전송하지 않되, 빠진 자리마다 아래 항목을 넣습니다.

```json
{"t": 1786583812, "gap": 180, "to": 1786583844}
```

"이 자리에서 180줄이 빠졌고 그 구간은 32초"라는 뜻입니다. 이것을 넣지 않으면 모델이
떨어져 있는 두 줄을 이어진 기록으로 읽고 인과 관계를 만듭니다.

**전송한 줄 수와 생략한 줄 수의 합은 읽어 온 줄 수와 같습니다.** 무작위 입력 300회로
이 조건을 검사합니다.

### 2-1-5. 심각도 판정 기준

세 갈래로 판정하며, 앞의 둘은 대소문자를 가리지 않고 마지막은 대문자만 인정합니다.

| 순서 | 대상 | 예 |
|---|---|---|
| 1 | 등급 필드 | `level=error` · `{"severity":"ERROR"}` · `{"lvl":"error"}` |
| 2 | 괄호 안 | `[error]`(nginx) · `[core:error]`(Apache) |
| 3 | 문장 속 **대문자** 낱말 | `... ERROR connection reset` |

`alert` · `crit` · `emerg` 는 3번 경로에서 제외합니다. 이 환경에서는 게이트웨이와 Keep과
Zabbix 가 평상시에 쓰는 낱말이므로, 인정하면 `alert manager started` 같은 정상 줄이 오류
자리를 차지합니다.

심각도 낱말이 없어도 아래 문구는 오류로 봅니다. 문구는 공식 소스로 확인했습니다.

`Out of memory: Kill` · `oom-kill` · `segfault` · `Failed to start ` ·
`Failed with result '` · `Dependency failed for ` · `Timed out starting ` ·
`I/O error` · `EXT4-fs error`

**판정하지 못하면 미상으로 두며, 미상을 오류로 올리지 않습니다.**

### 2-1-6. 이 규칙의 한계

- 배정 값(14/8/12/6)·같은 모양 상한(3줄)·읽는 상한(300줄)은 **모두 랩 기준으로 정한
  임의값**입니다. 실환경 측정 후 재산정해야 합니다(§2-5-3).
- 창 한가운데에 한 번만 나타난 정보성 로그는 선택 순위가 낮습니다. 평상시 기록과 비교해
  "평소에 없던 줄"을 가려내는 기능이 붙기 전까지는 이 한계가 남습니다.
- `LOG_SELECT_ENABLED=0` 으로 선별을 끄면 종전 동작(최신 40줄)으로 돌아갑니다.

## 3. 전송 차단 데이터 명세 (명시적 차단 항목)

- **모든 종류의 자격 증명 (Credential):** Zabbix 토큰, 게이트웨이 인증 토큰, SNMP Community, 계정 비밀번호 등
- **식별자 원문 데이터:** 호스트명, 공인/사설 IP 주소, 고객사명 원문 (가명 토큰으로 전면 치환)
- **개인식별정보 (PII):** 사용자 계정명, 이메일 주소, Slack 채널명 등
- **화이트리스트 외 메타데이터:** Zabbix 이벤트/트리거 메타데이터 중 허용 목록에 포함되지 않은 전체 항목
- **로그 원문 데이터:** 마스킹 필터링, 글자 수/줄 수 제어, 최근 15분 시간 창(Window) 제어를 통과하지 않은 원문 로그 전송 차단
- **로그 선별용 내부 값:** 정규화 형태(비교 키), LogQL 질의문, 조회 커서 등 선별 과정에서만 사용하는 값. 전송 대상은 마스킹된 원문이며 내부 값은 화이트리스트에 포함하지 않음

## 4. 데이터 학습 및 보존 정책

- **모델 학습 제외 (No-training Policy, 확정):**  
  Anthropic Commercial Terms (2025-06-17 발효) Section B "Customer Content" 조항 준수:  
  *"Anthropic may not train models on Customer Content from Services."*  
  API 입출력 데이터는 모델 학습 목적으로 활용되지 않음이 상용 계약 조항으로 명시되어 있습니다 ([Anthropic Commercial Terms](https://www.anthropic.com/legal/commercial-terms) 참조).
- **로컬 보관 (판정 이력 저장소):**  
  역치환이 끝난 **분석 결론 원문은 게이트웨이 로컬 SQLite 에 실명으로 보관**됩니다(`GATEWAY_STORE_FILE`). 전송 대상이 아니라 사후 측정과 과거 결론 연계(`bot/GATEWAY_GUIDE.md` §25-6)의 재료입니다. 통제는 다음과 같습니다 — 파일 권한 `0600`(디렉토리 `0700`), 서술 보관 30일(행 자체는 90일)로 **서술을 먼저 삭제**, 프롬프트 원문은 미보관(결론만 보관). 이 원문을 다시 외부로 보낼 때는 마스킹을 재수행하며, 가명화 후 잔여 식별자가 검출되면 본문을 전송에서 제외합니다.
- **데이터 보존 기간 (Data Retention, 검토 중):**  
  조직 설정 및 적용 모델별 요구사항이 상이합니다. 프로덕션 도입 시점에 관제 조직 콘솔의 보존 설정 및 최신 정책 문서를 검증하여 확정합니다. (*현재 시점 기준: "학습 불가 규정은 계약으로 확정, 보존 기간은 확정 절차 진행 중"으로 정의함*)

## 5. 장애 및 폴백(Fallback) 상황 대응 정책

- **Ollama 폴백 (온프레미스 내장 모드):**  
  외부 데이터 전송 건수 0건. 동일한 마스킹 파이프라인을 거쳐 사내 내부망으로 전달되므로, 보안 정책 강화 시 **즉시 전환 가능한 대안 경로**로 활용합니다.
- **열화(Degraded) 모드 (LLM 불통 상황):**  
  외부 데이터 전송 건수 0건. 코드 기반 선판정 문장만 수집하여 회신합니다.

## 6. 데이터 반출 검증 방법

```bash
cd bot
# 전송 전문 내 원문 호스트명·IP·고객그룹 및 미허용 필드 포함 여부 자동 검증
```

`gateway.llm` 실행을 통해 실제 외부로 반출되는 데이터 전문 및 내부 가명화 매핑 상태를 시각적으로 검증할 수 있습니다.

# 규칙 전수 — 무엇이 규칙이고 무엇이 아닌가

"규칙이 판정하고 LLM은 설명만 한다"고 말합니다. 그런데 **"규칙"이라는 말을 두 가지 뜻으로
섞어 쓰기 쉽습니다.** 여기서 한 번 정리합니다. 근거는 전부 `bot/gateway/` 코드입니다.

---

## 0. 먼저 — 규칙이 아닌 것

**열화(`degraded`)는 규칙이 아니라 입력값입니다.**

"규칙이 열화를 평가한다"고 쓰면 틀립니다. 열화는 평가의 **대상**이 아니라, LLM 어댑터가
호출을 마친 뒤 **돌려주는 관측 사실**입니다. 규칙은 그 사실을 **읽고** 다음 행동을 정합니다.

### 열화의 정확한 정의

**`degraded = True`는 "AI 문장이 하나도 없이 나갔다"는 뜻입니다.**

어댑터는 Claude → Ollama 순으로 시도하고, 둘 다 못 쓰면 코드 판정만 문장으로 만들어 회신합니다.

```
(LLM 분석 불가 — 코드 판정만 회신)
2건 병합 사건 — 동일 호스트 · 41s 관측창 · 2건 · 알려진 인과 조합
```

**이렇게 되는 경우** — 타임아웃, 429·529, **크레딧 소진**(실제 발생), API 키 미설정,
Ollama 미배선. 예외 종류를 가리지 않고 전부 다음 어댑터로 넘깁니다.

**Claude가 실패해도 Ollama가 답하면 `degraded = False`입니다.** 열화는 "주 경로 실패"가 아니라
**"전부 실패"** 입니다. 그래서 이 플래그는 곧 "사람이 받은 카드에 원인 설명이 없다"와 같은
말입니다.

**중요한 성질 — 봇은 죽지 않습니다.** 열화돼도 카드는 나가고 병합·만성/신규 판정은 그대로
실립니다. 판정이 규칙에 있기 때문입니다. **다만 그래서 조용히 얕아집니다** — 크레딧이 떨어졌을
때 동작이 유지되는 바람에 인지가 늦었습니다. 그 사실을 심층조사 발동 조건으로 쓴 것이 §2-3의
4번 조건입니다.

입력값과 규칙을 갈라 두면 이렇게 됩니다.

| | 예 | 성격 |
|---|---|---|
| **입력(사실)** | 소스, 원본 심각도, 트리거 태그, 이벤트 값, 호스트, 시각, `degraded`, 조회 성공/실패(`sources`) | 바깥에서 들어오거나 실행 결과로 관측된 것 |
| **판정 규칙** | 정규화, 분류, 병합, 만성/신규 | 사실로부터 **새 사실**을 만드는 것 |
| **게이트 규칙** | 경로 결정, LLM 발동, 심층조사 발동, 승인 | 사실과 판정을 조합해 **다음 행동**을 정하는 것 |

**LLM은 셋 어디에도 없습니다.** 판정이 다 끝난 뒤 설명만 씁니다.

### 그런데 왜 열화가 심층조사 조건에 있나

**우리 1차 분석의 품질이 떨어졌다는 사실 자체가 조사 필요 신호**이기 때문입니다. AI 없이 규칙
결과만 나갔으면 사람이 받은 정보가 얕습니다. 그 공백을 더 비싼 도구로 메우는 것이 맞습니다.

바꿔 말하면 **봇이 못 하면 심층 조사가 대신 봅니다.** 그래서 이 조건은 만성 억제보다 **앞**에
있습니다 — 아는 문제든 모르는 문제든, 우리가 제대로 못 봤으면 봐야 합니다.

## 1. 판정 규칙 — 사실에서 새 사실을 만든다

### 1-1. 심각도 정규화 (`severity.normalize`)

세 시스템이 서로 다른 눈금을 씁니다. 하나로 접습니다.

| 원본 | 규칙 |
|---|---|
| 사내 Zabbix 0~5 | `5→SEV1, 4→SEV2, 3→SEV3, 2→SEV4, 1→SEV4, 0→NONE` |
| MSP Zabbix 0~5 | `5→SEV1, 4→SEV2, 3→SEV3, 2→SEV3, 1→SEV4, 0→NONE` |
| Wazuh 0~15 | `14+→SEV1, 10+→SEV2, 7+→SEV3, 3+→SEV4, 그 미만→NONE` |

**핵심은 Warning(2)의 비대칭입니다.** 사내 Warning은 SEV4, MSP Warning은 SEV3.
사내 Warning이 99.5%를 차지하는 노이즈인 반면 MSP Warning은 고객이 보는 신호라서 같은 값이
아닙니다.

Wazuh 10을 SEV2에 둔 것은 **팀의 현행 컷라인을 그대로 보존**하기 위해서입니다. 우리가 임계를
새로 정한 것이 아닙니다.

미지 입력은 **SEV2 페일세이프** — 놓치는 것보다 시끄러운 쪽으로 넘깁니다.

원본 표는 [`severity-normalization.md`](severity-normalization.md).
**표를 고칠 때 문서를 먼저 고치고 코드를 따라갑니다.**

### 1-2. 통보 컷 (`severity.notifies`)

`SEV1`·`SEV2`만 Slack으로 갑니다. SEV3는 요약, SEV4는 대시보드에만 남습니다.

### 1-3. 사건 분류 (`incident.classify`)

알림 하나를 유형 하나로 접습니다. `replication` / `cpu_io_pressure` / `auth_security` /
`disk_space` / `memory_pressure` / `service_*` / `network` / `other`.

**순서가 중요합니다 — 선언이 문자열을 이깁니다.**

1. Zabbix 트리거 태그 `class=` 가 있으면 그것을 씁니다
2. 없으면 Wazuh `rule.groups` 를 봅니다
3. 그것도 없으면 알림 이름 키워드로 추정합니다

3번은 폴백이지 본체가 아닙니다. 실환경 태그 사용률이 사실상 0에 가까워 지금은 대부분 3번을
타지만, **팀이 태그를 붙이면 코드를 안 고쳐도 분류가 정확해집니다.** 그게 이 계층을 둔 이유입니다.

### 1-4. 병합 (`incident_key` + `BRIDGE_GROUPS`)

기본 키는 **(호스트, 유형)**. 같은 호스트에서 같은 유형이면 한 사건입니다.

다른 유형이라도 **인과가 알려진 조합**이면 묶습니다.

```python
BRIDGE_GROUPS = [
    frozenset({"replication", "cpu_io_pressure"}),   # 자원 경합이 복제를 민다
    frozenset({"disk_space", "service_down"}),       # 디스크가 차서 서비스가 죽는다
]
```

**`auth_security`는 어느 조에도 없습니다.** 보안은 다른 축과 자동으로 묶이지 않습니다 —
"CPU가 튀는 동시에 로그인 실패가 있었다"를 인과로 단정하면 안 되기 때문입니다.

브리지 조끼리 겹치면 **기동할 때 예외로 죽습니다**. 첫 매칭을 반환하는 구조라 겹치면 뒤 조가
죽은 코드가 되는데, **조용히 죽는 것보다 못 뜨는 편이 낫습니다.**

### 1-5. 창 마감 (디바운스)

언제까지 기다렸다가 "이게 한 사건이다"라고 확정할지.

| 값 | 기본 | 뜻 |
|---|---|---|
| `INCIDENT_DEBOUNCE_S` | 90초 | 마지막 알림 뒤 이만큼 조용하면 마감 |
| `INCIDENT_MAX_WINDOW_S` | 300초 | 알림이 계속 와도 여기서 자른다 |
| `INCIDENT_PRIORITY_DEBOUNCE_S` | 15초 | SEV1은 짧게 기다린다 |
| `INCIDENT_MAX_ALERTS` | 20건 | 한 사건에 담을 상한 |

**30초를 재는 기준이 여기서 나옵니다.** 첫 알림이 아니라 **창이 닫힌 시점**부터 잽니다.
상관 시스템이 사건을 확정하는 방식과 같습니다.

### 1-6. 만성/신규 선판정 (`prejudge.judge`)

같은 트리거가 **90일 안에 몇 번 발생했는지**를 셉니다. 현재 이벤트는 뺍니다.

| 발생 수 | 판정 |
|---|---|
| 0회 | **신규** |
| 1~4회 | 재발 |
| 5회 이상 | **만성** |

기준값은 환경변수입니다. 5회는 MSP 만성군이 수십 회 반복하는 실측에서 잡았습니다.

**한계 — Wazuh 알림에는 이 판정이 안 붙습니다.** Zabbix 트리거 ID로 이력을 세는데 Wazuh
알림엔 그게 없습니다. 그래서 보안 축만으로 이뤄진 사건은 판정이 **미상**이 되고, 만성 억제도
신규 발동도 타지 않습니다. **알려진 갭입니다.**

### 1-7. 사건 판정 접기 (`dominant_verdict`)

알림이 여럿이면 판정도 여럿입니다. 하나로 접습니다.

- **하나라도 신규면 신규** — 모르는 것이 섞여 있으면 조사 가치가 있습니다
- **전부 만성이면 만성**
- 그 사이는 재발
- 전부 비어 있으면 카드에 **미상**으로 표시

**보수적인 쪽으로 접습니다.** 아는 문제 9개에 모르는 문제 1개가 섞이면 그건 모르는 사건입니다.

## 2. 게이트 규칙 — 다음 행동을 정한다

### 2-1. 경로 결정 (`router.decide`)

```
event_value == 0        → resolve          (해소 알림)
SEV == NONE             → drop
SEV4                    → dashboard_only
SEV3                    → digest
SEV1·SEV2 +
  automate 태그 있음 +
  scope != notify_only  → remediate        (데모 B — 조치 후보)
그 외 SEV1·SEV2         → triage           (데모 C — 초동 분석)
```

**`scope`가 `automate`를 이깁니다.** 조치 플레이북이 지정돼 있어도 계약이 `notify_only`면
조치 경로를 안 탑니다. **MSP 계약 제약을 코드로 굳힌 지점입니다.**

### 2-2. LLM 트리아지 발동 (`incident.should_triage`)

값비싼 LLM을 언제 부를지. **위에서부터 처음 걸리는 것으로 결정합니다.**

| 조건 | 결과 |
|---|---|
| SEV1 | 발동 — 위중하면 무조건 |
| 병합됨(2건+) | 발동 — 교차 축이 있다 |
| 로그·보안 **조회 실패** | 발동 — 신호 없음이 아니라 **미상** |
| 단일 알림 + 교차 소스 1종 이상 | 발동 |
| 그 외 | 스킵 |

**세 번째 줄이 핵심입니다.** 조회 실패를 "신호 없음"으로 읽으면 **관측 백엔드가 죽을수록
봇이 조용해집니다** — 가장 필요할 때 침묵합니다. 그래서 실패는 미상으로 보고 보수적으로
발동합니다.

**미배선(`disabled`)은 발동 사유가 아닙니다.** 안 붙인 것은 의도된 구성이지 고장이 아닙니다.

### 2-3. 심층조사 발동 (`holmes.should_investigate`)

**순서에 의미가 있습니다.**

| # | 조건 | 결과 | 왜 이 자리인가 |
|---|---|---|---|
| 1 | 기능이 꺼져 있음 | 미발동 | 아예 안 쓰는 상태 |
| 2 | MSP 알림인데 마스킹 프록시 없음 | **제외** | 원문 반출이 되므로 |
| 3 | SEV1 | 발동 | 위중은 지식 여부와 무관 |
| 4 | 봇 열화 | 발동 | 우리가 제대로 못 봤다 |
| 5 | 판정이 **만성** | **억제** | 반복 확인된 문제 |
| 6 | 판정이 **신규** | 발동 | 지식 공백 = 조사 가치 최대 |
| 7 | 병합된 사건 | 발동 | 마지막 폴백 |

**5·6번이 이 게이트의 본체입니다.** 원래는 7번(병합)이 주 발동 경로였는데, 병합 조합은 사람이
룰로 넣은 것이라 **가장 비싼 분석이 이미 아는 문제에만 돌아가는** 구조였습니다. 그래서 같은
선판정을 양방향으로 씁니다 — **아는 것은 아끼고 모르는 것에 씁니다.**

3·4번이 5번보다 앞에 있는 이유는 위중함과 분석 실패가 지식 여부와 무관하기 때문입니다.
만성이어도 SEV1이면 봅니다.

### 2-4. 승인 게이트 (Keep 워크플로)

**시스템을 바꾸는 일과 고객에게 나가는 일만 사람이 누릅니다.** 조회·분석은 자동입니다.

```yaml
triggers:
  - type: manual                                       # 자동 실행 안 됨 = 승인 게이트
steps:
  - if: "'{{ alert.playbook }}' == 'service_restart'"   # 안전 게이트
```

`manual` 트리거가 **승인 게이트**, `if` 조건이 **안전 게이트**입니다. 둘은 다릅니다 —
앞엣것은 "사람이 눌러야 한다", 뒤엣것은 "엉뚱한 알림에서 눌러도 아무 일 없다"입니다.

같은 형태를 두 번 씁니다. 조치는 `service_restart`, 리포트 발송은 `report_approve`.
**승인 계층을 새로 만들지 않았습니다** — 별도 워크플로 엔진을 더하지 않는 근거가 여기 있습니다.

### 2-5. 조치 후 재검증 (`remediate_service.yml`)

```yaml
failed_when: after.stdout != "active"
```

**조치했다고 말하지 않고 확인한 것만 말합니다.** 재기동 전후로 `systemctl is-active`를 찍고,
after가 `active`가 아니면 플레이북이 실패로 끝납니다.

### 2-6. 리포트 값 게이트

승인 전에는 아이템 값이 **"검토 대기"** 입니다. 예약 발송이 그 사이에 돌아도 검토 안 된 서사가
고객에게 실릴 수 없습니다. **게이트를 발송이 아니라 값에 걸었습니다.**

산출 못 한 값은 `-1`(`NOT_MEASURED`)로 보냅니다. **0으로 보내면 "전부 실패"로 읽히고, 안
보내면 지난 집계 값이 그대로 남습니다** — 둘 다 고객 문서에 틀린 숫자를 만듭니다.

## 3. 반출 규칙

상세는 [`llm-data-contract.md`](llm-data-contract.md). 요약만 둡니다.

- **화이트리스트** — 목록 밖 필드는 구조적으로 전송이 안 됩니다. 빼는 게 아니라 애초에 안 담깁니다.
- **가역 마스킹** — **긴 원문부터 치환**합니다(짧은 이름이 긴 이름의 일부일 때 앞엣것이 먼저
  먹으면 깨집니다). 등록 안 된 IP도 정규식으로 자동 토큰화합니다.
- **멱등** — `(소스, 이벤트 ID, 이벤트 값)`을 1시간 기억합니다. 같은 게 또 오면 `duplicate`로
  **200을 돌려줍니다** — 발송측이 재시도를 멈추게 하려면 에러가 아니라 성공을 줘야 합니다.
  **인메모리라 프로세스가 죽으면 잊습니다.**

## 4. 한 장 요약

```
알림 도착
  ├ 멱등 (중복이면 여기서 끝)
  ├ [판정] 심각도 정규화 ── 세 눈금을 SEV 하나로
  ├ [게이트] 경로 결정 ──── drop / dashboard / digest / remediate / triage
  ├ [판정] 분류 ─────────── 선언 우선, 키워드 폴백
  ├ [판정] 병합 ─────────── (호스트, 유형) + 브리지 조합, 창 마감까지 대기
  ├ [판정] 만성/신규 ────── 90일 이력 개수
  ├ [게이트] LLM 발동? ──── 교차 상관할 게 있을 때만
  │     └ LLM ─────────── 설명만 쓴다. 판정을 뒤집지 않는다
  ├ [게이트] 심층조사? ──── 만성은 아끼고 신규·위중·열화에 쓴다
  └ [게이트] 승인 ───────── 시스템 변경·고객 발송만 사람이 누른다
```

**LLM이 등장하는 곳은 한 군데뿐이고, 그 앞뒤가 전부 규칙입니다.**

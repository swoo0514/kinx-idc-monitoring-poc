# 규칙 정의서 — 판정 규칙, 게이트 규칙 및 시스템 제어 메커니즘

본 문서는 게이트웨이 파이프라인 내에서 적용되는 **규칙(Rule)의 정의, 분류 및 적용 메커니즘**을 정리한 명세서입니다. 본 문서의 기준은 `bot/gateway/` 소스 코드를 바탕으로 작성되었습니다.

---

## 0. 규칙의 분류 및 '열화(Degraded)' 상태의 정의

### 0-1. '열화(Degraded)' 상태의 개념 정의

**열화(`degraded`) 상태는 규칙(Logic)이 아닌 수신/연동 상태의 '입력 속성(Input Attribute)'에 해당합니다.**

열화 상태는 판단 규칙의 대상이 아닌 LLM 어댑터 연산 결과로 반환되는 관측 상태값입니다. 시스템 규칙은 해당 상태값을 참조하여 후속 제어 동작을 수행합니다.

* **`degraded = True` 정의:** "AI 기반 분석 문장이 전혀 포함되지 않은 상태"를 의미합니다.
* **동작 메커니즘:** Claude ➔ Ollama 순서로 폴백 호출을 시도하며, 모든 LLM 호출이 실패할 경우 코드 기반 선판정 결과만으로 요약 문장을 생성하여 회신합니다.

```text
(LLM 분석 불가 — 코드 판정 결과만 회신)
2건 알림 병합 인시던트 — 동일 호스트 · 41초 관측창 · 2건 수집 · 정의된 연관 인과 조합
```

* **발생 원인:** API 타임아웃, Rate Limit (429/529), API 크레딧 소진, 인증 키 미설정, Ollama 서비스 미연동 등
* **`degraded = False` 조건:** 메인 경로(Claude) 실패 후 폴백 경로(Ollama) 호출에 성공한 경우 열화 상태로 간주하지 않습니다. 열화 상태는 **"모든 LLM 파이프라인 실패"**를 의미합니다.
* **시스템 내구성 (Fault Tolerance):** 열화 상태가 발생하더라도 알림 카드는 정상 발송되며, 알림 병합 및 만성/신규 선판정 로직은 정상 유지됩니다. (단, 분석 깊이가 제한되므로 해당 상태 발생 시 심층 조사 발동 조건으로 연계됩니다.)

### 0-2. 데이터 및 규칙의 성격별 구분

| 구분 | 주요 예시 | 성격 및 역할 |
|---|---|---|
| **입력 데이터 (Facts)** | 소스, 원본 심각도, 트리거 태그, 이벤트 값, 호스트명, 시각, `degraded` 플래그, 조회 상태(`sources`) | 시스템 외부에서 수신되거나 실행 결과로 수집된 관측 데이터 |
| **판정 규칙 (Decision Rules)** | 심각도 정규화, 알림 분류, 알림 병합, 만성/신규 선판정 | 관측 데이터 기반으로 **파생 데이터(새로운 사실)**를 생성하는 로직 |
| **게이트 규칙 (Gating Rules)** | 라우팅 경로 결정, LLM 트리아지 발동, 심층 조사 발동, 승인 워크플로 | 관측 데이터와 판정 결과를 조합하여 **후속 제어 동작**을 결정하는 로직 |

*LLM 모듈은 판정 로직이 완료된 후 설명 생성 용도로만 관여합니다.*

## 1. 판정 규칙 (Decision Rules)

### 1-1. 심각도 정규화 (`severity.normalize`)

3개 관측 시스템의 심각도 눈금을 통합 표준 심각도(SEV)로 정규화합니다.

| 수집 소스 및 원본 범위 | 정규화 규칙 (Mapped Severity) |
|---|---|
| **사내 Zabbix (0~5)** | `5 ➔ SEV1`, `4 ➔ SEV2`, `3 ➔ SEV3`, `2 ➔ SEV4`, `1 ➔ SEV4`, `0 ➔ NONE` |
| **MSP Zabbix (0~5)** | `5 ➔ SEV1`, `4 ➔ SEV2`, `3 ➔ SEV3`, `2 ➔ SEV3`, `1 ➔ SEV4`, `0 ➔ NONE` |
| **Wazuh (0~15)** | `14+ ➔ SEV1`, `10+ ➔ SEV2`, `7+ ➔ SEV3`, `3+ ➔ SEV4`, `<3 ➔ NONE` |

* **Warning(2) 심각도의 비대칭 정규화:** 사내 Warning은 노이즈 비중이 높아 `SEV4`로 하향 조정하며, MSP Warning은 고객 노출 지표이므로 `SEV3`를 부여합니다.
* **Wazuh 레벨 10 매핑:** 운영 관제 기준(컷라인)과의 정합성을 위해 `SEV2`로 할당합니다.
* **미정의 입력 예외 처리:** 페일세이프(Fail-safe) 원칙에 따라 `SEV2`로 격상 처리합니다.

*(상세 기준: [`severity-normalization.md`](severity-normalization.md) 참조)*

### 1-2. 통보 컷오프 (`severity.notifies`)

* `SEV1` / `SEV2`: Slack 채널 실시간 알림 카드 발송
* `SEV3`: 요약 대시보드 및 리포트 집계
* `SEV4`: 관측 대시보드 전용 기록

### 1-3. 인시던트 유형 분류 (`incident.classify`)

알림 데이터를 단일 유형으로 분류합니다: `replication` / `cpu_io_pressure` / `auth_security` / `disk_space` / `memory_pressure` / `service_*` / `network` / `other`

**분류 적용 우선순위:**
1. Zabbix 트리거 태그 `class=` 값이 정의되어 있는 경우 최우선 적용
2. Wazuh `rule.groups` 설정값 참조
3. 알림명 키워드 기반 폴백(Fallback) 추정 분류 적용

### 1-4. 알림 병합 (`incident_key` + `BRIDGE_GROUPS`)

* **기본 병합 키:** `(호스트명, 유형)` 조합 단위로 단일 사건 그룹화
* **연관 인과 유형 병합 (Bridge Rules):** 유형이 상이하더라도 인과 관계가 정의된 조합은 단일 사건으로 병합합니다.
  ```python
  BRIDGE_GROUPS = [
      frozenset({"replication", "cpu_io_pressure"}),   # 시스템 자원 경합에 의한 DB 복제 지연
      frozenset({"disk_space", "service_down"}),       # 디스크 용량 초과에 의한 서비스 중단
  ]
  ```
* **`auth_security` 독립성 유지:** 보안 경보는 타 일반 알림과 자동 병합되지 않도록 독립성을 유지합니다.
* **브리지 그룹 중복 방지:** 설정 교차 검증을 통해 구동 시점 예외(Exception)를 발생시켜 무효 코드 생성을 차단합니다.

### 1-5. 디바운스 창 제어 (Debounce Window)

| 파라미터명 | 기본값 | 제어 의미 및 설명 |
|---|---|---|
| `INCIDENT_DEBOUNCE_S` | 90초 | 마지막 알림 수신 후 추가 발생이 없을 때까지 마감 대기 시간 |
| `INCIDENT_MAX_WINDOW_S` | 300초 | 알림이 지속 수신될 때 단일 사건 마감 최대 허용 시간 |
| `INCIDENT_PRIORITY_DEBOUNCE_S` | 15초 | SEV1 긴급 알림 발생 시 단축 대기 시간 |
| `INCIDENT_MAX_ALERTS` | 20건 | 단일 사건 내 수용 가능한 최대 알림 수 |

*30초 처리 지연 시간 KPI 산출 기준점은 첫 알림 발생 시점이 아닌 **디바운스 창 마감 시점**부터 적용됩니다.*

### 1-6. 만성/신규 장애 선판정 (`prejudge.judge`)

동일 트리거의 **최근 90일간 발생 이력 횟수**를 기반으로 판정합니다 (현재 이벤트 제외).

| 발생 횟수 | 선판정 결과 |
|---|---|
| 0회 | **신규 (New)** |
| 1~4회 | **재발 (Recurrent)** |
| 5회 이상 | **만성 (Chronic)** |

*(참고: Wazuh 보안 알림의 경우 전용 트리거 ID 부재로 인해 선판정이 '미상(Unknown)'으로 처리되는 구조적 한계점이 존재합니다.)*

### 1-7. 대표 판정 통합 (`dominant_verdict`)

단일 사건 내 복수 알림의 판정 결과를 보수적 기준으로 통합합니다.

- **신규 알림이 1건이라도 포함된 경우 ➔ 신규로 최종 판정** (조사 필요성 부여)
- **전체 알림이 만성 알림인 경우 ➔ 만성으로 최종 판정**
- 기타 상황 ➔ 재발 또는 미상으로 구별 표기

## 2. 게이트 규칙 (Gating Rules)

### 2-1. 경로 결정 및 라우팅 (`router.decide`)

```text
event_value == 0        ➔ resolve          (장애 해소 알림)
SEV == NONE             ➔ drop             (무시)
SEV4                    ➔ dashboard_only   (대시보드 전용)
SEV3                    ➔ digest           (요약 리포트)
SEV1·SEV2 +
  automate 태그 설정 +
  scope != notify_only  ➔ remediate        (자동 조치 후보)
기타 SEV1·SEV2          ➔ triage           (초동 분석 대상)
```

`scope=notify_only` 설정은 `automate` 태그보다 우선 적용되어 조치 경로 진입을 차단합니다. (MSP 위탁 계약 제약 조건의 코드화)

### 2-2. LLM 트리아지 발동 조건 (`incident.should_triage`)

아래 조건 중 **가장 먼저 부합하는 항목** 발생 시 LLM 분석을 실행합니다:

| 순번 | 적용 조건 | 동작 결과 및 적용 사유 |
|---|---|---|
| 1 | `SEV1` 등급 | 무조건 발동 |
| 2 | 2건 이상 알림 병합 사건 | 발동 (복합 인과 관측 필요) |
| 3 | 로그/보안 데이터 **조회 실패 (`unavailable`)** | 발동 (**미상 상태**에 따른 보수적 분석 실행) |
| 4 | 단일 알림 + 교차 소스 1종 이상 수집 | 발동 |
| 기타 | 상기 조건 미부합 시 | 스킵 |

*(미연동 `disabled` 상태는 의도된 구성이지 장애가 아니므로 발동 사유에서 제외됩니다.)*

### 2-3. 심층 조사 발동 조건 (`holmes.should_investigate`)

평가 순서에 따라 발동 여부를 정밀 제어합니다:

| 순번 | 평가 조건 | 발동 여부 | 제어 목적 및 이유 |
|---|---|---|---|
| 1 | 기능 비활성화 상태 | 미발동 | 기능 미사용 설정 |
| 2 | MSP 데이터 + 마스킹 프록시 미배치 | **제외** | 데이터 외부 유출 방지 |
| 3 | `SEV1` 등급 | 발동 | 긴급 장애 분석 |
| 4 | LLM 분석 열화 (`degraded`) 상태 | 발동 | 1차 분석 품질 미비 보완 |
| 5 | 선판정 결과: **만성 (Chronic)** | **억제** | 기지 파악 장애 리소스 절감 |
| 6 | 선판정 결과: **신규 (New)** | 발동 | 지식 공백 영역 분석 |
| 7 | 병합 사건 발생 | 발동 | 복합 사건 분석 |

### 2-4. 승인 게이트 (Keep 워크플로)

시스템 설정 변경 및 외부 고객 통보 작업은 명시적 사용자 승인 클릭을 거치도록 제어합니다.

```yaml
triggers:
  - type: manual                                       # 승인 게이트: 수동 승인 필수
steps:
  - if: "'{{ alert.playbook }}' == 'service_restart'"   # 안전 게이트: 플레이북 매칭 검증
```

### 2-5. 조치 후 자동 재검증 (`remediate_service.yml`)

```yaml
failed_when: after.stdout != "active"
```

자동 조치 실행 후 `systemctl is-active` 상태를 확인하여 `active` 검증 실패 시 플레이북을 실패 처리합니다.

### 2-6. 리포트 데이터 제어 게이트

* **승인 전 데이터 상태:** `검토 대기` 상태로 격리
* **미산출 데이터 표기:** `-1` (`NOT_MEASURED`) 값으로 명시적 구별 표기

## 3. 데이터 반출 규칙

*(상세 명세: [`llm-data-contract.md`](llm-data-contract.md) 참조)*

- **화이트리스트:** 허용 목록 외 필드의 직렬화 차단
- **가역 가명화:** 치환 오류 방지를 위해 긴 원문 문자열부터 순차 치환을 수행하며, 미등록 IP는 정규식으로 자동 가명화 처리
- **멱등성 처리:** `(소스, 이벤트 ID, 이벤트 값)` 조합을 1시간 동안 인메모리 캐싱하여 중복 수신 시 `200 OK` (`duplicate`) 응답 반환

## 4. 게이트웨이 파이프라인 처리 흐름도

```text
알림 수신 (Alert Ingestion)
  ├─ 멱등성 검사 (중복 시 200 OK 처리)
  ├─ [판정] 심각도 정규화 ─────────── 3개 소스 눈금을 통합 SEV로 변환
  ├─ [게이트] 라우팅 경로 결정 ───── drop / dashboard / digest / remediate / triage
  ├─ [판정] 알림 분류 ─────────────── 태그 선언 우선, 키워드 폴백 적용
  ├─ [판정] 알림 병합 ─────────────── (호스트, 유형) + 브리지 조합, 디바운스 대기
  ├─ [판정] 만성/신규 선판정 ──────── 최근 90일 이력 건수 기준
  ├─ [게이트] LLM 트리아지 발동 여부 ── 교차 분석 조건 부합 시 발동
  │     └─ LLM 파이프라인 ──────────── 인과 설명 생성 (판정 로직 변경 불가)
  ├─ [게이트] 심층 조사 발동 여부 ── 신규·SEV1·열화 조건 시 발동 (만성 억제)
  └─ [게이트] 사용자 승인 ─────────── 시스템 변경 및 통보 작업 시 승인 필요
```
